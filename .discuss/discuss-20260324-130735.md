## 内容摘要
讨论围绕 HFT 场景下 JSON 库选型展开。初始争议在"手写解析器（~100-200ns）vs 通用库（~300ns）"和"simdjson vs yyjson vs Glaze"之间。关键转折点是 simdjson On-Demand 在 field ordering 不保证时性能暴跌 92% 的致命弱点——这对加密交易所消息是不可接受的风险。Glaze 以"同等性能 + field ordering 鲁棒性 + 编译时类型安全 + 零 DOM 分配"在第 3 轮获得 4/5 票支持。最终全票通过 Glaze，附条件：依赖隔离、fuzz test 前置验证、fallback 路径设计。

## 第 1 轮：各角色独立提出核心论点

### 【R3 性能狂热者 | 手写解析器是理论最优解】
1. 已知 schema 下手写 ~100-200ns，比通用库快
2. 通用库有不必要开销：UTF-8 验证、转义处理、数值验证
3. simdjson field ordering 不保证时暴跌 92%
4. SIMD 降频风险（pre-Ice Lake CPU）

### 【R1 风险卫士 | 手写解析器是安全噩梦】
1. JSON 规范边界多，手写 = CVE 工厂
2. 交易所消息格式会变化，手写脆弱
3. simdjson 有 OSS-Fuzz 持续验证
4. 解析错误代价远超 200ns 延迟节省

### 【R2 极简主义者 | 最小依赖优先】
1. simdjson 20K+ 行太大
2. yyjson 更极简：纯 C, ~7K 行, 1106 MB/s
3. Glaze 模板重，编译错误难调试
4. 极简 ≠ 手写，极简 = 最小外部依赖

### 【R4 实用主义者 | 看实测数据】
1. Apex 生产数据：simdjson P50 ~300ns, P99 ~1.3μs
2. Glaze 1200 MB/s 且 out-of-order 鲁棒
3. 手写加上错误处理后差距缩小到 50-100ns
4. JSON 解析不是真正瓶颈（占 tick-to-model 的 ~9%）

### 【R6 维护性倡导者 | 长期健康度】
1. simdjson 社区强，长期健康
2. yyjson / Glaze bus factor = 1
3. 手写维护成本最高
4. 建议 simdjson 或 yyjson

## 最终方案

### 核心决策
选用 **Glaze** 作为 JSON 库，不手写解析器。

### 方案细节

**选择 Glaze 的理由：**
- ~300ns/400B 消息，与 simdjson 持平
- out-of-order keys 下维持全速（决定性优势）
- 编译时 struct 映射，零 DOM、零分配
- 默认跳过 unknown keys，forward compatible
- 支持 `glz::quoted<double>` 处理 Binance 字符串数字

**实施要求：**
1. 依赖隔离 — 只在 eph-exchange/eph-json 内部使用
2. 编译优化 — explicit template instantiation
3. Fuzz test 前置 — libFuzzer + ASan/UBSan，Binance 消息 corpus
4. Fallback 路径 — 接口允许替换为 simdjson On-Demand
5. Micro-benchmark — Binance depth/trade 真实消息验证

**为什么不选其他：**
- simdjson：field ordering 暴跌 92% 不可接受
- yyjson：全 DOM 构建浪费，bus factor = 1
- 手写：安全风险高、维护成本高
- RapidJSON：3-4x 慢
- sonic-cpp：生产验证不足

### 已解决的分歧
- 手写 vs 库 → 全票否决手写
- simdjson vs Glaze → Glaze 胜出（field ordering）
- 编译时间 → extern template 解决
- Bus factor → 依赖隔离 + fallback 消解

### 未解决的权衡
- Glaze 版本策略：pin 特定版本 vs 跟踪最新
