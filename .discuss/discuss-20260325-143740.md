## 内容摘要
核心争议围绕三个独立子问题展开：(1) TX queue 无数据——`send_ws_ping()` 绕过 TX 队列是设计缺陷，全员同意修复（让 ping 走 `enqueue_tx()` 路径）；(2) RX pipeline 语义差异——Socket 版隐藏了内核协议栈延迟，这是物理事实而非 bug，通过报告标注解决；(3) 是否扩展 probe 架构——R14 提出的分层 probe 被收缩为可选的 `on_rx_decrypted` 单点扩展，作为独立后续增强。R3 最初提出的 `SO_TIMESTAMPNS` 方案被 R5 以时钟源不对齐为由否决。最终共识：修 TX queue 路径 + 标注 RX 语义差异，不大改架构。

## 代码事实确认

| 探针点 | 调用位置 | 线程 |
|--------|----------|------|
| `on_rx_arrival` | `rx_loop()` 中 `tcp_->poll_rx()` 回调内 | RX 线程 |
| `on_rx_deliver` | `deliver_message()` 中，TLS 解密 + WS 解帧完成后 | RX 线程 |
| `on_tx_enqueue` | `enqueue_tx()` 成功入队后 | App 线程 |
| `on_tx_flush` | `tx_loop()` 中批量编码加密后、`tcp_->send()` 前 | TX 线程 |
| `send_ping()` | **直接在 TX loop 构建发送，不经过 TX 队列** | TX 线程 |

关键差异：
- Socket: `poll_rx()` = `::recv()` syscall，数据已过内核协议栈
- DPDK: `poll_rx()` = `rte_eth_rx_burst()` + 用户态 TCP 状态机，数据从网卡直取

## 第 1 轮：核心论点

**【第一性原理者 R5 | 先定义"公平"再讨论方案】**
论点：问题不是"如何让数字相同"，而是"两个后端各自的 benchmark 要回答什么问题"。当前 RX pipeline 指标的语义是"从 Transport 层拿到原始字节 → 交付应用层消息"——这个定义对两个后端是一致的，差异在于"原始字节"的起点不同。真正该问的是：用户拿到这两组数字后要做什么决策？如果是选型决策（DPDK vs Socket），比较 RX pipeline 本身就不合适——应该比较端到端（网卡到应用）。如果是调优决策（优化 TLS/WS 解帧），当前打点是公平的，因为两边 TLS+WS 代码路径完全相同。

**【性能狂热者 R3 | 必须补齐 Socket 的内核盲区】**
论点：当前 Socket 版的 `on_rx_arrival` 丢失了内核协议栈的全部延迟——中断合并（`adaptive-rx`）、NAPI softirq、TCP 重组、socket buffer 拷贝，这些在高负载下可达 50-100μs。Socket 版应增加 `SO_TIMESTAMPNS` 获取内核收包时间戳，在 `poll_rx()` 回调中用 `cmsg` 取出硬件/软件时间戳，计算内核栈延迟并单独上报。同时 TX 侧 `send_ping()` 绕过了 TX 队列，导致两个版本都没有 TX queue 采样——应将 ping 也走 `enqueue_tx()` 路径，或者在 `send_ws_ping()` 中手动调用 probe。

**【极简主义者 R2 | 不改架构，改文档】**
论点：两个 example 的 HftProbe 代码一字不差，Transport 的 probe 接口也一致——架构上已经是公平的。差异来自物理事实：Socket 有内核栈，DPDK 没有。加 `SO_TIMESTAMPNS` 引入平台特定代码（`cmsg` 在不同 OS 上行为不同），且硬件时间戳需要网卡支持。正确做法是在报告输出中明确标注测量区间语义差异，让用户自己判断。Probe 的职责是测量 Transport 层自身开销，不是测量操作系统。

**【架构师 R14 | Transport 需要分层 probe 接口】**
论点：根本问题是 `TransportProbe` concept 只有 4 个点，粒度太粗。应扩展为分层 probe：L1 wire→raw bytes, L2 raw bytes→decrypted, L3 decrypted→deframed, L4 deframed→delivered。Socket 的 L1 报 0，DPDK 的 L1 报用户态 TCP 延迟，L2-L4 苹果对苹果。

**【实用主义者 R4 | 看数据说话】**
论点：Socket P50 1,058ns vs DPDK P50 1,985ns 的差异主要来自 DPDK 用户态 TCP 状态机的开销（`process_rx()` 中的序列号追踪、乱序重组），不是"更早的打点起点"。要验证假设，在 DPDK `process_rx()` 前后加 TSC 采样即可，不需要大改架构。

## 第 2 轮：交锋

**【第一性原理者 R5 | 维持立场】**
反驳 [R3]：`SO_TIMESTAMPNS` 获取的是 softirq 时间戳，不是网卡硬件时间戳。DPDK 用 TSC，`SO_TIMESTAMPNS` 用 `ktime_get_real()`，混合对比没有意义。
反驳 [R14]：L1 对 Socket 永远为空值，定义必然为空的接口层违反接口契约完整性。
联盟 [R2]：同意"标注语义差异"是最低成本高收益方案。

**【性能狂热者 R3 | 部分让步】**
放弃 `SO_TIMESTAMPNS` 方案（时钟源不对齐）。坚持修 TX queue——`send_ping()` 绕过队列导致永远无数据。
反驳 [R2]："改文档"是逃避，TX queue 始终 (no samples) 让用户怀疑 probe 坏了。
反驳 [R5]：选型场景下建议文档给出 `perf`/`bpftrace` 单行命令测内核栈延迟。

**【极简主义者 R2 | 调整立场】**
同意 ping 绕过 TX queue 是设计缺陷。
反驳 [R14]：分层 probe 让 concept 从 4 方法膨胀到 8-10 个，过度设计。
联盟 [R3]：TX queue 修复——让 ping 走 `enqueue_tx()` 是正确的。

**【架构师 R14 | 收缩方案】**
收缩为：不扩展 concept，在 `rx_loop()` TLS 解密后增加可选 `on_rx_decrypted(tsc)`。用 `if constexpr` + concept 检测，向后兼容。
反驳 [R4]：`on_rx_decrypted` 能精确拆分解密/解帧两段，不比临时加 TSC 更侵入。

**【实用主义者 R4 | 维持立场】**
反驳 [R14]：`on_rx_decrypted` 只能拆分 TLS 和 WS，不能拆分 DPDK 用户态 TCP 和 TLS。
联盟 [R3]：同意 ping 必须走 TX queue。

## 第 3 轮：深入子议题

**【第一性原理者 R5 | 提出分类方案】**
三个独立子问题：(1) TX queue 无数据——设计缺陷，修复明确；(2) RX pipeline 语义差异——物理事实，标注解决；(3) 更细粒度 probe——独立增强需求。

**【性能狂热者 R3 | 聚焦 TX 修复】**
方案 A：让 `send_ws_ping()` 调用 `enqueue_tx()` + 设置 ping 标记。方案 B：手动调 probe。推荐 A——语义一致。

**【极简主义者 R2 | 接受方案 A】**
ping 走 TX queue 后优先级降低可接受（example 中数据发送频率极低）。

**【架构师 R14 | 让步但保留建议】**
`on_rx_decrypted` 作为独立增强，不阻塞。建议代码中留注释锚点。

**【实用主义者 R4 | 收敛】**
方案 A 需确保 ping 在 TX 线程中仍记录 `last_ping_tsc_`，需要消息元数据中区分 ping 和普通帧。

## 第 4 轮：收敛与立场修正

- **R5**：维持核心观点。被 R3 说服修 TX queue。被 R14 启发 `on_rx_decrypted` 有价值但不阻塞。
- **R3**：放弃 `SO_TIMESTAMPNS`（R5 指出时钟源问题）。坚持 TX queue 修复（方案 A）。接受 RX 语义差异用标注解决。
- **R2**：从"只改文档"让步到"修 TX queue + 改文档"。
- **R14**：从"分层 probe"收缩到可选 `on_rx_decrypted`，接受作为独立增强。
- **R4**：同意 TX 修复可立即做，profiling 作为后续工作。

## 最终方案

### 核心决策
当前打点框架在 RX pipeline 上存在语义差异（物理事实，非 bug）；TX queue 无数据是 `send_ping()` 绕过队列的设计缺陷，应修复；不需要大改架构。

### 方案细节

**立即修复（1 个 PR）：**
1. **TX Queue 路径修复**：让 `send_ws_ping()` 通过 `enqueue_tx()` 发送 ping 帧（方案 A）。消息元数据中增加 `is_ping` 标记，TX 线程处理 ping 帧时记录 `last_ping_tsc_` 用于 RTT 计算。两个版本都能产生 TX queue latency 数据。
2. **报告标注语义差异**：在 example 的报告输出中，RX Pipeline 标题改为标注测量区间：
   - Socket: `RX Pipeline (socket recv → deliver)`
   - DPDK: `RX Pipeline (NIC rx_burst → deliver, includes userspace TCP)`

**后续增强（独立 PR，不阻塞）：**
3. **可选 `on_rx_decrypted` 探针**：在 `rx_loop()` TLS 解密完成后增加打点，拆分解密/解帧两段延迟。通过 concept 检测向后兼容。
4. **DPDK TCP profiling**：在 `process_rx()` 中临时插入 TSC 采样，量化用户态 TCP 状态机开销。

### 已解决的分歧
- **是否加 `SO_TIMESTAMPNS`** → 否。时钟源不对齐（TSC vs ktime），混合对比无意义
- **是否分层 probe** → 否（当前）。缩减为可选的单点扩展 `on_rx_decrypted`，作为独立增强
- **TX 修复方案 A vs B** → 方案 A（ping 走 `enqueue_tx()`），语义一致性优先

### 未解决的权衡（需用户决策）
- **ping 走 TX queue 后优先级降低**：如果未来 example 有高频数据发送，ping 可能被积压。若优先级敏感 → 增加 priority queue 或保留快速路径但手动调 probe；若不敏感（当前场景） → 方案 A 直接实施
- **`on_rx_decrypted` 是否值得正式化**：取决于 DPDK profiling 结果——若用户态 TCP 占比 >50%，值得拆分；否则当前 4 点够用
