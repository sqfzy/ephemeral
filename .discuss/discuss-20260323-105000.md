## 内容摘要
围绕 ConnectorConfig 必填字段强制方式的三个候选方案（构造函数、拆分结构体、编译期 Builder）展开讨论。核心争议在于类型安全与代码简洁的平衡。R12 指出构造函数对多字段 config 不可扩展（TransportConfig 有 15+ 字段），R7 指出相邻 string 参数的安全风险，这两个论点淘汰了方案 1 和 3。最终收敛为方案 2 的增量变体：新增 DpdkEndpoint 结构体（2 个必填字段）+ 简化 connect() 重载，现有 API 保持不变。

## 第 1 轮

**【极简主义者 R2 | 支持方案 1：构造函数】**
论点：构造函数是最基本的强制参数机制。零认知负担，一行搞定。方案 2 引入新类型，方案 3 代码量是结构体 3 倍，都是过度设计。

**【用户代言人 R7 | 支持方案 2：拆分结构体】**
论点：designated initializers 是 C++20 最大可读性改进。方案 2 同时保持 aggregate 和编译期强制。

**【激进创新者 R8 | 支持方案 3：Builder】**
论点：唯一能给出精确编译错误信息的方案。requires 约束直接告诉你少填了什么。

**【实用主义者 R4 | 倾向方案 2】**
论点：方案 3 需要 50-60 行样板包装 7 字段结构体。方案 2 只提取 3 行新结构体。ROI 差距巨大。

**【系统思维者 R12 | 关注全局一致性】**
论点：库里还有 TransportConfig、SocketConfig、TcpConfig 等。不管选哪种方案，都应对所有 config 一视同仁。

## 最终方案

### 核心决策
方案 2 增量变体：新增 DpdkEndpoint + 简化 connect() 重载，保留现有 API。

### 方案细节
```cpp
struct DpdkEndpoint {
    std::string local_ip;
    std::string gateway_ip;
};

// 新增简化重载
auto connect(std::string_view host, const DpdkEndpoint& ep,
             const ConnectorOptions& opts = {});

// 现有重载保留
auto connect(const ConnectorConfig& cfg, const TransportConfig& tp_cfg);
```

### 已解决的分歧
- 构造函数 vs 拆分 → 构造函数对多字段 config 不可扩展
- Builder vs 拆分 → Builder 代码量大，ROI 不合理
- 是否改现有结构体 → 不改，增量新增
- 命名 → DpdkEndpoint（语义清晰）

### 未解决的权衡
- ConnectorOptions 是否需要独立新类型，还是直接复用 ConnectorConfig（local_ip/gateway_ip 由 DpdkEndpoint 传入后剩余字段就是 options）
