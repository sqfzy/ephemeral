## 坑与教训

### 坑 1：GCC 14 已安装但 xmake 找不到

**背景**
AWS AL2023 默认 GCC 11，项目需要 C++23。`gcc14-c++` 已通过 dnf 安装。

**现象**
`xmake f --toolchain=gcc-14` 报 `toolchain("gcc-14"): not found!`

**当时的错误判断**
以为需要通过 xmake 的包管理器安装 GCC 14。

**根因**
xmake 的 `gcc-14` toolchain 期望二进制名为 `g++-14`，但 AL2023 的包命名为 `gcc14-g++`。xmake 的自动探测逻辑不覆盖这种命名。

**解决方式**
手动指定：`xmake f --cc=gcc14-cc --cxx=gcc14-g++`

**教训**
Amazon Linux 的 GCC 多版本包命名与 Debian/Ubuntu 不同（`gcc14-g++` vs `g++-14`）。在多发行版支持场景下，xmake.lua 应在顶部显式检测并设置工具链，而非依赖自动探测。

**可复用的模式**
当构建工具报告"找不到工具链"时，先用 `which` 和 `rpm -ql` 确认二进制实际路径，再手动指定给构建系统。

**相关代码位置**
`xmake.lua:5` (`set_languages("c++23")`)

### 坑 2：GCC 14 编译 + GCC 11 libstdc++ 链接

**背景**
用 `--cc=gcc14-cc --cxx=gcc14-g++` 编译成功，但链接时出错。

**现象**
```
undefined reference to `std::__cxx11::basic_string<...>::_M_replace_cold'
undefined reference to `__cxa_call_terminate'
```

**当时的错误判断**
第一反应是缺少某个库。

**根因**
GCC 14 生成的目标文件引用 GLIBCXX_3.4.31 和 CXXABI_1.3.15 符号，但链接器默认搜索 GCC 11 的 libstdc++（/usr/lib64），该版本不包含这些符号。GCC 14 的 libstdc++ 在 `/usr/lib/gcc/aarch64-amazon-linux/14/`。

**解决方式**
```
--ldflags="-L/usr/lib/gcc/aarch64-amazon-linux/14 -Wl,-rpath,/usr/lib/gcc/aarch64-amazon-linux/14"
```

**教训**
在系统中存在多个 GCC 版本时，仅指定编译器不够，还必须确保链接器能找到匹配版本的运行时库。`gcc14-g++ -print-search-dirs` 可以快速定位正确的库路径。

**可复用的模式**
`<compiler> -print-search-dirs | grep libraries` + `nm -D <libstdc++.so> | grep <missing_symbol>` 是诊断 libstdc++ 版本不匹配的标准流程。

**相关代码位置**
xmake 配置层面，非源码问题

### 坑 3：DPDK ARM64 的 RTE_FORCE_INTRINSICS

**背景**
vcpkg 构建的 DPDK 在 ARM64 上使用。

**现象**
```
rte_byteorder.h:9: #error Platform must be built with RTE_FORCE_INTRINSICS
```

**当时的错误判断**
以为是 vcpkg DPDK 包构建配置错误。

**根因**
`rte_byteorder.h`（ARM 版本）在文件顶部检查 `RTE_FORCE_INTRINSICS`，但这个 define 实际定义在 `rte_build_config.h` 中（通过 `rte_config.h` 间接包含）。问题是 DPDK 头文件被直接 include 时，`rte_config.h` 可能还没被包含。vcpkg 的 pkgconfig Cflags 也没有提供这个 define。

**解决方式**
两管齐下：
1. `add_defines("RTE_FORCE_INTRINSICS", { public = true })` — 确保 define 存在
2. `add_cxflags("-include", "rte_config.h", { public = true })` — 强制在所有翻译单元前 include

**教训**
DPDK 在 ARM64 上的头文件依赖顺序与 x86 不同。x86 不需要 `RTE_FORCE_INTRINSICS`（内联汇编直接可用），但 ARM64 必须用 compiler intrinsics。当 pkgconfig 没有提供必要的编译标志时，`-include` 是一种干净的 workaround。

**相关代码位置**
`xmake.lua:91-92`, `~/vcpkg/installed/arm64-linux/include/rte_byteorder.h:9`

### 坑 4：headeronly target 的 add_linkgroups 不传播

**背景**
`eph-dpdk` 是 `set_kind("headeronly")` 的 target，其中配置了 `add_linkgroups(..., { whole = true })`。

**现象**
DPDK 二进制（test_eal, dpdk_quickstart）运行时 EAL init 失败："No such device"。`strings` 检查二进制发现没有任何 PMD 驱动名称字符串。

**当时的错误判断**
以为是 EAL 参数问题（`-a` 指定了设备但找不到）。

**根因**
xmake 的 headeronly target 不参与链接阶段。`add_linkgroups` 只对有实际链接步骤的 target（binary/static/shared）生效。headeronly target 上的 linkgroups 被静默忽略，不会传播到依赖它的 binary target。

**解决方式**
创建 `apply_dpdk_pmd_linkgroups()` helper 函数，在每个依赖 DPDK 的 binary target 中显式调用。

**教训**
xmake（以及大多数构建系统）中，headeronly target 的语义是"仅提供头文件和编译标志"。链接属性（library groups、link flags）必须附加到最终的 binary target。这与 `add_packages`（可以传播链接库）的行为不同，容易混淆。

**可复用的模式**
当静态库的 `__attribute__((constructor))` 不执行时，检查链接命令中是否有 `--whole-archive` 包裹。当使用 headeronly target 传播链接属性时，验证属性是否真的到达了最终 binary。

**相关代码位置**
`xmake.lua:93-95`（注释），`xmake.lua:138-141`（helper 函数）

### 坑 5：rte_mempool_ring 遗漏导致 EINVAL（本次最隐蔽的问题）

**背景**
修复了 linkgroups 传播后，EAL init 成功，ARP 解析成功，但 `rte_pktmbuf_pool_create` 返回 EINVAL (22)。

**现象**
```
rte_pktmbuf_pool_create failed: pool_size=4095, rte_errno=22: Invalid argument
```

**当时的错误判断**
依次怀疑：
1. hugepage 不够 → 验证 256 pages, 254 free，排除
2. IOVA 模式错误 → PA 模式是 ENA 要求的，排除
3. pool_size 参数错误 → 4095 = 2^12 - 1，符合 DPDK 要求，排除
4. VFIO noiommu 不支持 mempool → 用系统 dpdk-testpmd 验证，testpmd 成功创建 pool

**根因**
关键线索来自 dpdk-testpmd 的日志：
```
testpmd: preferred mempool ops selected: ring_mp_mc
```

DPDK 的 mempool 实现是插件式的。`rte_mempool_ring.a` 包含默认的 ring-based mempool ops（`ring_mp_mc`），它通过 `__attribute__((constructor))` 在加载时自注册。当这个 `.a` 没有被 `--whole-archive` 链接时，constructor 被 strip，DPDK 找不到任何可用的 mempool ops 实现，于是 `rte_pktmbuf_pool_create` 返回 EINVAL。

**解决方式**
在 `apply_dpdk_pmd_linkgroups()` 中添加 `"rte_mempool_ring"`。

**教训**
**DPDK 的 constructor 自注册模式不仅限于 PMD 网卡驱动**。mempool ops、crypto ops、bus drivers 等模块都使用相同模式。在静态链接 DPDK 时，必须识别所有依赖 constructor 注册的模块并 whole-archive 它们。诊断时，用系统已安装的 DPDK 工具（dpdk-testpmd）做对比测试是快速定位差异的有效方法。

**可复用的模式**
当 DPDK 函数返回 EINVAL 且参数看起来正确时，检查是否有 constructor 注册的插件缺失。对比方法：`strings <binary> | grep <plugin_name>` 确认插件是否被链接进来。

**相关代码位置**
`xmake.lua:139`（`apply_dpdk_pmd_linkgroups()`），`eph-dpdk/include/eph/dpdk/platform.hpp:223-234`

### 坑 6：test_connector 在单端口 NIC 上的测试失败

**背景**
AWS 实例有 2 个 ENA NIC，一个用于 SSH（ens34），一个绑定 DPDK（ens35）。DPDK 只能看到 1 个端口。

**现象**
`ConnectValidation.EmptyLocalIpReturnsError` 通过（消耗了唯一端口），后续 3 个测试报 "No DPDK ports available"。测试期望得到参数验证错误（如 "local_ip"），但实际得到 Platform 创建失败。

**当时的错误判断**
无 — 问题原因从日志中一目了然。

**根因**
`connector::connect()` 先创建 Platform（独占端口），再验证参数。EAL 是进程全局的，Platform 创建后端口被占用，同进程内后续 Platform 创建调用找不到可用端口。

**解决方式**
尚未修复。建议：将参数验证（local_ip、gateway_ip 非空检查）移到 Platform::create() 调用之前（fail-fast）。

**教训**
DPDK 资源（EAL、port）是进程级单例。测试套件中的多个测试共享同一进程时，资源独占会导致测试间干扰。测试应在资源获取之前完成所有可以提前检查的验证，或在资源不可用时 GTEST_SKIP。

**相关代码位置**
`eph-dpdk/include/eph/dpdk/connector.hpp`，`tests/dpdk/test_connector.cpp:110-158`

## 心得与洞察

### 心得 1：用系统工具做对比测试是诊断构建问题的利器

**发现场景**
`rte_pktmbuf_pool_create` 返回 EINVAL，穷尽参数层面的排查后无果。运行系统的 `dpdk-testpmd` 发现它能成功，从其日志中发现 "mempool ops selected: ring_mp_mc" 线索。

**核心洞察**
当自建二进制行为异常但相同环境下系统工具正常时，差异一定在链接/编译层面。对比系统工具的日志输出可以快速缩小问题范围。

**为什么有价值**
避免在运行时参数层面无谓地兜圈子。直接跳到"为什么系统版本行但我的不行"这个更有效的问题。

**应用条件**
适用于所有依赖外部库的项目。前提是有一个已知正常工作的参照物。

---

### 心得 2：DPDK 静态链接的心智模型 — "constructor 清单"

**发现场景**
连续遇到两个 whole-archive 问题（PMD 驱动 + mempool ops），意识到 DPDK 的模块注册是统一模式。

**核心洞察**
DPDK 的插件体系完全依赖 `__attribute__((constructor))` 在 `main()` 之前自注册。动态链接时这是自动的（.so 加载即执行 constructor）。静态链接时，必须显式 whole-archive 每一个需要 constructor 的模块。可以通过以下命令找出所有需要 whole-archive 的模块：
```bash
for f in /path/to/dpdk/lib/librte_*.a; do
    nm $f | grep -q "__rte_.*_register\|RTE_INIT" && echo $f
done
```

**为什么有价值**
将来升级 DPDK 版本或添加新功能时，可以系统性地检查是否遗漏了需要 whole-archive 的模块，而不是等到运行时 EINVAL 才发现。

**应用条件**
适用于所有使用 constructor 自注册模式的 C 库（不限于 DPDK）。例如 gRPC 的 plugin 注册也有类似模式。

---

### 心得 3：DPDK 在 AWS Graviton 上的 IOVA 模式约束

**发现场景**
尝试 `--iova-mode=va` 解决 mempool 问题时，发现 ENA 驱动要求 PA 模式。

**核心洞察**
AWS Graviton 没有硬件 IOMMU，DPDK 使用 VFIO No-IOMMU 模式。ENA PMD 要求 IOVA PA（Physical Address）模式，VA 模式下 PCI bus 拒绝初始化设备。这意味着：
- 必须有 hugepage（PA 模式需要物理连续内存）
- `--no-huge` 在真实 NIC 场景下不可用
- 测试用 `--no-huge --no-pci --vdev=net_null0` 可以绕过此限制

**应用条件**
所有在 AWS Graviton 上使用 DPDK 的场景。在 Intel 有 VT-d 的环境下，VA 模式可用，约束不同。
