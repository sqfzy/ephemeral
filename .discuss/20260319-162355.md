### Step 2: 结构化讨论

#### 第 1 轮：各角色独立提出核心论点

**【性能狂热者 R3 | 还有明确的优化空间】**

论点：
1. 批量操作（Batch）缺失：高吞吐场景下，单次 push/pop 的 atomic store/load 开销无法摊销。应提供 `try_push_batch` / `try_pop_batch` 接口。
2. `std::invoke` + `std::forward` 的间接调用开销可能阻碍内联。
3. `try_pop()` 返回 `std::optional<T>` 引入不必要的构造开销。

**【极简主义者 R2 | 当前设计已足够好】**

论点：
1. 影子索引 + cache line 对齐已覆盖 SPSC 队列最关键的优化。
2. API 表面积适中，不应再添加更多接口。
3. 代码不到 300 行，结构清晰。任何优化必须证明收益超过复杂度成本。

**【风险卫士 R1 | 正确性隐患需优先处理】**

论点：
1. 头文件中的 `using` 声明（第 13-15 行）污染全局命名空间。
2. `size()` / `empty()` / `full()` 的 relaxed 语义需文档标注。
3. 阻塞接口的纯 `cpu_relax()` 自旋在长时间满/空场景下浪费 CPU。

**【实用主义者 R4 | 拿数据说话】**

论点：
1. 没有 benchmark，讨论 "优化空间" 是空谈。
2. 应与 rigtorp/SPSCQueue、Folly 等竞品对比。
3. 实际使用场景决定优化方向。

**【第一性原理者 R5 | 质疑根本约束】**

论点：
1. `TrivialData` 约束排除了常见类型（std::string 等），是否过严？
2. 固定容量的模板参数 vs 运行时参数的取舍。
3. 缺少 "可丢弃" overwrite 模式的变体。

#### 第 2 轮：交叉反驳

**【性能狂热者 R3】**
- 反驳 R4：batch 收益可从硬件模型原理推导，不必依赖 benchmark。
- 反驳 R2：batch 接口是正交功能，不影响现有简洁性。
- 反驳 R5：放松 TrivialData 属于另一个队列实现的范畴。

**【极简主义者 R2】**
- 反驳 R3：batch 引入认知负担（batch 大小、部分失败处理等）。
- 反驳 R5：支持非 trivial 类型会把 300 行变 1000 行。
- 联盟 R1：同意 `using` 声明问题应立即修复。

**【风险卫士 R1】**
- 反驳 R3：`std::invoke` 在 -O2 下内联能力极强，需反汇编证据。
- 反驳 R5：constexpr mask 是零风险的性能保证。
- 补充：阻塞接口的自旋问题仍是最重要的实际问题。

**【实用主义者 R4】**
- 反驳 R3：atomic store 的开销模型远比线性可加复杂。
- 联盟 R1：`using` 声明和自旋策略是确定性改进。

**【第一性原理者 R5】**
- 反驳 R2：部分同意非 trivial 应独立实现。
- 反驳 R1：SPSC 不变量下 `tail >= head` 恒成立，无回绕风险。
- 补充：`try_push` 的 `is_assignable_v` 约束可能允许隐式转换。

#### 第 3 轮：确定性改进 vs 可选优化

**【性能狂热者 R3】**
- 接受区分"确定性改进"和"需 benchmark 的优化"。
- 撤回 `std::invoke` 影响内联的论点。
- 反驳 R2：batch 应是 "全部或全不" 语义，认知负担低。

**【极简主义者 R2】**
- 接受确定性修复清单。
- 反驳 R3：即使简单 batch 也是 30%+ 代码膨胀。
- 联盟 R4：batch 应在有 benchmark 后再决定。

**【风险卫士 R1】**
- 形成 P0/P1 改进清单：using 修复、状态查询文档、阻塞退避。

**【实用主义者 R4】**
- 提炼行动矩阵（确定执行/推迟/不执行）。

**【第一性原理者 R5】**
- 建议增加 `static_assert` 确保 WriterLine/ReaderLine 布局正确。

#### 第 4 轮：退避策略 & batch 最终立场

**【性能狂热者 R3】**
- 反驳 R1：yield 触发上下文切换（~1-10us），在 SPSC 低延迟场景中是错误选择。
- 联盟 R2：退避策略不应内置。

**【极简主义者 R2】**
- 接受 R5 的 `static_assert` 建议。

**【风险卫士 R1】**
- 接受退避不内置，转为建议加文档。
- 补充：缺少显式 `= delete` 拷贝/移动。

**【实用主义者 R4】**
- 更新行动矩阵：移除退避，增加 delete 和 static_assert。

#### 第 5 轮（最后一轮）：立场修正

**【性能狂热者 R3】** 撤回 std::invoke 和退避论点；接受 static_assert 和 delete；坚持 batch 有价值但接受推迟。

**【极简主义者 R2】** 接受所有确定性改进；坚持 batch 应极简或推迟；坚持非 trivial 应独立实现。

**【风险卫士 R1】** 撤回内置退避；撤回 size() 回绕担忧（保留文档建议）；坚持 using 修复为最高优先级。

**【实用主义者 R4】** 接受部分优化可从原理推导；坚持所有确定性改进优先于性能优化。

**【第一性原理者 R5】** 接受 TrivialData 和编译时 Capacity 在当前定位下合理；撤回收紧 try_push 约束建议。

## 最终方案

### 核心决策
bounded_queue.hpp 是高质量的 SPSC 实现，核心算法无需改动；优化空间集中在代码卫生、防御性断言和文档层面。

### 方案细节

**立即执行（P0/P1）：**

1. **修复头文件 `using` 声明污染**（第 13-15 行）→ 移入 namespace 或改用全限定名
2. **显式 `= delete` 拷贝和移动操作**
3. **添加 `static_assert` 布局检查**（确保 WriterLine/ReaderLine 不超过 cache line）
4. **状态查询函数加文档标注**（估计值、仅供监控/调试）
5. **阻塞接口加使用场景文档**（假设 CPU-pinned 线程、短暂拥塞）

**推迟决策（P2/P3）：**

6. **batch 接口** — 需 benchmark 验证后决定
7. **非 trivial 类型支持** — 独立实现

### 已解决的分歧
- 退避策略 → 不内置（纯自旋是 SPSC pinned 场景的正确选择）
- std::invoke 内联 → 不是问题（编译器 -O2 完全内联）
- TrivialData 约束 → 保持现状
- 编译时 vs 运行时 Capacity → 保持编译时

### 未解决的权衡（需用户决策）
- batch 接口：若高吞吐批量传输选加入；若单元素低延迟通信选不加入
- optional try_pop 是否保留：若追求最小 API 考虑移除；若追求便利性保留
