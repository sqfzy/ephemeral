### 心得与洞察

#### 心得 1：Header-only 库的日志控制需要全局策略

**发现场景**：审查 10 个文件中的日志器创建代码
**核心洞察**：每个模块独立创建 spdlog logger 并硬编码 trace 级别，导致用户无法通过 `spdlog::set_level()` 统一控制日志输出。删除 `set_level` 调用让日志器继承全局默认级别，是最简单的修复。
**应用条件**：header-only 库中，日志器应始终从全局默认继承级别，除非有明确的每模块级别配置接口。

#### 心得 2：close frame buffer 大小应由协议常量推导

**发现场景**：审查 stop() 中的硬编码 128 字节 buffer
**核心洞察**：WebSocket close frame 最大 payload 125 字节 + header 14 字节 = 139 字节。使用 `ws::kMaxFrameHeaderLen + 125` 计算而非硬编码数字，既正确又自文档化。
**应用条件**：任何协议层 buffer 大小都应从协议常量推导。

### 关键决策

#### 决策 1：搁置 encrypt() API 的临时覆写设计

**选项**：A) 保留当前设计（文档标注 caller 保证 1 字节可写空间） vs B) 改为内部 memcpy 避免 in-place mutation
**选择**：A（搁置）
**原因**：这是热路径优化（避免全 payload memcpy），所有调用方已正确保证。修改影响面大且需要 benchmark 验证。
**现在回看**：正确决策——这是 /refactor 或 /discuss 的议题，不是 /improve 应处理的。
