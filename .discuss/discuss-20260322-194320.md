## 内容摘要
用户希望 DPDK `connect()` 能直接接受 hostname 而非预解析的 IP，并将 `resolve_hostname` 纳入库。争议焦点是 DNS 时序安全——独占 NIC 模式下 EAL 初始化后内核 DNS 不可用。R1（风险卫士）和 R3（性能狂热者）反对将 DNS 作为默认路径。R12（系统思维者）提出两个重载共存方案打破僵局：hostname 重载（从 `transport_cfg.remote_host` 自动解析）+ server_ip 重载（现有）。R2 发现 hostname 已在 TransportConfig 中，无需新参数。全员接受。

## 第 1 轮

**【用户代言人 R7 | 极度简化】**
论点：当前 run_dpdk 仍有 55 行。理想体验是 `connect(conn_cfg, transport_cfg)` 无需手动 DNS。resolve_hostname 每个 DPDK 用户都需要且实现一样，应由库提供。

**【风险卫士 R1 | 警惕时序陷阱】**
论点：DNS 必须在 EAL 初始化之前完成（独占 NIC 模式下内核栈不可用）。connect() 内置 DNS 时，如果用户已在外部初始化 EAL，DNS 可能静默失败。

**【性能狂热者 R3 | DNS 不属于数据面库】**
论点：eph-dpdk 是数据面库，getaddrinfo() 是阻塞的内核系统调用。DPDK 用户可能有自己的 DNS 方案。resolve_hostname 作为 utility 可以，但不应是 connect() 的默认路径。

**【系统思维者 R12 | 分层问题】**
论点：connect() 已跨 eph-dpdk 和 eph-net 边界。再加 DNS 就变成跨三层。建议：独立 resolve_hostname utility + connect() 双重载（ip 版和 hostname 版）。

**【极简主义者 R2 | 审视边界】**
论点：resolve_hostname 由库提供合理。但 URL 解析级别的封装走太远了。提供 utility + 重载即可。

## 第 2 轮

**【R7】** 反驳 R1：大多数 DPDK 场景用 bifurcated driver，DNS 可用。为 80% 常见场景优化。反驳 R3：库里已有 arp::resolve()（也是控制面操作），DNS 同理。
**【R1】** 反驳 R7：库不能假设 driver 类型。让步：hostname 重载可以，但错误信息必须提示独占 NIC 问题。
**【R3】** 反驳 R7：ARP 通过 DPDK 数据面收发包，不依赖内核栈。DNS 依赖 getaddrinfo()。两者本质不同。接受 resolve_hostname 作为 utility。
**【R12】** 补充：hostname 重载可在 DNS 超时时输出 WARNING 日志。
**【R2】** 反驳 R3：C++ 重载惯例已足够区分，不需要命名区分。

## 最终方案

### 核心决策
将 resolve_hostname 纳入库，并为 connect() 增加无需 server_ip 参数的 hostname 重载。

### 方案细节

1. `resolve_hostname()` 移入 `connector.hpp` 作为库 utility
2. `connect()` hostname 重载：从 `transport_cfg.remote_host` 解析 DNS，转发给 ip 重载
3. DNS 失败错误信息包含独占 NIC 模式提示

### 已解决的分歧
- DNS 在库内还是库外 → 两个重载共存
- DNS 时序风险 → 错误信息 + @warning 文档
- ARP vs DNS 类比 → ARP 走数据面，DNS 走内核栈，本质不同
- 命名区分 → 标准 C++ 重载
