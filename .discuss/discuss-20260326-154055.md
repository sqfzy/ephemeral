## 内容摘要

议题：`process_ws_data_twophase_fast` 快速路径 + `SymbolHashFn` 配置字段的代码设计质量评审。核心争议在于 200 行并行路径（含重复的控制帧处理和手写 WS 头解析）是否值得 5% 的实测收益。R4（实用主义者）首先指出实测数据显示唯一有效优化是快速哈希函数，不需要独立路径。R14（架构师）指出 `SymbolHashFn` 把业务概念（symbol hash）泄漏到通用 Transport 层，且与 `on_frame_filter` 语义重叠、优先级隐式。R6（维护性倡导者）量化了控制帧处理重复和 WS 校验跳过的维护风险。R3（性能狂热者）在第 3 轮承认抽象层次问题，但坚持快速扫描技术本身正确。最终全员收敛到 R14 方案：删除快速路径，给 `make_twophase_filter` 加原生函数指针重载，优化封装在 filter 层。

## 第 1 轮

**【R4 实用主义者 | 唯一有效的优化不需要快速路径】**

论点：报告自己证明了——快速扫描、紧凑哈希表、直接入队、位掩码合计只贡献 5%，在噪声范围内。真正有效的是把 FNV-1a 换成 4 字节直接读取。这件事完全可以在现有的 `make_twophase_filter` + `process_ws_data_filtered` 路径中完成——只需让用户传一个更快的哈希函数。200 行新代码换 5% 的不可靠收益，ROI 为负。

**【R2 极简主义者 | 两条路径是设计债务】**

论点：现在 `process_ws_data` 有三条分支：`symbol_hash_fn` → `on_frame_filter` → 内联处理。`process_ws_data_twophase_fast` 200 行代码中，控制帧处理（ping/pong/close）是从 `dispatch_indexed_frame` 手动复制粘贴的。WS 头部解析是从 `ws::decode_frame` 手动重写的。这不是优化，是分叉。每次修 `dispatch_indexed_frame` 或 `ws::decode_frame` 的 bug，都要记得同步改快速路径——但没有编译器会提醒你。

**【R3 性能狂热者 | 快速路径是正确的架构模式】**

论点：热路径特化是标准的高性能设计模式（Linux 网络栈、DPDK 本身都有 fast path / slow path 分离）。通用路径（`process_ws_data_filtered`）保留兼容性，快速路径针对已知场景极致优化。`SymbolHashFn` 用原生函数指针替代 `std::function` 是正确的——即使不影响整体 p99，也是零成本抽象原则的体现。5% 的收益在微秒级系统中不是噪声，是真实的。

**【R6 维护性倡导者 | 三个独立的 WS 解析器是定时炸弹】**

论点：现在 transport.hpp 中有三处独立的 WS 帧解析逻辑：
1. `ws::decode_frame()`（完整 RFC 校验）
2. `process_ws_data_filtered` 的 Phase 1 扫描（通过 `ws::decode_frame`）
3. `process_ws_data_twophase_fast` 的快速扫描（手写 2-4 字节头解析）

第 3 处跳过了 RSV 位检查、opcode 合法性检查、控制帧长度校验。如果 Binance 或其他数据源发送了一个 RSV 位非零的帧（表示使用了 WebSocket 扩展），快速路径会静默接受并错误处理，而通用路径会正确拒绝。这不是理论风险——WebSocket permessage-deflate 扩展就设置 RSV1。

**【R14 架构师 | `SymbolHashFn` 是错误的抽象层次】**

论点：`TransportConfig` 现在有两个语义重叠的过滤机制：`on_frame_filter`（通用）和 `symbol_hash_fn`（专用）。它们的优先级是隐式的（代码中 `symbol_hash_fn` 先检查）。如果用户同时设置了两者，行为是什么？`symbol_hash_fn` 静默覆盖 `on_frame_filter`，没有警告。这违反了最小惊讶原则。更根本的问题是：Transport 层不应该知道"symbol hash"这个业务概念。当前设计把交易所特定的去重策略泄漏到了通用传输层。

## 第 2 轮

**【R3 性能狂热者 | 回应 R4 和 R2】**

反驳 R4：「在现有路径中换更快的哈希函数」——不行。`make_twophase_filter` 接收 `std::function<uint32_t(...)>`，即使传入一个快速函数体，`std::function` 的间接调用仍在。而且 `process_ws_data_filtered` 仍会对所有帧做 `ws::decode_frame` + 构建 `FrameIndexEntry`。快速哈希只是优化的一半，另一半是跳过不需要的全量解码。

反驳 R2：分叉是必要的代价。Linux `napi_gro_receive` 和 `netif_receive_skb` 就是两条路径，处理相同的事情但针对不同场景优化。重复 ≠ 坏设计，而是性能和通用性的权衡。

**【R4 实用主义者 | R3 的论点可以实测验证】**

反驳 R3：你说「`std::function` 间接调用 + 全量解码是另一半优化」，但实测数据不支持。v1（快速路径 + FNV 哈希）只比基线好 5%。如果全量解码真是瓶颈，替换它应该有显著改善。实际上瓶颈只在 FNV 的串行乘法链。建议：在 `make_twophase_filter` 中改接受原生函数指针，加一个 `make_twophase_filter(uint32_t(*)(const uint8_t*, size_t))` 重载，测一下是否足够。

**【R14 架构师 | 提出替代方案】**

反驳 R3：fast path / slow path 模式本身没问题，问题是抽象层次错误。不应该把 `SymbolHashFn` 放在 `TransportConfig` 里。替代方案：

1. 给 `make_twophase_filter` 加一个原生函数指针重载，内部实现优化版本，仍走 `on_frame_filter` 接口
2. 或者让 `on_frame_filter` 本身支持类型擦除的"fast filter"概念

这样 Transport 不需要知道 "symbol hash" 是什么，优化封装在 filter 实现内部。

联盟 R6：同意快速路径中的 WS 头解析重复是真实风险。

**【R6 维护性倡导者 | 量化重复风险】**

反驳 R3：Linux 的 fast path / slow path 有成百上千的维护者和完善的测试基础设施。这个项目有几个人？控制帧处理在快速路径中被完整复制（3294-3336 行），与 `dispatch_indexed_frame`（3382-3437 行）逻辑重复。如果 ping 处理需要加一个回调，要改两处。如果忘了一处，bug 只在 `symbol_hash_fn` 被设置时触发——这是最难排查的条件性 bug。

联盟 R14：赞成把优化封装在 filter 内部而非 Transport 层。

**【R2 极简主义者 | 指出最小改动方案】**

反驳 R3：如果 R4 的实测验证通过（给 `make_twophase_filter` 传原生指针就够了），那 200 行快速路径可以全部删除。即使不够，R14 的方案（把优化封装在 filter 内部）也比在 Transport 中加并行路径更干净。

联盟 R4：同意先做最小实验再决定保留多少代码。

## 最终方案

### 核心决策

`SymbolHashFn` 和 `process_ws_data_twophase_fast` 应该删除；优化封装在 filter 层，不泄漏到 Transport。

### 方案细节

1. **删除** `TransportConfig::symbol_hash_fn` 和 `process_ws_data_twophase_fast()`
2. **给 `make_twophase_filter` 加原生函数指针重载**：
   ```cpp
   inline FrameFilterFn make_twophase_filter(
       uint32_t (*extractor)(const uint8_t* data, size_t len));
   ```
   内部实现可以利用原生指针避免 `std::function` 开销
3. **benchmark 中**改为 `.on_frame_filter = make_twophase_filter(binance_symbol_hash)`
4. **验证**：跑 5 轮对比，确认 p99 无退化（预期主要收益来自快速哈希，与路径无关）

### 已解决的分歧

- **"快速路径是否值得"** → 实测只有 5% 收益（噪声范围），不值得 200 行重复代码
- **"优化放在哪一层"** → filter 层，不是 Transport 层。Transport 不应知道 "symbol hash"
- **"控制帧重复怎么办"** → 删除快速路径后自动消除

### 未解决的权衡（需用户决策）

- **filter 内部是否也做快速扫描**：如果将来高流量（>1500 msg/s）下发现通用路径的 per-frame `ws::decode_frame` 仍然是瓶颈，可以在 `process_ws_data_filtered` 内部引入条件优化（对不投递的帧跳过 full decode）。但当前没有实测数据支持这一需求，建议先不做。
