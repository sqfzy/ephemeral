- 用户原始需求：在 ephemeral 框架中实现代理支持。当前 SocketTransport 做裸 TCP 连接，不支持 HTTP/SOCKS5 代理。需要讨论：在哪一层实现代理（SocketTransport 内部？新的 ProxyTransport？TcpFactory lambda 中？）、支持哪些代理协议（SOCKS5/HTTP CONNECT）、如何保持零开销原则（不用代理时无额外开销）、API 设计（配置方式、与现有 TransportConfig/SocketConfig 的集成）。

## 内容摘要
核心争议在于 ProxyTransport 新类型（R14 主张，概念完整、模块隔离）vs TcpFactory + helper 函数（R3/R2/R4 主张，零类型膨胀、利用现有 concept 契约）。R14 在第 3 轮被说服：send()/poll_rx() 是 TcpTransport concept 的公开接口，在 TcpFactory 中做代理握手不违反契约，ProxyTransport 的类型隔离价值不足以抵消复杂度。最终 5/5 一致收敛到：新增 proxy.hpp 提供 ProxyConfig 结构体 + socks5/http_connect 握手 helper 函数 + make_proxied_factory 便利函数。安全硬约束：SOCKS5 使用域名类型防 DNS 泄露，凭证不入日志。

## 讨论全文

### 第 1 轮

**【R14 架构师 | 方案 A：独立 ProxyTransport 层】**
论点：代理是传输层关注点，应新建 `ProxyTransport<TcpImpl>` 适配器满足 TcpTransport concept，在 connect() 中做代理握手，send/poll_rx 透传到内部 TcpImpl。优势：不修改 SocketTransport；concept 边界清晰；可复用于 DPDK。

**【R3 性能狂热者 | 方案 B：TcpFactory lambda 手动实现】**
论点：代理握手只发生一次，不在热路径。在 TcpFactory lambda 中连接代理、做握手、返回 SocketTransport。零新类型、零运行时开销。

**【R2 极简主义者 | 方案 B 变体：helper 函数】**
论点：提供 `socks5_connect()` 和 `http_connect()` helper 函数，用户在 TcpFactory 中调用。不引入新类型。

**【R4 实用主义者 | 方案 C：SocketConfig 加 proxy_url】**
论点：99% 用户想要的是"配个代理地址就行"。在 SocketConfig 加 .proxy_url 字段。

**【R10 安全专家 | 安全约束】**
论点：SOCKS5 必须用远程 DNS（0x03 域名类型）防泄露；凭证不能入日志；代理类型必须显式指定。倾向方案 C（显式配置最安全）。

### 第 2 轮

**【R14 架构师】** 反驳 R3：TcpFactory 中用 send()/poll_rx() 是未记录行为。反驳 R4：proxy_url 破坏 SocketTransport 单一职责。

**【R3 性能狂热者】** 反驳 R14：send()/poll_rx() 是 concept 公开契约，不是未记录行为。ProxyTransport 改变 Transport 类型签名。

**【R2 极简主义者】** 反驳 R14：ProxyTransport 的所有热路径方法都是 trivial 委托，为 50 行握手逻辑创建新模板类不值得。

**【R4 实用主义者】** 立场修正：接受不在 SocketConfig 内置。提出 factory builder：`make_socks5_factory(sock_cfg, proxy_cfg)` 返回标准 TcpFactory。

**【R10 安全专家】** 联盟 R4：factory builder 可内部处理 DNS 泄露防护。要求 ProxyConfig 的 password 字段脱敏。

### 第 3 轮

**【R14 架构师】** 立场修正：放弃 ProxyTransport。接受 TcpFactory + helper + factory builder。指出 SocketConfig.host 在代理场景下指向代理服务器的语义需文档化。

**【R3 性能狂热者】** 确认 host 语义分层是正确设计。SOCKS5 握手 2-3 RTT vs HTTP CONNECT 1 RTT。

**【R2/R4/R10】** 无新论点，同意收敛方案。

### 第 4 轮 — 全体无新论点，终止。

## 最终方案

### 核心决策
在 TcpFactory 层实现代理——提供 SOCKS5/HTTP CONNECT 握手 helper 函数 + factory builder，不引入新类型或 concept。

### 新增文件：`eph-net/include/eph/net/proxy.hpp`

```cpp
namespace eph::net::proxy {

enum class ProxyType { kSocks5, kHttpConnect };

struct ProxyConfig {
    std::string host;
    uint16_t    port = 1080;
    ProxyType   type = ProxyType::kSocks5;
    std::string username{};
    std::string password{};  // Never logged
    std::chrono::milliseconds timeout{5000};
};

std::expected<void, std::string>
socks5_handshake(SocketTransport& tcp, std::string_view target_host,
                 uint16_t target_port, const ProxyConfig& proxy);

std::expected<void, std::string>
http_connect_handshake(SocketTransport& tcp, std::string_view target_host,
                       uint16_t target_port, const ProxyConfig& proxy);

std::function<std::expected<std::unique_ptr<SocketTransport>, std::string>()>
make_proxied_factory(const std::string& target_host, uint16_t target_port,
                     const SocketConfig& base_sock_cfg,
                     const ProxyConfig& proxy);
} // namespace eph::net::proxy
```

### 安全硬约束
1. SOCKS5 使用域名类型（0x03）做远程 DNS 解析
2. ProxyConfig.password 不出现在任何日志/dump()/format()
3. 代理类型显式指定，不做端口推断

### 未解决权衡
- SOCKS5 vs HTTP CONNECT 默认值（取决于用户代理环境）
- 代理链支持（当前不支持，可通过手动 TcpFactory 串联）
