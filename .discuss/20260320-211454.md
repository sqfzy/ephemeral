## 内容摘要
核心争议在于 ARP 协议应该放在协议栈的哪一层。所有角色在第 1 轮即达成共识：ARP 是 L2/L3 边界协议，不属于 eph-net（L4-L7 协议层库）。后续讨论聚焦于是否需要在 eph-dpdk 中实现以及实现范围。R2（极简主义者）最初认为静态 MAC 配置已够用，但被 R12（系统思维者）和 R4（实用主义者）说服——DPDK bypass 了内核协议栈意味着没有系统 ARP 缓存可用，提供一个正确的 helper 比让用户自己写更好。最终 5/5 支持在 eph-dpdk 中添加无状态的 `arp::resolve()` 函数。

## 讨论过程

### 第 1 轮：核心论点

**【R5 第一性原理者 | ARP 不属于 eph-net】**
论点：从 OSI 模型和协议栈分层看，ARP 是 L2/L3 边界协议。eph-net 的定位是 L4-L7 协议层（TCP concept、TLS、WebSocket、HTTP），通过 TcpTransport concept 抽象了底层传输。ARP 属于链路层实现细节，应在 eph-dpdk 中处理。

**【R2 极简主义者 | 不需要 ARP】**
论点：当前通过 TcpConfig 静态配置 MAC 地址。目标场景（数据中心低延迟 WebSocket）中网关 MAC 是已知的，无需 ARP。引入 ARP 意味着广播帧、缓存管理、超时刷新等不必要的复杂性。

**【R12 系统思维者 | 不放 eph-net，可以考虑放 eph-dpdk】**
论点：DPDK bypass 内核意味着用户没有系统 ARP 缓存。ARP 实现依赖 rte_eth_tx/rx_burst，是 DPDK 特有功能。建议在 eph-dpdk 中添加独立的 arp.hpp。

**【R3 性能狂热者 | ARP 影响首次连接延迟】**
论点：首次连接时 ARP 增加 1-2 RTT（数据中心 < 1ms），缓存命中后零开销。关键约束：不能在热路径上做 ARP。

**【R4 实用主义者 | 用户确实需要 MAC 解析能力】**
论点：当前用户体验需要手动查 `ip neigh` 或写脚本获取 MAC。提供 `resolve_gateway_mac()` 即可，不需要完整 ARP 协议栈。

### 第 2 轮：反驳

**R5** 反驳 R4：resolve_gateway_mac 依赖以太网接口，不可能放 eph-net。联盟 R12。
**R2** 反驳 R3/R4：配置文件写死或启动脚本 `ip neigh` 已够用，不值得为省一行脚本引入协议实现。
**R12** 反驳 R2：网关 failover 导致 MAC 变更时静态配置会失败。联盟 R5 放 eph-dpdk。
**R3** 反驳 R2：用户自己实现的 ARP 会更糟糕（不处理超时、不重试）。联盟 R12。
**R4** 反驳 R5：resolve_gateway_mac 本就是针对 eph-dpdk 的提议。反驳 R2：启动脚本是 workaround 不是 solution。

### 第 3 轮：聚焦方案细节

各角色就 eph-dpdk 中的接口达成一致：
```cpp
namespace eph::dpdk::arp {
std::expected<rte_ether_addr, std::string>
resolve(uint16_t port_id, const rte_ether_addr& src_mac,
        uint32_t src_ip, uint32_t target_ip,
        std::chrono::milliseconds timeout = std::chrono::milliseconds{1000});
}
```
约束：无状态、无缓存、无后台线程、连接前一次性调用。

### 第 4 轮：最终立场

- **R5**：ARP 不放 eph-net（坚持）。eph-dpdk 中的 resolve() 合理。
- **R2**：从"不需要"改为"可以有但极简"（被 R12/R4 说服）。不超过 ~100 行。
- **R12**：放 eph-dpdk/arp.hpp。需要集成测试。
- **R3**：支持。不能阻塞超过 timeout。
- **R4**：改善用户体验。建议在 TcpConfig 文档中注明 arp::resolve() 可用。

## 最终方案

### 核心决策
ARP 不应放在 eph-net 中，应放在 eph-dpdk 中作为无状态辅助函数。

### 方案细节
1. 新文件：eph-dpdk/include/eph/dpdk/arp.hpp
2. 接口：arp::resolve(port_id, src_mac, src_ip, target_ip, timeout)
3. 实现：构造 ARP 请求广播帧，轮询 ARP 应答，匹配 target_ip 返回 MAC
4. 不实现：ARP 缓存、老化、Gratuitous ARP、代理、后台线程

### 已解决的分歧
- ARP 放哪？→ eph-dpdk（5/5 共识）
- 是否需要？→ 需要，极简实现（R2 被说服）
- 实现范围 → 无状态一次性查询（5/5 共识）
