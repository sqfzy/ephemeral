## 内容摘要
对 ephemeral 项目的整体架构进行了多角度评审。核心争议集中在五个方面：TLS seq 溢出与 Key Update 策略、零拷贝 vs 统一抽象的取舍、API 回调入口过多（8 种）、record.hpp/transport.hpp 的拆分必要性、以及 ISN 降级路径的安全风险。安全问题在第 3 轮达成共识（必须添加 seq 溢出检查、删除 ISN 降级路径）；零拷贝在第 5 轮被放弃（额外 memcpy ~5ns 相对 TLS seal ~150ns 可忽略）；文件拆分在第 6 轮达成共识。最终结论：架构设计优秀，需修复 3 项安全/正确性问题、4 项维护性改进、4 项 API 优化，不需要架构级重构。

## 第 1 轮：初步立场

### 【性能狂热者 R3 | 设计基本合格但仍有优化空间】

论点：整体架构方向正确——DPDK 绕过内核、AEAD 单次调用绕过 SSL_write、MaskKeyCache 批量预生成、SPSC 队列 cache line 对齐。但几个地方还有明显延迟浪费：

1. `Transport::send()` 路径中，`TxMessage` 使用 `std::array<uint8_t, MaxPayload>` 做 memcpy 拷贝进队列，然后 TX 线程又做一次 WS encode + TLS seal。理想路径是零拷贝：应用直接写入最终 mbuf 的 payload 位置，省掉队列中的中间拷贝。
2. `TlsHotState` 虽然做了双 cache line 分离，但 `seq` 字段（8 字节）是每包递增的热计数器——它和 key/iv 放在同一结构体中。频繁写 seq 会导致同 cache line 的 key/iv 被无效化，而 key/iv 每次 seal/open 都要读。应将 seq 单独隔离。
3. `SocketTransport::connect()` 中使用 `std::async` + `wait_for` 做 DNS 超时——这会创建线程。对于建连路径可以接受，但如果重连频繁，线程创建开销会积累。

### 【维护性倡导者 R6 | 设计优雅但维护负担重】

论点：项目最大的维护风险来自三个方面：

1. Header-only 的全局传染性：任何内部修改都会导致所有依赖者全量重编译。`transport.hpp` 引入了几乎所有 net/* 头文件，一个 spdlog 格式字符串的修改就触发全量重建。
2. `record.hpp` 过于庞大（~1200 行）：HdrHistogram、Recorder、ConcurrentRecorder、SystemStats 都在一个文件中。ConcurrentRecorder 的 thread_local + shared_ptr 生命周期管理相当微妙。
3. 平台条件编译散布各处：没有统一的平台抽象层，每加一个新平台就要改多个文件。

### 【极简主义者 R2 | 抽象层次偏多】

论点：

1. `TcpTransport` concept 是否必要？只有两个实现者，从不在运行时切换。
2. `BoundedQueueBytes` / `EvictingQueueBytes` 是对底层队列的薄包装，90% 方法直接转发。
3. `ConnectResult` 暴露了过多中间产物。

### 【风险卫士 R1 | 关键路径上的故障模式未充分处理】

论点：

1. DPDK TCP 无重传——af_packet 模式下丢包率远高于硬件 PMD，可能频繁触发重连。
2. TLS 密钥材料生命周期——TLS 1.3 规范要求 2^24.5 记录后 Key Update，当前未实现。
3. 乱序缓冲区 8 slot 可能不足（多队列 NIC + 非对称路由下）。

### 【安全专家 R10 | 自定义 TLS 数据面引入微妙风险】

论点：

1. Nonce 唯一性依赖 seq 正确性——任何导致 seq 重复的代码路径会破坏 AES-GCM 安全性。
2. ISN 生成的降级路径（time ^ address）熵极低，TCP 连接可被劫持。
3. `extra_headers` 在 `to_json()` 中是否做了 JSON 转义需确认。

## 第 2 轮：交叉反驳

### 【性能狂热者 R3】
- 反驳 R6：30 个头文件规模下 header-only 是正确取舍，用 PCH/ccache 缓解编译时间
- 反驳 R2：concept 是零开销编译期文档，删掉反而降低 API 自描述性
- 反驳 R1：乱序缓冲区 8 slot 已留 4x 余量，RSS 冲突是配置错误

### 【维护性倡导者 R6】
- 反驳 R3：spdlog 自己都弃用了 header-only 模式；transport.hpp 的传递依赖才是真问题
- 反驳 R2：BoundedQueueBytes 的长度校验在 Release 下仍然生效，是唯一可靠防线
- 联盟 R1：record.hpp 应该拆分

### 【极简主义者 R2】
- 反驳 R6：DataWrap 构造时 assert 就够——但接受 Release 下 assert 被关闭的论点
- 反驳 R3：concept 可以，但 TcpFactory 的 std::function 类型擦除与零开销矛盾
- 反驳 R10：ISN 降级直接删掉，不要修复

### 【风险卫士 R1】
- 反驳 R3：RSS 行为会因固件/DPDK 版本更新而改变，reorder buffer 溢出应触发告警
- 反驳 R2：ConnectResult 的 Platform 暴露有实际用途（多连接复用 NIC 端口）
- 联盟 R10：Key Update 缺失 + seq 无上限检查 = 长连接定时炸弹

### 【安全专家 R10】
- 反驳 R2：ISN 只用 4 字节随机数，快速重连下有生日攻击碰撞风险
- 反驳 R3：seq 没有溢出保护，达到 TLS 1.3 协议限制后继续加密是安全未定义行为
- 联盟 R1：Key Update + seq 检查应一起修复

## 最终方案

### 核心决策
架构设计优秀，需修复少量安全缺陷和 API 一致性问题，不需要架构级重构。

### 方案细节

**必修项（安全 / 正确性）**：
1. seal_record()/open_record() 添加 seq ≥ 2^24.5 溢出检查，到达限制时触发主动重连
2. 删除 TcpSession::generate_isn() 的时间+地址降级路径
3. 文档化 send() 的 best-effort 语义

**强烈建议（维护性 / 一致性）**：
4. 拆分 record.hpp → hdr_histogram.hpp + recorder.hpp + system_stats.hpp
5. 拆分 transport.hpp → transport.hpp + transport_pipeline.hpp + transport_handshake.hpp
6. 统一 recv 回调签名：uint16_t len → size_t len
7. TlsHotState 中将 seq 从 key/iv 的 cache line 中分离

**值得做（API 优化）**：
8. 提供 send_text_unchecked() 跳过 UTF-8 校验
9. 统一回调模式：recv() 轮询为主，on_message 等降级为可选钩子
10. connector::connect() 增加接受已有 Platform 实例的重载
11. reorder buffer 大小从硬编码 8 改为模板参数

### 已解决的分歧
- 零拷贝旁路 → 不做（额外 memcpy ~5ns 可忽略）
- Key Update vs seq 限制重连 → seq 限制重连（复杂度远低于 in-band rekeying）
- TcpTransport concept → 保留（零开销 + 文档价值）
- BoundedQueueBytes → 保留（Release 下的安全防护）
- QueueDepth 运行时化 → 保持编译期（纳秒路径上有差异）
- ISN 随机性 → 纯随机可接受（TLS 保护下无攻击面）

### 未解决的权衡（需用户决策）
- 回调模式统一：削减到 3-4 个 vs 保留 8 种入口
- ConnectResult 简化：增加 connect(platform, config) 重载 vs 保留当前设计
