## 第 1 轮：各角色独立提出核心论点

### 【R1 风险卫士 | 防御性设计优先】

1. **TLS key rekeying 缺失**：TLS 1.3 要求 ~2^24 记录后更换密钥，当前无阈值检测，长连接下有 nonce 复用风险。
2. **reconnect 竞态**：RX 线程通过 flag 协调 TX 自旋，但 TX 可能已在 `crypto_->encrypt()` 内部，产生 UAF。
3. **reorder buffer 硬编码**：`kReorderSlots=8` 不可配置，`drain_reorder_buf` 是 O(n²)。
4. **WebSocket 缺少 continuation frame 重组**。

### 【R3 性能狂热者 | 延迟为王】

1. **TX 逐包 `tcp_->send()`**：应批量 `rte_eth_tx_burst` 减少 PCIe doorbell。
2. **RX reassembly 用 memmove**：应改为 ring buffer。
3. **masked_copy 无 SIMD**：AVX2 可减 60% 指令数。
4. **两次内存拷贝**（app→SPSC→ws_buf），应考虑就地编码。
5. **BoundedQueue 无退避策略**。

### 【R6 维护性倡导者 | 三年后的可读性】

1. **transport.hpp 995 行**，应按职责拆分。
2. **错误类型用 `std::string`**，导致字符串比较判错误类型。
3. **日志器模式重复**（5+ 处几乎相同代码）。
4. **注释语言不统一**（containers 中文，net/dpdk 英文）。
5. **WS opcode 缺乏类型安全**。

### 【R8 激进创新者 | 打破天花板】

1. **应提供 io_uring TcpTransport 后端**降低部署门槛。
2. **支持 WebSocket 压缩扩展**。
3. **支持多连接多路复用**。
4. **零拷贝 TX via mbuf 直接暴露**。
5. **内置延迟测量基础设施**。

### 【R2 极简主义者 | 反对一切不必要的复杂性】

1. **当前范围恰到好处**，不要功能膨胀。
2. **TransportConfig 已 15 字段**，应减少而非增加。
3. **FrameTemplate 抽象太薄**，无性能收益。
4. **不需要进一步拆分 transport.hpp**。

## 最终方案

### 核心决策
优先修复安全/正确性缺陷，再做性能优化和架构清理，新功能后置。

### 方案细节

**P0（必须修复的 bug/安全问题）：**
1. **TLS Key Update 支持**：`TlsRecordCrypto` 中加入序列号阈值检测，触发 rekey 流程
2. **Reconnect 竞态修复**：join TX thread → reconnect → restart TX thread
3. **密钥材料清零**：析构中 `OPENSSL_cleanse(write_iv_, read_iv_)`
4. **`TlsSession` 析构安全**：检查 TCP 状态再调 `SSL_shutdown`
5. **WS continuation frame 重组**
6. **WS 跨 TLS record 重组**

**P1（高价值改进）：**
7. **错误类型枚举化**：`TransportError` 枚举替代 `std::expected<T, std::string>`
8. **TX 批量发送**：单次 `rte_eth_tx_burst(mbufs[], n)`
9. **日志器工厂函数**：提取 `eph::detail::make_logger(name)`
10. **运行时 MSS 校验**

**P2（规划级）：**
11. 批量 recv API
12. 延迟测量基础设施
13. io_uring 后端
14. FrameTemplate 预计算优化
15. 注释语言统一

### 已解决的分歧
- scatter-gather vs 独立 mbuf 批量 → 独立 mbuf（PMD 兼容）
- 编译期 vs 运行时 MSS 校验 → 运行时
- SIMD masking → 撤回（ROI 不足）
- transport.hpp 拆分 → 降级（995 行可接受）
- push 回调模型 → 撤回（破坏解耦）
- TX 双优先级队列 → 撤回（pong 频率太低）

### 未解决的权衡（需用户决策）
- **TLS rekey 阈值**：2^23（保守）vs 更高值（减少 rekey 频率）
- **io_uring 后端时机**：有非 DPDK 用户需求则提前，否则后置
- **Transport 模块化**：计划扩展则拆分，否则维持现状
