## 内容摘要
围绕 aarch64 (Graviton c8g.xlarge) 首次部署中暴露的 8 个问题展开讨论。核心争议在于：性能优化（-march=corei7）与跨平台可维护性如何共存、AEAD buffer overflow 的严重性评估、以及部署流程应该用 Dockerfile 还是文档固化。最终收敛为分层行动计划：立即执行加密 API 注释规范，短期建立 aarch64 CI + per-arch 编译 rule，按需编写部署文档，长期考虑 TLS fuzzing。共识：**建立 aarch64 CI 管线是最高优先级的治本措施**。

## 第 1 轮：各角色独立提出核心论点

**【性能狂热者 R3 | 性能不可妥协】**
论点：问题不是"x86 假设太多"，而是缺乏按架构分层的优化路径。`-march=corei7` 本身没错，错的是没有 aarch64 对应的 `-march=neoverse-v2`。正确做法是每个架构都有专属的最优编译参数。

**【维护性倡导者 R6 | 消除平台假设是技术债】**
论点：8 个坑中有 4 个直接源于代码中的隐式平台假设。这是系统性设计缺陷。所有平台特定代码必须有编译期守卫，没有 aarch64 CI 就没有防护网。

**【风险卫士 R1 | 错误路径是安全盲区】**
论点：坑 4（AEAD max_out_len buffer overflow）最严重——只在解密失败路径上触发。所有涉及 `*_len` 参数的加密调用，必须在调用点注释清楚语义。

**【实用主义者 R4 | 聚焦可复现的生产路径】**
论点：最有价值的产出是证明了 ephemeral 栈在 Graviton 上端到端可用。真正影响生产的只有坑 2（编译失败）和坑 3（运行时崩溃），优先修复这些。

**【系统思维者 R12 | 缺的是部署管线，不是代码修复】**
论点：根本问题是没有跨平台 CI 管线和标准化部署流程。需要 aarch64 CI runner、环境固化方案、和可测试的部署 playbook。

## 第 2 轮：交叉反驳

- R3 反驳 R6：`-march=corei7` 不是假设是优化决策，`-march=native` 在 CI 不可复现
- R3 反驳 R4：buffer overflow 在网络栈中面对不可信输入，不能说"不会被用户触发"
- R6 反驳 R3：per-arch 显式指定正确，但没有 CI 守卫再好的规范也是空话
- R6 反驳 R4：坑 1 同样阻塞编译，实用主义不能成为忽略安全隐患的借口
- R1 反驳 R4：攻击者恰恰会构造触发解密失败路径的 record，CI 还应跑 fuzzer
- R1 联盟 R6：CI 必需，但应加 fuzzer
- R4 反驳 R1：客户端栈连接已知服务器，fuzzer 基础设施过度；反驳 R12：Dockerfile 过度工程
- R12 反驳 R4：8 个坑的排查成本 > 一次 Dockerfile；反驳 R3：per-arch 逻辑应固化为 xmake rule

## 最终方案

### 核心决策
这次部署暴露了系统性的 x86 平台假设和缺失的跨平台验证管线，修复个别 bug 是治标，建立 aarch64 CI 和编码规范是治本。

### 方案细节（分层行动）

**立即执行（零成本）：**
- 加密 API 调用点注释规范：所有 `*_len` 参数标注语义（plaintext/ciphertext/with_tag）
- xmake.lua 的 `-march` 已加 `is_arch` 守卫（已修）
- cpu.hpp ARM fallback（已修）

**短期执行（低成本）：**
- GitHub Actions 加 aarch64 matrix job，跑非 DPDK 测试
- 提取 `rule("arch.optimize")` xmake 规则，per-arch 管理编译参数
- 修复 transport stop() 的 TLS->TCP 关闭顺序

**按需执行（中成本）：**
- 编写 `docs/deploy-graviton.md` 部署指南
- 改进 `run_ws_echo.sh`：动态检测 `uname -m`

**长期考虑：**
- TLS 解析层 fuzzing
- 容器化部署环境

### 已解决的分歧
- `-march` 优化 vs 跨平台 -> per-arch rule 两者兼得
- Dockerfile vs 文档 -> 文档先行，容器化按需
- Fuzzer 优先级 -> 当前客户端场景后置
- 坑 4 严重性 -> 即使客户端也面对不可信输入，必须修

### 未解决的权衡（需用户决策）
- CI runner 成本：GitHub Actions arm64 runner 是否可用/可接受？
- 部署常态化：是否将"新平台部署后产出 retro"作为团队流程？
