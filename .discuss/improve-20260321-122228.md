### 坑与教训

#### 坑 1：hugepage allocate/deallocate size 不匹配

**背景**：审查 hugepage.hpp 时发现 `allocate` 内部做了对齐 padding（`actual_size`），但外部只传了 `sizeof(T)` 给 `deallocate`
**现象**：Linux munmap 需要精确的 mapped size，传入过小的 size 会导致部分页面未释放
**根因**：`allocate` 的 API 设计未暴露实际分配大小
**教训**：内存分配器若内部修改了请求大小，必须将实际大小传回给调用者
**代码位置**：`eph-utils/include/eph/utils/hugepage.hpp:103`

### 心得与洞察

#### 心得 1：编译期消除使"热路径开销"成伪命题

**发现场景**：讨论 logger 返回 shared_ptr 的开销时
**核心洞察**：`SPDLOG_ACTIVE_LEVEL` 在 Release 模式下将 TRACE/DEBUG 宏展开为空，logger 函数根本不会被调用。看似存在的运行时开销实际被编译器完全消除。
**应用条件**：评估 spdlog 宏包裹的代码开销时，先确认 `SPDLOG_ACTIVE_LEVEL` 的编译配置

### 关键决策

#### 决策 1：allocate API 破坏性变更 vs 保持兼容

**选项**：A) 给 allocate 加输出参数 vs B) 内部存储映射表
**选择**：A
**原因**：allocate 是底层 API，调用点只有 `make()` 和测试。加参数简单直接，映射表引入不必要的复杂性和锁。
**现在回看**：正确。测试更新也顺利。

#### 决策 2：不修改 logger shared_ptr 返回和 set_level

**选项**：A) 改为裸指针 + 移除 set_level vs B) 保持原样
**选择**：B
**原因**：编译期消除使运行时开销不存在；set_level(trace) 在 Debug 模式下有用
**现在回看**：正确。避免了无意义的改动。
