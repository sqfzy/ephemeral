## 内容摘要
核心争议在于：为只有一个后端（DPDK）的项目做 TCP 抽象是否值得。R2（极简主义者）以 YAGNI 原则反对，但被 R6（维护性倡导者）的可测试性论点说服——tls_session.hpp 的 BIO 层直接调用 `rte_eth_rx_burst` 导致 TLS 握手逻辑无法在无 DPDK 硬件的 CI 环境中测试。R3（性能狂热者）证明了 C++20 concepts + templates 的编译时多态在 header-only 代码库中可以实现真正的零运行时开销（单态化后机器码与现在相同）。R5（第一性原理者）纠正了用户的依赖方向思路：应该是 eph-net 定义 concept、eph-dpdk 实现，而非反过来。最终 5/5 角色支持分离。

---

## 讨论过程

### 第 1 轮：核心论点

**【R3 性能狂热者 | 技术上可行但需精确约束】**
论点：C++ concepts + templates 确实能做到零开销抽象。

1. **TX 路径**：`tcp_->send(data, len)` 内部调用 `pkt_template_.build_packet()` + `rte_eth_tx_burst()`。定义为 concept 后 `Transport<DpdkTcp>` 实例化时编译器完全内联，生成相同机器码。
2. **RX 路径有问题**：transport.hpp 直接调用 `rte_eth_rx_burst` 获取 `rte_mbuf*` 数组传给 `tcp_->process_rx(mbufs, n, callback)`。`rte_mbuf*` 不能出现在通用 concept 中。
3. **解法**：将 `rte_eth_rx_burst + process_rx` 合并为 `poll_rx(callback)` 方法封装在 TCP 实现内部。

结论：必须用 concept + templates，不能用虚函数（间接调用 ~5ns + 阻止内联）。

**【R2 极简主义者 | 反对，过度设计】**
论点：当前只有一个后端（DPDK），且短期内不会有第二个。YAGNI。websocket/http/tls_record 已不依赖 DPDK，不需要拆库也能复用。增加模板参数降低编译错误可读性。

**【R5 第一性原理者 | 质疑前提】**
论点：
1. "零性能损失"需定义标准——机器码 identical 可做到，但运行时统计需实测
2. 用户真正需求是什么？支持 io_uring？还是非 DPDK 环境测试？
3. 用户说的依赖方向（eph-net → eph-dpdk）是反的，正确方向是 eph-net 定义 concept，eph-dpdk 实现

**【R6 维护性倡导者 | 强烈支持分离】**
论点：
1. 可测试性是最大收益——tls_session.hpp BIO 层直接调用 `rte_eth_rx_burst` 导致无法在无 NIC 环境测试 TLS 握手
2. TLS 模块不该知道 DPDK mbuf 的存在
3. Header-only + template 天然适合这种分离

**【R12 系统思维者 | 支持但需注意依赖方向】**
论点：
1. 依赖方向：eph-net 定义 concept → eph-dpdk 满足
2. eph-net 不应 `add_packages("dpdk")`
3. Transport 多模板参数问题用 type alias 缓解

---

### 第 2 轮：反驳

**【R3 性能狂热者】**
反驳 [R2]：YAGNI 成立仅当抽象引入运行时开销。C++ concepts 的抽象在编译时完全消除。额外成本仅编译时间。
反驳 [R5]：header-only 方法 + concept 不引入间接层时，IPRA 和内联决策不变。可 `objdump -d` 对比验证。

**【R2 极简主义者】**
反驳 [R6]：可测试性有道理，但真正需要 DPDK 的只有 tcp 和 transport 集成测试——mock TCP 反而不可靠。
反驳 [R12]：编译错误时会暴露全部模板参数，可读性差。

**【R5 第一性原理者】**
反驳 [R3]：当前 `rte_eth_rx_burst` 直接写在 transport.hpp 中，移到 `poll_rx` 改变代码物理位置。虽然内联后结果应相同，建议用 `[[gnu::always_inline]]` 兜底。
联盟 [R12]：依赖方向必须纠正。

**【R6 维护性倡导者】**
反驳 [R2]：不是 mock，是 `LoopbackTcpSession`（内存中收发）——测 TLS 握手流程，不是测集成。BIO 直接调用 DPDK rx_burst 导致无法在没有 NIC 的环境下隔离测试握手逻辑。
联盟 [R3]：同意 concepts + templates，不要虚函数。

**【R12 系统思维者】**
反驳 [R2]：C++20 concepts 的诊断远好于 SFINAE。项目已在使用 concepts（`std::invocable`），团队不陌生。

### 第 3 轮：聚焦 RX 路径抽象

**【R3 性能狂热者 | RX 路径方案】**
concept 中不能出现 `rte_mbuf`，需要 `poll_rx` 方法封装 `rte_eth_rx_burst + process_rx`：
```cpp
template <typename T>
concept TcpTransport = requires(T& t) {
    { t.poll_rx(std::declval<std::invocable<const uint8_t*, uint16_t> auto>()) }
        -> std::same_as<std::expected<uint16_t, std::string>>;
};
```
DPDK 实现的 `poll_rx` 内联后与现在代码相同。

**【R2 极简主义者 | 承认部分合理】**
立场微调：承认 TLS BIO 直接调用 rx_burst 是耦合问题。但提出折中——只抽象 TCP I/O 接口，不需新建独立库。

**【R5 第一性原理者 | 验证零拷贝语义】**
当前 `process_rx` callback 接收 mbuf 内部数据指针，callback 结束后 mbuf 被 free。callback 内部本来就拷贝到 reassembly_buf。concept 化后语义不变，不存在额外拷贝。

**【R6 维护性倡导者 | 测试示例】**
```cpp
LoopbackTcpSession client, server;
TlsSession<LoopbackTcpSession> tls(client, ...);
tls.handshake(); // 内存 loopback 完成 TLS 握手
auto keys = tls.extract_hot_state();
```
CI 中 100% 可复现。

**【R12 系统思维者 | 构建系统方案】**

## 最终方案

### 核心决策
可以做到 TCP 层也迁移且零性能损失——使用 C++20 concepts + templates 编译时多态，单态化后生成与当前相同的机器码。

### 方案细节
1. 创建 eph-net 库：websocket、http、tls_record、tls_session（模板化）、transport（模板化）、tcp_concept
2. 依赖方向：eph-net 定义 `TcpTransport` concept → eph-dpdk 的 `DpdkTcpSession` 满足 concept → eph-dpdk 提供 `DpdkTransport` type alias
3. RX 路径：将 `rte_eth_rx_burst + process_rx` 合并为 `DpdkTcpSession::poll_rx(callback)`
4. 零开销保证：header-only + templates + `-O2` → 编译器完全内联，用 `objdump -d` + benchmark 对比验证

### 已解决的分歧
- YAGNI vs 可测试性 → 可测试性胜出（TLS BIO 直接调用 rx_burst 是实际耦合问题）
- API 复杂度 → type alias 解决
- concept 范围 → 最小化，只包含上层实际用到的方法

### 未解决的权衡（需用户决策）
- 是否同步实现 LoopbackTcpSession？实现则可验证 concept 设计正确性 + 提升测试覆盖；不实现则减少工作量。
