## 内容摘要

全面审查 eph-dpdk 当前代码，发现 4 个 bug，其中最严重的是 **TLS 密钥导出根本性错误**：`extract_hot_state()` 使用 `SSL_export_keying_material()` 导出 exporter keys，而非 application traffic keys。这两者从 TLS 1.3 key schedule 的不同分支派生，值完全不同。一旦 TLS handshake 成功（已修复），后续所有数据加解密都会因密钥不匹配而失败。R9 用 RFC 8446 key schedule 路径明确证明了这一点。修复方案采用 keylog callback 捕获真实 traffic secrets，再通过 HKDF-Expand-Label 派生 AES-GCM key/IV。同时修复了 TCP snd_nxt_ 数据竞争（ping/pong 移到 TX 线程）、IP total_length 越界校验缺失、TLS record > MSS 无法发送等问题。

---

## 最终方案

### 核心决策
修复 4 个 bug：密钥导出（CRITICAL）、TCP 数据竞争（HIGH）、IP 校验（MEDIUM）、MSS 分段（MEDIUM）。

### 方案细节

| Bug | 严重性 | 文件 | 修复 |
|-----|--------|------|------|
| 密钥导出用 exporter keys 而非 traffic keys | CRITICAL | tls_session.hpp | keylog callback 捕获 CLIENT/SERVER_TRAFFIC_SECRET_0 → HKDF-Expand-Label 派生 key/iv → 传入 seq offset |
| TCP snd_nxt_ 数据竞争（TX+RX 线程并发调用 tcp_->send） | HIGH | transport.hpp | ping/pong 通过 TX queue 路由，只在 TX 线程调用 tcp_->send() |
| parse_packet 不校验 ip_total ≤ pkt_len（潜在 OOB） | MEDIUM | net_header.hpp | 加 `if (kEtherHeaderLen + ip_total > pkt_len) return {}` |
| TLS record > MSS 无法发送（LargeTransport 完全失效） | MEDIUM | transport.hpp | TX loop 循环拆分为 MSS 大小的 TCP segment |

### 已解决的分歧
- exporter keys vs traffic keys → R9 用 key schedule 路径证明，R10 接受
- WS upgrade 是否要重构 → 保留 SSL_write/SSL_read，跟踪 seq offset

### 未解决的权衡（需用户决策）
- SSL_read 的 record 计数是估算值（每次 SSL_read 返回 >0 算 1 record），极端情况下可能不准确。如果出现 seq 不同步，可考虑改为通过 TlsRecordCrypto 做 WS upgrade（完全绕过 SSL_write/SSL_read）。
