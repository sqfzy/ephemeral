## 坑与教训

### 坑 1：GCC 版本 ABI 不匹配 — 编译用 GCC 14，链接用 GCC 11

**背景**
Amazon Linux 2023 默认 GCC 11，不支持 C++23。安装 GCC 14 后，xmake 正确使用 gcc14-g++ 编译，但链接器仍用系统默认的 ld，链接的是 GCC 11 的 libstdc++。

**现象**
```
undefined reference to `std::__cxx11::basic_string<...>::_M_replace_cold(...)'
```
所有测试都链接失败。

**当时的错误判断**
一开始以为是缺少库，实际是 ABI 不匹配 — `_M_replace_cold` 是 GCC 14 libstdc++ 的新符号。

**根因**
xmake 的 `--cc` 和 `--cxx` 只控制编译器，链接器仍用系统默认。GCC 14 编译出的 .o 文件引用了 GCC 14 libstdc++ 的符号，但链接时找到的是 GCC 11 的 libstdc++。

**解决方式**
`xmake f --ld=gcc14-g++` 显式指定链接器。

**教训**
在非标准工具链环境下，**编译器和链接器必须配套指定**。只设 CC/CXX 而不设 LD 是经典陷阱。

**相关代码位置**
xmake 配置命令

### 坑 2：-march=corei7 硬编码 — x86 指令集参数在 ARM 上非法

**背景**
`xmake.lua` 中 `eph-dpdk` target 无条件添加 `-march=corei7`，这是 x86 专属的指令集目标。

**现象**
```
cc1plus: error: unknown value 'corei7' for '-march'
cc1plus: note: valid arguments are: armv8-a armv8.1-a ...
```

**根因**
原始代码只考虑了 x86 平台，没有做架构守卫。

**解决方式**
```lua
if is_arch("x86_64", "i386") then
    add_cxflags("-march=corei7", { public = true, force = true })
end
```

**教训**
任何平台特定的编译选项（`-march`、`-m`系列、`-msse`等）都必须包裹在架构检测中。header-only 库尤其容易忽略这点，因为编译选项会传播到所有依赖者。

**相关代码位置**
`xmake.lua:65-67`

### 坑 3：CPU 拓扑解析器假设 x86 /proc/cpuinfo 格式

**背景**
`get_cpu_topology()` 解析 `/proc/cpuinfo`，要求同时找到 `physical id`、`core id`、`processor` 三个字段（valid_mask == 7）才记录一个 CPU 条目。

**现象**
```
CPU topology mismatch: parsed 0 CPUs, expected 4
```
在 ARM 上，`/proc/cpuinfo` 只有 `processor` 字段，没有 `physical id` 和 `core id`。

**当时的错误判断**
无 — 错误信息足够明确，一眼能看出 x86/ARM 格式差异。

**根因**
ARM `/proc/cpuinfo` 格式不含 x86 的拓扑字段。解析器用 bitmask 严格要求三个字段都存在。

**解决方式**
引入 `flush_entry()` 闭包，在遇到空行（CPU 条目分隔符）时，只要有 `processor` 字段就生成条目，缺失的 `physical id` 默认 0，`core id` 默认等于 `processor` 编号。

**教训**
`/proc/cpuinfo` 的格式因架构而异，不能假设所有字段都存在。正确做法是**以最少必要字段为基准，其余可选并提供合理默认值**。

**可复用的模式**
解析半结构化系统文件时，始终处理字段缺失的情况。用"空行 = 记录分隔符"模式，而非"收齐所有字段 = 记录完成"模式。

**相关代码位置**
`eph-utils/include/eph/utils/cpu.hpp:123-170`

### 坑 4：TLS AEAD 解密 max_out_len 包含了 auth tag 长度 — 缓冲区溢出

**背景**
`EVP_AEAD_CTX_open()` 的 `max_out_len` 参数应该是**明文最大长度**，但代码传入了 `payload_len`（包含 16 字节 auth tag）。

**现象**
`test_tls_record` 的 `DecryptWithWrongSeqFails` 测试崩溃（segfault，exit code -1）。正常解密路径不触发是因为输出缓冲区恰好足够大，但**解密失败路径**会导致 EVP 内部写越界。

**根因**
测试中 `uint8_t out[48]`，但 `payload_len = 49`（33 字节密文 + 16 字节 tag）。`max_out_len=49 > 48` → 缓冲区溢出。

**解决方式**
```cpp
payload_len - tls_record::kAuthTagLen  // max_out_len (plaintext only)
```

**教训**
AEAD API 的 `max_out_len` 是**输出缓冲区的容量**，必须严格匹配明文大小（不含 tag）。这类 bug 在正常路径上不触发（输出恰好不越界），只在**错误路径**上暴露 — 这正是为什么错误路径的测试如此重要。

**可复用的模式**
所有涉及加密/解密的缓冲区传参，都要画清楚：plaintext size ≠ ciphertext size ≠ ciphertext+tag size。任何 `size` 参数都要明确它对应的是哪个。

**相关代码位置**
`eph-net/include/eph/net/tls_record.hpp:310-311`

### 坑 5：xmake 的 DPDK 包名不是 "dpdk" 而是 "libdpdk"

**背景**
DPDK 手动编译安装后，xmake `add_requires("dpdk", {system=true})` 仍然报 "missing"。

**根因**
DPDK 的 pkg-config 文件名是 `libdpdk.pc`，不是 `dpdk.pc`。xmake 按包名查找 pkg-config。

**解决方式**
```lua
add_requires("libdpdk", { optional = true, system = true })
```

**教训**
系统包的 pkg-config 名称不一定和你期望的一致。`pkg-config --list-all | grep dpdk` 是最快的确认方式。

**相关代码位置**
`xmake.lua:14,64`

### 坑 6：af_packet 模式同机通信 — SYN-ACK 走 loopback

**背景**
尝试用 DPDK af_packet PMD 在 ens34 上发送 TCP SYN 到本机 IP 的 echo server。

**现象**
TCP handshake timeout。tcpdump 在 ens34 上看不到任何来自 DPDK 源 IP 的包。

**根因**
内核知道目标 IP 是本机地址，SYN-ACK 通过 loopback 发送而非物理网卡。af_packet 只能看到物理网卡上的流量，看不到 loopback 流量。

**解决方式**
放弃 af_packet 同机方案，改用 DPDK ENA PMD 直接绑定 ens35，连接外部服务器。

**教训**
**af_packet PMD 不能用于同机回环通信**。内核路由表优先级高于物理网卡，本地 IP 的流量永远走 lo。要测试 DPDK 栈，必须有真正的远端。

### 坑 7：EC2 安全组阻止跨 ENI 通信

**背景**
将 ens35 绑定到 DPDK 后，尝试连接同实例 ens34 上的 echo server（端口 8443）。

**现象**
TCP handshake timeout。ARP 成功（证明 DPDK 收发正常），但 TCP SYN 不到达 ens34。

**根因**
两个 ENI 属于不同安全组（sg-094f... 和 sg-01cb...），安全组未开放端口 8443。没有 AWS CLI 凭证无法修改。

**解决方式**
改为连接外部 `echo.websocket.org:443`（443 端口出站默认放行）。

**教训**
EC2 双 ENI 通信不等于"本机通信" — **每个 ENI 有独立安全组**，流量仍经过 VPC 安全组过滤。在 EC2 上做 DPDK 测试时，确认安全组规则是第一步。

## 心得与洞察

### 心得 1：DPDK ENA PMD 在 EC2 Graviton 上开箱即用

**发现场景**
将 ens35 绑定到 vfio-pci 后，DPDK 立即识别 ENA 设备，ARP 一次成功，TCP 3ms 建连。

**核心洞察**
DPDK 24.11 的 ENA PMD 在 aarch64 + Graviton 3 (c8g) 上完全可用，无需特殊配置。noiommu 模式足够（EC2 虚拟化层已提供隔离）。

**为什么有价值**
证明 ephemeral 网络栈在 ARM 服务器上可生产部署，不限于 x86。

**应用条件**
需要 vfio-pci + noiommu 模式。需要至少两个 ENI（一个给 SSH/管理，一个给 DPDK）。

---

### 心得 2：子代理并行调查 bug 高效

**发现场景**
test_cpu 和 test_tls_record 同时失败，用两个 Explore 子代理并行分析根因。

**核心洞察**
两个独立 bug 的根因分析完全不相关，并行执行总共只花了 ~15 秒，而串行可能需要 30+ 秒。对于多个独立失败，**并行调查 → 串行修复** 是最优流程。

---

### 心得 3：trap cleanup EXIT 是 DPDK 脚本的刚需

**发现场景**
编写一键脚本时，意识到如果脚本中途崩溃或被 Ctrl-C，网卡会停留在 vfio-pci 绑定状态，ens35 消失，可能需要手动恢复。

**核心洞察**
任何操作 DPDK 设备绑定的脚本，都**必须**有 trap-based cleanup。记录原始驱动名、在 EXIT/INT/TERM 时恢复。否则一次意外中断就会导致网卡"丢失"。

**应用条件**
所有涉及 dpdk-devbind.py 的自动化脚本。

## 关键决策记录

### 决策 1：放弃 af_packet，直接使用 ENA PMD

**决策点**
用户要求"ens 模式"运行 example，可选 af_packet（共享网卡）或 ENA PMD（独占网卡）。

**选项对比**
| 方案 | 优点 | 缺点 | 排除原因 |
|------|------|------|----------|
| af_packet | 不需要解绑网卡 | 同机回环不可用；性能差 | 无法完成 TCP handshake |
| ENA PMD（已选）| 真实 DPDK 路径；高性能 | 需要 root + vfio 绑定 | — |

**最终选择**：ENA PMD

**当时的信息状态**
用户明确说"不需要 af_packet 模式，直接 ens 模式"。af_packet 已被证明在同机场景不可用。

**现在回看**
正确的决策。ENA PMD 是 ephemeral 栈的设计目标，af_packet 只是开发便利。

### 决策 2：连接外部 echo.websocket.org 而非本地 echo server

**决策点**
ENA PMD 绑定 ens35 后，需要一个 WSS echo 服务端。本地 echo server 受安全组限制无法连通。

**选项对比**
| 方案 | 优点 | 缺点 | 排除原因 |
|------|------|------|----------|
| 本地 echo server | 延迟低；可控 | 安全组阻塞；无 AWS 凭证修改 | 不可用 |
| echo.websocket.org（已选）| 公网可达；真实场景 | 依赖外部服务 | — |

**最终选择**：echo.websocket.org

**现在回看**
正确。这实际上是更好的验证——证明整个栈（DPDK → TCP → TLS 1.3 → WebSocket）能与真实互联网服务通信。
