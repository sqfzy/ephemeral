## 内容摘要
基于 DPDK WebSocket pipeline 的延迟 benchmark 数据（E2E TX 256B P50 = 2587ns），讨论了全链路优化方案。核心争议集中在：(1) RAND_bytes 替代方案的安全性——R3 提议确定性 PRNG 被 R1 以 RFC 6455 合规性否决，最终达成 CSPRNG 批量预生成共识；(2) 优化范围——R8 提议单 buffer in-place 架构重构被 R2 以 ROI 不足否决，最终采纳分 Sprint 路线图；(3) masking 必要性——R5 提议跳过 masking 被 R1 以 CDN/WAF 合规风险否决。最终方案分两个 Sprint：Sprint 1 实施 6 项低风险高收益优化（P0-P5），目标 E2E TX P50 从 2587ns 降至 ~520ns（5x 提速）；Sprint 2 基于 profiling 结果做 AEAD API 切换和单 buffer 架构等深度优化。

## 结构化讨论

### 第 1 轮：独立方案提出

**【R3 性能狂热者 | 立场：消灭 RAND_bytes，全链路零拷贝】**

论点：数据铁证——WS Encode 占 E2E TX 的 64.5%，而其中 masking 本身只有 88ns（XOR），剩余 ~1581ns 全是 `RAND_bytes()` 的开销。这是一个系统调用级别的密码学安全随机数生成器，用在每帧 4 字节的 masking key 上，荒谬至极。

方案优先级（按收益排序）：
1. 替换 RAND_bytes 为快速 PRNG：用 xoshiro256** 预生成 mask key 表（4KB 表 = 1024 个 key），热路径只需一次 table[idx++ & 1023] 查表，~2ns
2. TCP checksum 硬件卸载：设置 mbuf->ol_flags，让 NIC 硬件计算 TCP checksum，省 ~214ns
3. IP checksum 硬件卸载：同理，再省 ~50ns
4. TLS nonce 预计算：用递增计数器直接 XOR 最后 8 字节，省一次 memcpy

预期收益：WS Encode 从 1669ns → ~100ns，E2E TX 从 2587ns → ~750ns，3.4x 提速。

---

**【R1 风险卫士 | 立场：RAND_bytes 不可替换，checksum 卸载需验证】**

论点：RFC 6455 Section 5.3 明确要求客户端 masking key 必须是"不可预测的"。用 xoshiro256** 这种确定性 PRNG 生成 masking key 存在安全性和合规性风险。

方案：批量预生成——启动时或每秒调用一次 RAND_bytes(buf, 4096)，生成 1024 个 key 缓存，热路径从缓存中顺序消费。既保留密码学安全性，又摊薄调用开销。Checksum 卸载必须先验证 NIC 支持。

---

**【R2 极简主义者 | 立场：只做 RAND_bytes 优化，其他都是过度工程】**

论点：帕累托法则——RAND_bytes 一个点贡献了 64.5% 的延迟。修复这一个点，E2E TX 就能从 2587ns 降到 ~1000ns。其他优化每个只能省几十到几百 ns，但都需要增加代码复杂度。

---

**【R5 第一性原理者 | 立场：质疑 masking 的必要性】**

论点：masking 的目的是防止缓存投毒攻击。在我们的场景下通信双方都不是浏览器，已经在 TLS 之上，没有透明代理。masking 在我们的场景下是安全性为零的纯开销。

---

**【R8 激进创新者 | 立场：架构级重构，消灭所有中间拷贝】**

论点：当前 TX 路径有 3 次 memcpy。激进方案——单 buffer in-place 构建：在 mbuf 中预留 headroom，payload 直接写入 mbuf，in-place masking，AES in-place 加密，向前填充头部。最终只有 1 次 payload 写入 + 1 次 XOR + 1 次 AES。

### 第 2 轮：聚焦 RAND_bytes 替代方案

**【R3】** 反驳 R1：批量预生成的 key 顺序消费，攻击者截获一个 key 就能预测位置，安全性和 xoshiro 没本质区别。接受批量预生成（最简实现）。

**【R1】** 反驳 R3：批量预生成的 key 从 CSPRNG 输出，每个 key 无数学关联。xoshiro 的 256 位状态可从 ~4 个连续输出恢复。方案不变：批量 RAND_bytes 预生成。

**【R2】** 联盟 R1：实现细节支持 R1 的批量预生成，不需要安全性论证文档。

**【R5】** 立场修正：接受 R1 的 CDN/WAF 论点，masking 必须保留。提出 masked_copy 优化——合并 memcpy + XOR 为单次遍历。

**【R8】** 接受分步实现单 buffer 方案。联盟 R5 的 masked_copy 思路。

### 第 3 轮：聚焦 TCP Checksum 优化

**【R3】** checksum 卸载是必做项，5 行代码省 ~284ns。所有主流 NIC 都支持。

**【R1】** 有条件接受：需要 use_hw_checksum 标志 + NIC capability 检测 + fallback。

**【R5】** 软件 checksum 也有优化空间：IP header checksum 可以做增量预计算（模板 checksum + delta 更新）。

**【R2】** 硬件卸载足够，增量 checksum 可读性差，不值得。联盟 R3。

**【R8】** 提出 GSO 合并多个小 TCP segment 的思路。

### 第 4 轮：TLS 加密优化

**【R3】** EVP API 有 ~150ns overhead。优化：避免每次 EVP_EncryptInit_ex、使用 EVP_AEAD_CTX_seal、nonce 用 uint64_t XOR。预期 268ns → ~120ns。

**【R1】** EVP_AEAD 是 BoringSSL 特有 API，稳定性风险。保持 EVP 标准 API，只做 nonce uint64_t XOR。

**【R5】** AES-256-GCM 理论下限 ~119ns。当前 268ns，overhead 149ns。封装 TlsRecordCrypto 可以隔离 API 切换。

**【R8】** 批量加密：N 个 payload 连续处理，利用 AES-NI pipeline。

**【R2】** 只做 nonce 优化（2 行），EVP 切换不做。

### 第 5 轮：WS Encode 重构

**【R3】** 联盟 R5：masked_copy 是第二大收益点。给出具体实现（uint32_t 块处理）。

**【R1】** 接受 masked_copy，要求覆盖 payload size = 1, 3, 4, 7 等边界值的 benchmark。

**【R5】** 提出 AVX2 masked_copy 方案（_mm256_xor_si256）。

**【R2】** SIMD 是过度优化，净省 40ns 只占 E2E TX 1.5%。接受 scalar masked_copy。

**【R8】** 接受先做 scalar masked_copy，后续 profiling 再决定 SIMD。

### 第 6 轮：架构级优化——buffer 消除

**【R8】** 提出具体分步实现：Step 1 消灭 ws_buf，Step 2 在 mbuf 上原地加密。

**【R2】** Step 1 可做（~5 行），Step 2 EVP 原地加密有限制，太激进。

**【R3】** Step 2 可行：EVP 原地加密（output == input）被 OpenSSL/aws-lc 显式支持。TLS header 和 tag 分开写。

**【R1】** 原地加密需验证非 16 字节对齐 payload 的行为。联盟 R2：先做 Step 1，Step 2 做 spike 验证。

**【R5】** Step 2 全部收益仅 ~35ns，ROI 不足以 justify 复杂度。

### 第 7 轮：RX 路径优化

**【R3】** RX P99/P50 = 2.1x，tail latency 来自 TLS decrypt 的间歇性 cache miss。建议 prefetch 下一个包。

**【R2】** RX 绝对值 < 1µs，优先级低于 TX。唯一值得做的：decode_frame 的 binary opcode fast-path。

**【R1】** RX 真正风险是 reassembly_buf（std::vector）的 reallocation 导致 P99 膨胀。建议用固定 ring buffer 替换。

**【R5】** 如果消息 < MSS，不需要 reassembly。可以跳过 reassembly buffer 直接解密解码。

### 第 8 轮：批量处理与 TX loop 重构

**【R8】** TX loop 必须改为批量模式。当前每包独立 tx_burst(1) 浪费 PCIe doorbell。

**【R2】** 简单 drain 循环足够：尽量多取，一次 tx_burst。~30 行代码。联盟 R3。

**【R3】** 联盟 R2：drain 循环 + prefetch。两遍循环让第二遍处理时 payload 已在 L1 cache。

**【R1】** partial send 不能丢弃，必须重试直到全部发送。

### 第 9 轮：优化优先级与实施计划

**【R2】** ROI 排序：P0(RAND_bytes)★★★★★ > P1(masked_copy)★★★★ > P2(checksum offload)★★★★ > P3(nonce)★★★ > P4(drain)★★★ > P5(消灭ws_buf)★★★。建议做 P0-P3。

**【R3】** P4 和 P5 也应做。P4 在高频场景摊薄 PCIe 交互。P5 只需改指针。

**【R5】** 优先级取决于场景假设。P0 做完后先 benchmark，看 P99/P50 比值再决定后续。

**【R1】** P2 需要 NIC 验证 + fallback 代码。

**【R8】** 提出分 Sprint：Sprint 1 做 P0-P5（目标 < 700ns），Sprint 2 做 P6/P7/P9（目标 < 500ns）。

### 第 10 轮：最终立场声明

**【R3】** 接受 CSPRNG 批量预生成（安全+性能兼得）。接受分 Sprint。坚持 P0-P5 是 Sprint 1 最小集。目标 E2E TX P50 < 500ns。

**【R1】** masking 不可跳过。接受 P2 但坚持 fallback。坚持 P0 必须用 CSPRNG。P9 需 spike 验证。

**【R2】** 接受 P4 进 Sprint 1（PCIe 开销论点）。接受 Sprint 路线图。坚持 Sprint 1 不做 AEAD 切换和 AVX2。坚持每个优化项有 benchmark 验证。

**【R5】** masking 必须保留。Sprint 2 值得做 P6（EVP API 有 55% overhead）。坚持 P0 做完后重新 benchmark。RX reassembly（P7）优先级应高于 TX 进一步优化。

**【R8】** 接受分步实施。P9 前需 spike 验证。坚持长期目标 < 500ns。P5 应和 P0 一起做。

## 最终方案

### 核心决策
分两个 Sprint 优化 DPDK WebSocket TX 热路径：Sprint 1 做 6 项低风险高收益改动（P0-P5），目标 E2E TX P50 < 700ns；Sprint 2 基于 profiling 结果做深度优化，目标 < 500ns。

### 方案细节

**Sprint 1（立即实施）**：

| ID | 优化项 | 实现方式 | 预期收益 |
|----|--------|---------|---------|
| P0 | RAND_bytes 批量预生成 | 启动时 RAND_bytes(buf, 4096) 生成 1024 个 mask key，热路径顺序消费 | ~1570ns |
| P1 | masked_copy | 合并 memcpy + XOR 为单次遍历 | ~50ns |
| P2 | TX checksum 硬件卸载 | 检查 tx_offload_capa，支持时设 ol_flags，否则 fallback | ~280ns |
| P3 | nonce uint64_t XOR | build_nonce 中用 uint64_t 直接 XOR | ~15ns |
| P4 | TX drain 循环 | drain 模式批量消费 + tx_burst | ~100ns/包 |
| P5 | 消灭 ws_buf | WS encode 目标地址直接指向 TLS 加密输入区域 | ~50ns |

预期 Sprint 1 结果：E2E TX 256B P50 从 2587ns → ~520ns（5x 提速）

**Sprint 2（Profile 驱动）**：P6(AEAD API), P7(RX ring buffer), P9(单 buffer in-place)

### 已解决的分歧
- RAND_bytes 替代方案 → CSPRNG 批量预生成（R1 安全性 + R3 性能折中）
- masking 是否可跳过 → 不可跳过（R1 的 CDN/WAF 论点说服 R5）
- Checksum 卸载 → 做，但必须有软件 fallback
- AVX2 SIMD masking → 推迟到 Sprint 2 后评估
- 单 buffer 架构 → 分步：Sprint 1 只做 Step 1

### 未解决的权衡（需用户决策）
- P4 partial send 策略：重试 vs 丢弃 → 若对端是交易所订单接口选重试；若是行情推送可丢弃
- Sprint 2 AEAD API：BoringSSL 绑定 vs OpenSSL 兼容 → 若长期绑定 aws-lc 选 AEAD；否则保持 EVP
