## 内容摘要
ephemeral 当前拥有优秀的底层基础设施（SPSC 队列、TSC 计时器、DPDK/socket 双后端传输层、TLS 1.3 + WebSocket、ITCH/FIX 解析器），但距离完整的 HFT 库还缺少关键的应用层组件。主要争议集中在：(1) 应用层（order book、OMS、exchange adapter、风控）的优先级排序；(2) API 设计模型（polling vs callback）；(3) 先设计 concept 还是先实现后抽象。最终达成共识：以加密 HFT 为首要目标市场，分三阶段建设——Phase 1 交付 Binance adapter + order book + 基础 OMS + 风控的最小可用系统，Phase 2 生产级加固，Phase 3 扩展到传统市场。

## 第 1 轮：各角色独立提出核心论点

### 【R3 性能狂热者 | 延迟关键路径存在重大缺口】

论点：
1. **没有 order book 数据结构** — HFT 的核心是 order book。有 ITCH 解析器但没有 order book 管理器，就像有 JSON 解析器但没有数据库。需要一个 cache-friendly 的限价订单簿（price-level aggregation + individual order tracking），基于数组而非 std::map。
2. **缺少 UDP multicast 支持** — 大部分交易所市场数据走 UDP multicast（如 NASDAQ TotalView via MoldUDP64），当前只有 TCP/WebSocket 路径。对于 co-located HFT，这是致命缺陷。
3. **没有零拷贝内存池** — 当前依赖 hugepage + aligned_alloc，但缺少 slab allocator 或 object pool。热路径上的内存分配是延迟杀手。
4. **缺少 lock-free MPSC 队列** — 只有 SPSC。真实系统中多个策略线程需要向同一个发送线程提交订单，MPSC 是必需的。
5. **TCP 重传/拥塞控制缺失** — DPDK TcpSession 不做重传，依赖"检测丢包→重连"。在跨数据中心或偶发丢包场景下，2ms 重连时间可能导致错过交易机会。

### 【R14 架构师 | 模块边界和概念完整性需要加强】

论点：
1. **缺少统一的 "Session" 抽象层** — TLS + WebSocket + Transport 组合逻辑分散在多个层。需要一个 Session 概念将这些封装为单一交互点。
2. **协议层与传输层耦合** — ITCH 和 FIX 的 framer 直接依赖 eph-net，但协议解析应独立于传输。
3. **缺少配置管理体系** — 缺少统一的配置加载、校验、热更新机制。
4. **没有连接管理器** — 多交易所场景下，需要管理数十个并发连接的生命周期。
5. **缺少事件循环/reactor 模型** — 当前 Transport 为每个连接开两个线程（TX/RX），50+ 连接时线程开销巨大。

### 【R1 风险卫士 | 关键安全和可靠性机制缺失】

论点：
1. **没有消息序列号和 gap detection** — 丢消息意味着 order book 不一致。
2. **缺少 graceful degradation 机制** — 没有断路器、降级策略或风控触发机制。
3. **没有状态持久化** — 连接断开后无法恢复之前的 order book 状态。
4. **缺少审计日志和回放能力** — 监管要求完整的消息审计追踪。
5. **DPDK TCP 缺少 RST flood 防护** — 用户态 TCP 暴露更大攻击面。

### 【R4 实用主义者 | 区分理论完美和实际需要】

论点：
1. **WebSocket 作为 HFT 传输层是正确选择** — 加密交易所大量使用 WebSocket。
2. **SPSC 队列已经够用** — 最关键路径是天然的 SPSC 管道。
3. **需要优先补全的是 exchange connector** — 完整的交易所适配器比完美的 order book 更能证明价值。
4. **基准测试需要更多真实场景** — 需要端到端延迟测试。
5. **文档需要从 API reference 升级为 deployment guide**。

### 【HFT 量化开发者 | 开箱即用才是关键】

论点：
1. **没有 order management 层** — 需要 NewOrderSingle、CancelOrder 的抽象。
2. **缺少市场数据标准化层** — 需要标准化的 Quote、Trade、OrderBookUpdate 事件类型。
3. **没有时间同步方案** — 缺少 PTP 或与交易所时间戳对齐的机制。
4. **缺少回测支持** — 策略代码需要能在实盘和回测模式间切换。
5. **没有监控仪表盘** — 缺少导出到 Prometheus/Grafana 的途径。

## 第 2 轮：交叉反驳与深化

### 【R3 性能狂热者】

- 反驳 HFT 量化开发者：应优先做 message journal 而非模拟交易所。

### 【R4 实用主义者】

- 反驳 R14：HFT 关键连接通常 < 10，per-connection 线程可接受。
- 联盟 HFT 量化开发者：exchange connector 是最高优先级。

### 【HFT 量化开发者】

- 反驳 R3：order book 应提供多粒度（BBO、5档、完整）。

## 第 3 轮：Order Book 设计深入

### 【R3 性能狂热者】

## 最终方案

### 核心决策
ephemeral 当前是优秀的低延迟网络传输层 + 容器库，最紧迫的缺失是应用层（order book、OMS、exchange adapter、风控）。以加密 HFT 为首要目标市场，分三阶段完善。

### 方案细节

**Phase 1 — 最小可用 HFT 系统（加密市场优先）：**

前置条件：
- CI pipeline (GitHub Actions) + ASan/UBSan/TSan
- 确立性能基线（所有现有 benchmark 入 CI）

核心功能：
1. simdjson 集成 — JSON 解析/构建
2. HTTP client — REST API（基于现有 SocketTransport 扩展）
3. Binance WebSocket adapter — 参考实现（market data + trading）
4. Price-level Order Book — cache-friendly, < 50ns/update
5. 基础 OMS — order lifecycle tracking, fill management
6. 基本风控 — kill switch + position limit + rate limit + price sanity check (< 20ns)
7. Prometheus text format exporter — 利用现有 HdrHistogram/SystemStats
8. Polling API — `exchange.poll()` 作为底层接口

成功标准：Binance 完整交易流程，tick-to-trade < 5μs。

**Phase 2 — 生产级加固：**
1. Binary message journal (mmap ring buffer, < 100ns/msg)
2. Object Pool + Arena Allocator
3. 完整风控框架（loss limit、异常检测、可插拔规则）
4. Fuzz test (libFuzzer) for all parsers
5. Long-running stability test (nightly)
6. CMake find_package 支持
7. API 文档 (Doxygen) + Getting Started 教程
8. High-level callback API wrapper
9. 第二个交易所 adapter (OKX or Bybit)
10. 标准化事件模型 (Quote, Trade, OrderBookUpdate, Fill)

**Phase 3 — 传统市场扩展 + 高级功能：**
1. UDP Multicast + MoldUDP64
2. SBE codec
3. OUCH 协议
4. io_uring / AF_XDP 后端
5. Order-by-order Book
6. 连接管理器 + 多路复用
7. Exchange concept 体系
8. Market data replay + Mini exchange simulator
9. Shared Memory IPC
10. 编译时可观测性级别

### 已解决的分歧
- **风控时机** → Phase 1 四项基本风控，完整框架 Phase 2
- **API 模型** → polling 先于 callback（更简单、延迟更低）
- **concept 设计时机** → Phase 1 硬编码 Binance，Phase 2 提炼 concept
- **构建系统** → xmake 主 + CMake 辅
- **目标市场** → 加密优先，传统市场 Phase 3

### 未解决的权衡（需用户决策）
- **Order Book 实现策略**：sorted array O(1) vs sorted vector + binary search
  → 若 co-located HFT（百万级/s），选前者；若远程加密 HFT（千级/s），选后者
- **JSON 库选型**：simdjson 共识，需确认许可证兼容性
- **DPDK TCP 重传**：维持检测丢包→重连 vs 添加轻量重传
  → 依部署网络质量决定
