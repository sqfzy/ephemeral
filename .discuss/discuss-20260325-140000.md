# Discussion Record

## Context
- 时间：2026-03-25 14:00:00
- 耗时：约 4 分钟
- 用户原始需求：在 ephemeral 框架中支持 TLS 1.2。当前框架只支持 TLS 1.3（aws-lc/BoringSSL），使用自定义 BIO + 手动 AEAD 热路径（extract keys → TlsRecordCrypto 加解密）。TLS 1.2 的 record layer 和密钥导出机制与 1.3 不同。背景：通过 Clash 代理连接 Binance 时，TLS 1.3 握手被 close_notify 拒绝，只有 TLS 1.2 能通过。
- 复杂度评估：高
- 讨论轮数：5 轮
- 参与角色：R3(性能狂热者)、R10(安全专家)、R4(实用主义者)、R14(架构师)、R2(极简主义者)

## 内容摘要
核心争议经历三个阶段：(1) 是否值得支持 TLS 1.2——R4 的实际用户场景（代理环境无法用 1.3）说服了 R2/R3；(2) 如何支持——R2 提出 SSL_write/SSL_read fallback 被 R3 否决（破坏双线程无锁模型）；(3) 最终收敛到在 TlsRecordCrypto 内部加运行时 version 分支，TLS 1.2 限定 GCM-only 套件，密钥通过 SSL_generate_key_block() 提取。R3 的性能量化分析证实热路径影响为零（差异在纳秒级 nonce/AAD 构造），R10 的 GCM-only 约束确保安全性。用户 API 零变化。

---

## 最终方案

### 核心决策
TlsRecordCrypto 运行时 version 分支支持 TLS 1.3 + TLS 1.2 GCM，对用户 API 完全透明。

### 改动文件
1. `tls_session.hpp` — SSL_CTX 允许 1.2+1.3；extract_hot_state() 按版本选密钥提取方式
2. `tls_record.hpp` — TlsHotState 增加 version 字段；encrypt/decrypt 按版本构造 nonce/AAD
3. 无 Transport/TransportConfig 变化

### TLS 1.2 GCM vs TLS 1.3 Record Format

| 维度 | TLS 1.3 | TLS 1.2 GCM |
|------|---------|-------------|
| IV 长度 | 12B (full) | 4B (implicit) |
| Nonce | IV XOR seq_num | implicit_IV(4B) ‖ explicit_nonce(8B) |
| explicit nonce | 无 | 8B 在密文前 |
| AAD | record header (5B) | seq(8B) ‖ type(1B) ‖ version(2B) ‖ length(2B) |
| Record header type | 固定 0x17 | 真实类型 |

### 安全硬约束
1. SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION)
2. TLS 1.2 cipher list: ECDHE-RSA-AES128-GCM-SHA256 / ECDHE-RSA-AES256-GCM-SHA384 only
3. explicit nonce 使用递增序列号（避免 nonce reuse）
4. 绝不支持 CBC 套件

### 已解决的分歧
- SSL_write fallback vs 手动 AEAD → 手动 AEAD（SSL_write 破坏无锁模型）
- 虚函数 vs bool 分支 → bool 分支（分支预测友好）
- TLS 1.2 密钥提取 → SSL_generate_key_block() 可行
- CBC 支持 → 不支持（安全风险）
