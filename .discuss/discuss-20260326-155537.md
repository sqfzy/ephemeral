## 第 1 轮

**【R5 第一性原理者 | mock 测的是什么？】**

论点：先搞清楚目标。我们要验证的是"高流量下 p99 ≤ 6μs"。高流量的本质是：单条 TLS record 内包含大量 WS 帧。这不是 mock server 发送速率的问题——速率决定的是每秒多少条消息，但 TLS record 打包多少帧取决于 TCP 发送时机和 Nagle 算法。控制的变量应该是"每 TLS record 的帧数"，不是"每秒消息数"。

**【R3 性能狂热者 | 必须走真实 TLS + WS 路径】**

论点：mock server 必须是真正的 TLS WebSocket server。我们测的是完整 RX pipeline（TLS decrypt → WS decode → filter → deliver），任何跳过 TLS 的 mock 都无法验证真实 p99。

**【R4 实用主义者 | 用现有工具最快】**

论点：Python websockets 几十行就能写。但关键问题：mock server 在 kernel 网卡上，benchmark 在 DPDK 网卡上，两者怎么通信？

**【R2 极简主义者 | 最小方案】**

论点：单文件 C++ 程序，复用项目已有的 TLS + WS 库。用 C++ 而非 Python 是因为发送端抖动会影响接收端 batch 分布。

**【R13 测试驱动者 | 可重复性是核心价值】**

论点：参数化的发送速率 + 确定性结束条件，未来可集成到 CI。

## 第 2 轮

**【R5 第一性原理者】**

反驳 R4：Python 的 ssl.SSLSocket.send() 无法控制 TLS record boundary。
反驳 R2：关键是怎么控制 TLS record 打包——需要先拼接多个 WS 帧字节，再一次性 TLS encrypt。

**【R3 性能狂热者 | TLS record 打包方案】**

方案：生成 N 个 WS 帧 → 拼接 → 一次 TLS_encrypt → TCP send = 一条含 N 帧的 TLS record。

## 最终方案

### 核心决策
写一个 C++ mock Binance server，核心控制变量是 `--batch-size`（每 TLS record 打包的 WS 帧数），运行在 kernel 网卡上通过 VPC 路由与 DPDK benchmark 互通。

### 方案细节

架构：
```
[mock_binance_server]          [bench_market_multi_dpdk]
  kernel NIC (ens34)              DPDK NIC (28:00.0)
  172.31.x.x:9443                172.31.23.112
         │                              │
         └──── VPC subnet routing ──────┘
```

命令行：
```
mock_binance_server --port 9443 --symbols btcusdt,ethusdt,solusdt \
    --batch-size 30 --rate 2000 --duration 30
```

关键参数：
- `--batch-size N`：每条 TLS record 打包 N 个 WS 帧（核心控制变量）
- `--rate N`：目标 msg/s（0 = 无限制）
- `--symbols`：symbol 列表
- `--duration`：运行秒数

### 已解决的分歧
- Python vs C++ → C++（需精确控制 TLS record boundary）
- 控制变量 → batch-size（帧/record），不是 rate（msg/s）
- 网络拓扑 → 同机双网卡，VPC 路由互通
- CI 集成 → 延后

### 未解决的权衡
- 复用项目 TLS 库 vs 系统 OpenSSL：建议 mock server 用系统 OpenSSL（SSL_write 天然控制 record boundary），benchmark 客户端不变
