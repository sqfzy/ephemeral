## 内容摘要
讨论围绕 ephemeral 项目在 HFT 场景中的定位和缺失功能展开。核心争议在于 ephemeral 应该做"HFT 传输基础设施层"还是"完整 HFT 框架"——R5 在第 3 轮划定了清晰边界（传输层增强 vs 上层职责），获得全员认可。各角色在 rate limiter（归上层）、FIX 协议（归上层）、kill switch（归传输层）、可插拔分帧器（归传输层）上达成共识。最终产出 9 项分 P0/P1/P2 优先级的增强方案：P0 包括 TLS bypass、进程级 kill switch、硬件时间戳；P1 包括可插拔分帧器、延迟 breakdown、可观测性增强；P2 包括多连接管理器、CPU isolation 检测、shared memory IPC 模块。

## 第 1 轮：初步立场

### 【性能狂热者 R3 | 延迟是唯一王道】
论点：
1. 无 kernel bypass 的订单发送路径——行情 RX 延迟 139ns，但订单可能走内核 TCP
2. 缺少 FIX/ITCH/OUCH 协议支持——WebSocket 只适用于加密货币
3. 没有 zero-allocation 热路径保证——TLS seal 内部可能触发隐式 malloc
4. 缺少硬件时间戳支持——TSC 跨机器不可比

### 【风险卫士 R1 | HFT 故障是灾难级的】
论点：
1. 没有消息速率限制（Knight Capital 事故引鉴）
2. 没有心跳超时的快速 kill switch
3. 缺少序列号/去重机制
4. 没有 position/exposure 跟踪层

### 【第一性原理者 R5 | ephemeral 应该是什么？】
论点：
1. ephemeral 是低延迟传输库，不是 HFT 框架
2. 变成 HFT 框架意味着加入 OMS、风控、策略——完全不同的项目
3. 正确的问题是"作为 HFT 基础设施层，还缺什么"
4. 传输层合理扩展：硬件时间戳、多连接、协议无关传输

### 【系统思维者 R12 | 要看完整的交易链路】
论点：
1. 上行/下行不对称性——TX 单消息延迟是关键
2. 缺少连接管理器——多 venue、primary/backup
3. 跨组件时钟同步——端到端时间戳链路
4. 配置热更新——交易时段内不能重启

### 【HFT 实战者 | 从部署痛点出发】
论点：
1. 没有协议无关的消息边界抽象
2. 缺少 shared memory 传输后端
3. 没有 CPU isolation 集成
4. 日志路径在热路径上——即使被过滤也有参数评估开销

## 最终方案

### 核心决策
ephemeral 定位为 HFT 传输基础设施层——扩展协议无关性、可观测性和安全底线，不越界做协议解析、风控或策略框架。

### P0 核心必需
1. TLS bypass 模式（Crypto 模板参数 + NullCrypto）
2. 进程级 kill switch（全局原子 flag，0 开销）
3. 硬件时间戳支持（DPDK rte_eth_read_clock）

### P1 高价值差异化
4. 可插拔消息分帧器（MessageFramer concept）
5. 传输层延迟 breakdown（编译期开关 + HdrHistogram）
6. 可观测性增强（队列水位、NIC 统计、延迟直方图）

### P2 完整性扩展
7. 多连接管理器（TransportGroup）
8. CPU isolation 检测
9. shared memory IPC 模块（独立 eph-ipc）

### 已解决的分歧
- FIX/ITCH 协议解析 → 不做（上层职责），用可插拔分帧器解耦
- Rate limiter → 不做内置，提供发送频率统计
- Position tracking → 不做（OMS/风控层）
- TLS bypass → 模板参数（编译期消除）
- shared memory → 独立 eph-ipc 模块
- TransportGroup → 降为 P2（复杂度高）

### 未解决的权衡
- 日志热路径零开销：ring buffer vs SPDLOG_ACTIVE_LEVEL
- 直通发送模式：绕过 TX 队列 vs 保持线程安全
