## 内容摘要
讨论围绕 `run_dpdk`（130行）与 `run_socket`（40行）的差距展开。争议焦点是封装粒度——类级封装 vs 函数级封装 vs 不封装。R3（性能狂热者）担心封装隐藏 DPDK 调优点，R5（第一性原理者）提出"函数 < 类 < 框架"原则打破僵局。最终共识：`EalGuard`（RAII 生命周期管理）+ `connect()` helper 函数，总计约 80 行新代码，每个 DPDK example 减少约 85 行。

## 第 1 轮：各角色独立提出核心论点

**【极简主义者 R2 | 赞成封装】**
论点：`run_dpdk` 有 130 行，而 `run_socket` 只有 40 行，两者做的是同一件事——建立 WebSocket 连接并跑 echo loop。差异来自 DPDK 的初始化仪式：EAL→Platform→MAC→ARP→TcpConfig→Factory。这些步骤在每个 DPDK 客户端中都一样，应该提供一个 `DpdkContext` 或类似封装。

**【性能狂热者 R3 | 反对过度封装】**
论点：选 DPDK 就是因为需要完全控制数据面。`run_dpdk` 里的每一步都是用户可能需要自定义的：Platform 的队列数/描述符数、ARP 超时策略、端口选择逻辑、mempool 大小。封装层把这些藏起来后，高级用户就得 unwrap 或靠 config struct 暴露参数——到头来 config struct 就是 `run_dpdk` 的另一种写法。DPDK 的复杂度是**本质复杂度**，不是偶然复杂度。

**【第一性原理者 R5 | 质疑封装层级】**
论点：`run_dpdk` 的 130 行中，**不变的**（EAL init/cleanup、Platform、MAC、ephemeral port）约 40 行，**按应用变化的**（DNS、ARP 参数、TcpConfig 五元组）约 50 行，**胶水代码**（错误处理、日志）约 40 行。真正可封装的只有 40 行，收益有限。

**【维护性倡导者 R6 | 赞成封装】**
论点：随着更多 DPDK 应用出现，每个都手写 EAL→Platform→ARP 流程，Platform API 变更就要改 N 处。`do {} while(false)` + break 的模式本身就说明代码在用 workaround 模拟 RAII——封装正好解决这个问题。

**【实用主义者 R4 | 条件性支持】**
论点：目前只有 1 个 DPDK 示例。Rule of Three：等到第 3 个应用出现时再提取公共模式。但如果已规划多个 DPDK 应用，现在做也合理。

## 第 2 轮：交叉反驳

**【R2】**
反驳 [R3]：config struct 提供**声明式**接口——用户说"我要什么"，而不是"怎么做"。当前 15 步命令式流程要求用户理解执行顺序（DNS 在 EAL 前、ARP 在 connect 前），封装层消除**时序依赖的认知负担**。
反驳 [R5]：关键不是行数而是**认知复杂度**。`do-while(false)` + break + 手动 cleanup 的错误处理路径用 RAII 封装后会变简单。
反驳 [R4]：Rule of Three 适用于业务代码，不适用于**库的公共 API**。example 就是 API 的广告。

**【R3】**
反驳 [R2]：声明式接口意味着把所有参数堆到一个 config struct 里，会膨胀成 God Object。不如保持组合式 API：Platform + ARP + TcpSession 各自独立配置。
反驳 [R6]：Platform API 已经很稳定。封装层反而会成为不稳定的中间层。
联盟 [R5]：同意"本质复杂度不可压缩"。

**【R5】**
反驳 [R2]：时序依赖是**领域知识**——DPDK 用户必须理解"DNS 用内核栈，所以要在 EAL 接管 NIC 之前做"。封装层隐藏这个知识但不消除它。
反驳 [R6]：`do-while(false)` 的解法可以是**函数分解**而非新类型。函数 < 类 < 框架，选最轻量的工具。
立场修正：R2 关于认知复杂度的论点有道理，倾向**函数级封装**。

**【R6】**
反驳 [R3]：高层封装是**快捷路径**，不是唯一路径——用户仍可直接用底层 API。
反驳 [R5]：函数分解不管理生命周期。EAL cleanup 必须在 Platform 销毁后调用——RAII 正是解法。

**【R4】**
反驳 [R2]：2 行目标 API 太理想化，实际至少 15-20 行。但从 130 行到 20 行仍是显著改善。
联盟 [R5]：函数级封装是最低风险方案。

## 第 3 轮：方案收敛

**【R2】** 修正为函数级封装：提取 `connect_dpdk()` helper，EAL 由用户管理。
**【R3】** 条件接受：返回值必须暴露 Platform 和 mempool 等中间产物。
**【R5】** 提出折中两层方案：(1) `EalGuard` RAII 类 (2) connect helper 函数。两者合力将 run_dpdk 从 130 行降到 40-50 行。
**【R6】** 同意两层方案，补充 EalGuard 应 move-only。
**【R4】** 量化 ROI：~80 行新代码，每个 example 减少 ~85 行。

---

## 第 4 轮：最终立场声明

- **R2**：从类退让到函数。`EalGuard` + `connect()` 足够。
- **R3**：接受，条件是暴露中间产物。
- **R5**：两层方案是最小充分解。
- **R6**：EalGuard 解决 do-while 代码味道，helper 函数提供单一变更点。
- **R4**：方案 ROI 合理。

## 最终方案

### 核心决策
提供两层轻量封装：`EalGuard`（RAII 生命周期）+ `connect()` helper 函数（初始化流程），不引入重量级框架类。

### 方案细节

**1. `EalGuard`（eph-dpdk/include/eph/dpdk/eal.hpp）**
```cpp
class EalGuard {
public:
    static std::expected<EalGuard, std::string> init(int argc, char** argv);
    ~EalGuard() { if (initialized_) eal_cleanup(); }
    EalGuard(EalGuard&&) noexcept;
    EalGuard& operator=(EalGuard&&) noexcept;
    EalGuard(const EalGuard&) = delete;
private:
    bool initialized_ = false;
};
```

**2. `DpdkConnector`（新文件 eph-dpdk/include/eph/dpdk/connector.hpp）**
```cpp
struct DpdkConnectorConfig {
    PlatformConfig platform{};
    std::string    local_ip;
    std::string    gateway_ip;
    uint16_t       local_port = 0;
    std::chrono::milliseconds arp_timeout{3000};
    std::chrono::milliseconds connect_timeout{5000};
};

struct DpdkConnectorResult {
    Platform                        platform;
    std::unique_ptr<DpdkTransport>  transport;
    rte_ether_addr                  local_mac;
    rte_ether_addr                  gateway_mac;
};

template <typename TransportType = DpdkTransport>
std::expected<DpdkConnectorResult, std::string>
connect(const DpdkConnectorConfig& dpdk_cfg,
        const TransportConfig& transport_cfg);
```

### 已解决的分歧
- **类 vs 函数** → 采用 helper 函数 + 轻量 EalGuard 类
- **God Object 风险** → 通过嵌套复用 PlatformConfig 和 TcpConfig 解决
- **过早抽象** → 库 API 示例不适用 Rule of Three，且实现量小

### 未解决的权衡（需用户决策）
- **DNS 放在封装内还是外**：DNS 必须在 EAL 之前调用，connect() 应接受 server_ip 还是 hostname？
- **Transport 模板参数**：helper 函数模板化（灵活但复杂）vs 固定用 DpdkTransport（简单但不支持变体）
