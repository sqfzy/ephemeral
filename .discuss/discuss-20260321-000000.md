# Discussion Record

## Context
- 时间：2026-03-21
- 用户原始需求：Root cause: With af_packet PMD, the kernel and DPDK share the NIC. When the SYN-ACK arrives, the kernel's TCP stack sees it first, finds no matching socket, and sends RST — killing the connection before DPDK can process it. 如何解决这个问题？给出方案
- 复杂度评估：高
- 讨论轮数：6 轮
- 参与角色：性能狂热者(R3)、风险卫士(R1)、极简主义者(R2)、激进创新者(R8)、实用主义者(R4)（全部为预定义角色）

## 内容摘要
讨论围绕 af_packet PMD 下内核 TCP 栈发送 RST 干扰 DPDK 用户态连接的问题展开。核心争议包括：(1) 是否应完全放弃 af_packet 转用原生 PMD——被否决，因 af_packet 在开发环境（尤其 WSL2）不可替代；(2) network namespace 隔离方案——被证伪，af_packet 绑定物理接口后内核 TCP 栈在 netns 中仍存在；(3) 一次性建立四层可插拔过滤抽象 vs 分阶段改进——分阶段策略胜出。最终共识为三阶段方案：Phase 1 改进现有 iptables 过滤（精确匹配、IPv6、错误报告、崩溃恢复），Phase 2 评估 AF_XDP PMD 替代，Phase 3 按需建立可插拔过滤抽象。

## 讨论过程

### Step 0: 参数解析 & 复杂度评估

**复杂度：高** — 跨内核/用户态边界，涉及网络栈、PMD 架构、安全性、可移植性等多维度权衡，存在多个合理方案且无单一最优解。

**讨论轮数：7 轮（最低），连续 2 轮无新论点则终止 → 实际 6 轮终止**

**角色数量：5**

### Step 1: 角色选择

| 角色 | 代号 | 选择理由 | 预期冲突 |
|------|------|----------|----------|
| **性能狂热者** | R3 | 此项目追求超低延迟 WebSocket，性能是核心约束 | 与 R6（维护性）、R1（安全性）冲突 |
| **风险卫士** | R1 | 内核/DPDK 共享 NIC 涉及系统级风险，需识别故障模式 | 与 R3（性能优先）、R8（激进方案）冲突 |
| **极简主义者** | R2 | 项目哲学是"最小 TCP 实现"，复杂度控制至关重要 | 与 R8（理想方案）、R12（系统影响）冲突 |
| **激进创新者** | R8 | 需要跳出 af_packet 框架，探索根本性解决方案 | 与 R2（简单）、R4（实用）冲突 |
| **实用主义者** | R4 | 需要实证验证方案可行性，拒绝空谈 | 与 R8（理想化）冲突，与 R2 可能联盟 |

张力结构：R3↔R1（性能 vs 安全）、R8↔R2（复杂 vs 简单）、R8↔R4（理论 vs 实证）

### 第 1 轮：各角色独立提出核心方案

**【性能狂热者 R3 | 全内核旁路】**
论点：根本问题是 af_packet 与内核共享 NIC。唯一零开销方案是完全绕过内核——使用原生 PMD（如 igb_uio/vfio-pci）将网卡完全交给 DPDK。af_packet 本身就有 ~10μs 额外延迟，RST 问题只是"共享 NIC"这个架构缺陷的症状之一。治本之道是消除共享。

**【风险卫士 R1 | 多层防御】**
论点：当前 iptables RST 抑制方案是单点依赖——需要 root 权限、仅支持 IPv4、依赖特定 iptables 版本。主张多层防御策略：
1. 首选：nftables 替代 iptables（更现代，支持 IPv4/IPv6）
2. 备选：BPF/XDP 程序在最早阶段丢弃内核方向的 RST
3. 兜底：使用 network namespace 隔离 DPDK 流量

**【极简主义者 R2 | 改进现有 iptables】**
论点：KernelRstGuard 已经工作了。改进方向：支持 IPv6、加更精确的匹配规则、检测 nftables vs iptables 并自动选择。最小改动，最快交付，风险最低。

**【激进创新者 R8 | Network Namespace 隔离】**
论点：所有 iptables/nftables/BPF 方案都是在修补共享的后果而非消除共享。提议将 DPDK 使用的网卡移入独立的 network namespace，彻底隔离。

**【实用主义者 R4 | BPF 过滤】**
论点：主张 TC-BPF 或 socket filter。在 tc egress 挂载 BPF 程序，精确匹配并丢弃内核发出的 RST。比 iptables 更高性能（在 tc 层处理），比 XDP 更易部署。可精确匹配源 IP + 源端口 + TCP flags，误杀率趋近于零。

### 第 2 轮：交叉反驳

**【R3】**
反驳 R2：KernelRstGuard 需要 root 权限、静默失败时用户不知道、且没有覆盖 GRO 问题。
反驳 R8：Network namespace 对 af_packet 不适用——af_packet PMD 通过 AF_PACKET socket 直接绑定物理接口，移动接口到 netns 后内核栈在该 netns 中仍然存在。

**【R1】**
反驳 R3：完全内核旁路意味着放弃 WSL2 兼容性和开发便利性。
反驳 R4：BPF 程序的编写、编译、加载需要额外工具链，增加了构建依赖和部署复杂度。

**【R2】**
反驳 R3："用原生 PMD"等于说"别用 af_packet"——开发环境怎么办？
反驳 R8：R3 已经证伪了 netns 方案。
反驳 R4：BPF 的编译和加载需要 clang/llvm + libbpf，对 C++ 库来说是不合理的外部依赖。

**【R8 | 修正方案】**
承认 netns 方案对 af_packet 无效。修正为：在 netns 中创建 veth pair，DPDK 绑定 veth 端。
反驳 R2：iptables 方案是事后补救——内核已经处理了包、生成了 RST，然后在出口被丢弃。CPU 开销仍在。

**【R4】**
反驳 R8：veth 增加一次额外的数据包拷贝和上下文切换，延迟增加 5-15μs。
反驳 R1：可以做渐进式降级：优先 BPF → 降级 nftables → 降级 iptables。运行时检测，不需要编译时依赖。
反驳 R2：可以预编译 BPF 字节码嵌入到程序中（CO-RE），运行时通过 bpf() 系统调用加载。

### 第 3 轮：深入子议题——过滤层级对比

**【R3 | 分层分析】**

| 方案 | 拦截层 | 额外延迟 | 内核是否处理包 |
|------|--------|----------|---------------|
| 原生 PMD | 无内核参与 | 0 | 否 |
| XDP DROP | 驱动层 | <100ns | 否 |
| TC-BPF DROP | TC 层 | ~1μs | 部分 |
| nftables/iptables DROP | Netfilter | 3-5μs | 是 |
| veth + netns | 虚拟接口 | 5-15μs | 是 |

**【R1 | 环境兼容性矩阵】**

| 方案 | 原生 Linux | WSL2 | 容器 | 需要 root |
|------|-----------|------|------|----------|
| iptables | Y | Y | 需 CAP_NET_ADMIN | 是 |
| nftables | Y | 部分 | 需 CAP_NET_ADMIN | 是 |
| XDP | Y | N | 受限 | 是 |
| TC-BPF | Y | 部分 | 受限 | 是 |
| 原生 PMD | Y | N | N | 是 |

反驳 R3：XDP 在 WSL2 上不可用，而项目明确支持 WSL2 开发。

**【R2】**
iptables 是唯一在所有目标环境都工作的方案。
联盟 R1：同意多层防御思路，但 iptables 为主。

**【R8 | 转向混合方案】**
接受约束。主张应该在架构上明确 af_packet 是"开发模式"。
联盟 R4：同意渐进式降级，应设计可插拔 KernelFilter 抽象。

**【R4 | 渐进式降级架构】**
提出 KernelRstFilter 接口 + 四个后端（XDP/TC-BPF/nftables/iptables），运行时按优先级尝试。

### 第 4 轮：聚焦实现细节

**【R3】** 接受混合架构。要求：精确匹配五元组、规则生命周期与连接绑定、BPF map 动态更新。

**【R1 | 故障模式分析】**
1. 过滤安装失败：不再静默
2. 过滤意外移除：周期性检查
3. 进程崩溃未清理：comment 标记 + 启动清理
4. 并发实例：per-session 规则

**【R2 | 分阶段实施】**
Phase 1: 改进 KernelRstGuard（精确规则+IPv6+错误报告）
Phase 2: 抽象接口 + nftables 后端
Phase 3: BPF/XDP 后端

**【R8 | AF_XDP 替代方案】**
提出 AF_XDP PMD 作为 af_packet 的现代替代：比 af_packet 快 5-10x，支持 XDP 程序，DPDK 已原生支持 net_af_xdp。

**【R4】** AF_XDP 有价值但是独立议题。Phase 排序：改进 iptables → 评估 AF_XDP → 如仍需 af_packet 才建抽象层。

### 第 5 轮：收敛争议

所有角色趋向一致：
1. Phase 1（立即）：改进 KernelRstGuard 四项改进
2. Phase 2（中期）：评估 AF_XDP PMD
3. Phase 3（如需）：可插拔过滤抽象

### 第 6 轮：最终立场修正

**R3**：放弃"只用原生 PMD"，接受 af_packet 在开发环境的必要性。坚持精确过滤和 AF_XDP 方向。
**R1**：从多层防御全部实现缩减到分阶段。坚持故障模式必须在 Phase 1 处理。
**R2**：接受 Phase 1 范围比预想的大，但仍可控。坚持不在 Phase 1 引入新抽象。
**R8**：从 netns 方案退回，转推 AF_XDP 为 Phase 2。被 R3 证伪 netns 对 af_packet 无效。
**R4**：从四层抽象缩减为分阶段。坚持 BPF 预编译嵌入在 Phase 3 的价值。

## 最终方案

### 核心决策
分阶段解决：立即改进现有 iptables RST 过滤（精确匹配+健壮性），中期评估 AF_XDP PMD 替代 af_packet。

### 方案细节

**Phase 1：改进 KernelRstGuard（立即实施）**

1. **精确规则匹配**：从 `-s <src_ip> --tcp-flags RST RST` 改为 `-s <src_ip> -d <dst_ip> --dport <dst_port> --tcp-flags RST RST`
2. **IPv6 支持**：检测地址类型，使用 ip6tables 处理 IPv6
3. **错误报告**：安装失败时返回错误或记录 WARN 日志，不再静默
4. **崩溃恢复**：规则添加 `--comment "eph-dpdk-rst-<session-id>"`，启动时清理残留
5. **nftables 兼容**：运行时检测 nft 可用性，优先使用 nftables

**Phase 2：AF_XDP PMD 评估（中期）**

1. 测试 net_af_xdp PMD 的 WSL2/原生 Linux 兼容性和性能
2. AF_XDP 自带 XDP 程序能力，可从驱动层拦截 RST（<100ns）
3. 迁移成本预期很低（仅 EAL 参数变化）

**Phase 3：可插拔过滤抽象（如仍需 af_packet）**

KernelRstFilter 接口 + 多后端（NftablesFilter, IptablesFilter, TcBpfFilter, XdpFilter），工厂函数按优先级自动选择。

### 已解决的分歧
- netns 隔离方案 → 证伪：af_packet 绑定物理接口，netns 中内核 TCP 栈仍存在
- 四层抽象前置 vs 分阶段 → 分阶段胜出
- 只用原生 PMD vs 支持 af_packet → af_packet 在开发环境不可替代

### 未解决的权衡（需用户决策）
- **Phase 1 错误处理策略**：过滤安装失败应阻止启动 vs warning + 继续运行
  → 若面向生产环境选前者；若面向开发便利选后者（推荐后者）
- **AF_XDP 优先级**：立即评估 vs 等当前方案有痛点再说
  → 若性能是近期需求选前者；若稳定性优先选后者
