## 内容摘要

讨论围绕 ephemeral HFT 库的功能缺失展开。核心争议在于库的定位——R5 主张保持纯传输层，R4 和 HFT 领域专家认为需要向上扩展到订单簿、连接管理等交易基础设施。R3 聚焦性能死角（缺少 io_uring 后端、UDP multicast），R14 关注架构健康（错误类型不统一、Framer 概念受限、隐式依赖）。最终全员达成共识：通过四阶段路线图，以独立可组合模块的方式逐步从传输库演进为 HFT 工具集。最高优先级缺失：订单簿、JSON parsing、连接管理层、io_uring 后端。

---

## 第 1 轮：初步论点

### 【性能狂热者 R3 | 延迟还有压缩空间】
论点：
1. **缺少 io_uring 后端**——当前只有 POSIX poll() 和 DPDK，中间地带空白。io_uring 在 kernel 5.x+ 上能提供接近 DPDK 的延迟而无需专用硬件。
2. **WebSocket 掩码没有 SIMD 优化**——apply_mask 逐字节 XOR，缺少显式 NEON/AVX2 实现。
3. **没有 UDP/multicast 支持**——多数交易所行情是 UDP multicast（CME MDP、OPRA），只有 TCP WebSocket 覆盖不了主流场景。
4. **DPDK TCP 没有重传机制**——"丢包就重连"在跨数据中心场景代价太高。
5. **没有 CPU cache prefetch 策略**——SPSC 队列消费端、协议解析中显式 prefetch 能降低 cache miss。

### 【第一性原理者 R5 | 先定义边界再谈缺失】
论点：
1. **定位不清**——是"HFT 网络传输层"还是"HFT 完整框架"？会被拿来和 QuickFIX/Aeron/Chronicle 对比。
2. **WebSocket 不是 HFT 主流协议**——真正低延迟交易所用 raw TCP + 自定义二进制协议。WebSocket 主要用于加密货币。
3. **缺少的不是功能而是"约束声明"**——设计约束没有系统性声明。
4. **序列化不应是库的职责**——Protobuf/msgpack 是应用层的事。

### 【实用主义者 R4 | 看实际使用场景】
论点：
1. **FIX 4.4 版本过老**——生产环境已是 FIX 5.0 SP2 + FIXT 1.1。
2. **没有订单管理层**——FIX session 只做了 Logon/Heartbeat，缺少 OMS 骨架。
3. **没有 reconnect 后的状态恢复**——gap fill、sequence reset、message replay 未完整实现。
4. **缺少 rate limiter**——交易所对消息频率有严格限制。
5. **没有配置热加载**——运行时无法调整参数。

### 【架构师 R14 | 模块边界与扩展性】
论点：
1. **FIX/ITCH 对 eph-net 有隐式依赖**——用 add_includedirs 绕过正式依赖是架构异味。
2. **没有连接管理层**——多连接场景需要手动管理。
3. **Framer 概念不够通用**——静态 decode 方法不支持有状态 framer。
4. **缺少事件循环/调度器抽象**——没有 reactor/proactor 模式基础设施。
5. **模板参数过多导致类型爆炸**——6 个模板参数给用户认知负担太重。

### 【HFT 领域专家 | 缺少交易核心基础设施】
论点：
1. **没有订单簿**——ITCH 解析器能解出事件，但没有 L2/L3 订单簿重建。
2. **没有时钟同步方案**——TSC 只能度量本地间隔，缺少 PTP/PPS 支持。
3. **缺少 SoupBinTCP/OUCH/BOE 等关键协议**——协议覆盖面太窄。
4. **没有风控模块**——Pre-trade risk check 是监管要求。
5. **没有策略执行框架**——缺少信号→订单→执行→回报的完整 pipeline。
6. **没有 gateway/colocation 抽象**——生产 HFT 的进程分层无法自然表达。

## 第 2 轮：交叉反驳

### 【性能狂热者 R3】
反驳 [R5]：边界由竞品定义——Aeron 有 UDP multicast，Seastar 有 io_uring。定位可以窄，但选定领域内必须极致。
反驳 [R14]：QueueDepth 变运行时参数会引入堆分配，HFT 热路径不可接受。模板参数多的代价是编译时间不是运行时性能。

### 【第一性原理者 R5】
反驳 [HFT 领域专家]：加上订单簿、风控、策略框架就不是"库"是"平台"了，违反 C++ 组合式哲学。
反驳 [R4]：FIX 4.4 在加密货币交易所仍是主流，升级是演进方向不是"缺失"。

### 【实用主义者 R4】
反驳 [R5]："不该管"和"该提供但不强制"是两回事。零开销可选组件不违反组合哲学。
反驳 [R3]：SIMD masking 优先级不高，应投入 TLS record batching。
联盟 [HFT 领域专家]：rate limiter 和 reconnect state recovery 是生产刚需。

### 【架构师 R14】
反驳 [R3]：接受热路径参数模板化，但 LastOnlyDeliver 可用 if constexpr 代替。需要更多 type alias。
反驳 [HFT 领域专家]：订单簿应定义 OrderBookConcept，保持 concept-driven 架构风格。
联盟 [R4]：连接管理层应作为可选模块，零开销原则。

### 【HFT 领域专家】
反驳 [R5]：Linux 内核提供完整协议栈，不只是系统调用接口。HFT 库至少应做到"可连接交易所、接收行情、发出订单"。
反驳 [R14]：OrderBookConcept 过度设计——直接提供高性能实现，抽象是性能杀手。
联盟 [R4]：ping/pong 超时检测不够健壮。

## 第 3 轮：协议覆盖

### 【性能狂热者 R3】
聚焦 UDP multicast 缺失——equity HFT 行情来源是 multicast feed，DPDK 后端加 multicast 是自然延伸。
反驳 [R4]：TLS record batching 只对加密货币有用，应优先投入非 TLS 协议路径。

### 【第一性原理者 R5】
WebSocket + FIX + ITCH 组合透露库瞄准加密货币 HFT + Nasdaq equity 行情。应坦诚接受定位。
反驳 [HFT 领域专家]：与其广撒网加协议，不如在已有协议上做到极致。
联盟 [R3]：UDP multicast 限定 MoldUDP64 作为第一步。

### 【实用主义者 R4】
加密货币 HFT 最紧迫缺失：多交易所聚合、增量 orderbook 管理、REST API + HMAC、JSON parsing。
反驳 [R5]：定位加密 HFT 不等于不需要补齐标配。

### 【架构师 R14】
Framer 扩展机制瓶颈：decode 是静态方法、msg_type 是 uint8_t、缺少协议协商阶段。
反驳 [R3]：multicast 需要完全不同的 Transport 抽象，应设计独立的 MulticastReceiver。

### 【HFT 领域专家】
协议优先级排序：P0(JSON/MoldUDP64+ITCH) → P1(SoupBinTCP/OUCH/SBE) → P2(BOE/PILLAR) → P3(FIX 5.0)。
反驳 [R14]：decode 改实例方法有开销，更好方案是添加 context 模板参数。

## 第 4 轮：订单簿与数据结构

### 【性能狂热者 R3】
订单簿性能要求：sorted array（不是 std::map）、固定内存预分配、开放寻址 hash map、支持 implicit 和 explicit 两种模式。
反驳 [R14]：概念约束接口，但性能差异在实现。应提供极致实现而非概念定义。

### 【第一性原理者 R5】
订单簿真正需求：BBO O(1)、Top N O(1)、Order lookup O(1) hash、增量更新 O(1)、快照对账。区分行情 book（只读）和交易 book（读写）。
反驳 [R3]：sorted array 频繁插入需 memmove，深 book 不如跳表/B 树。

### 【实用主义者 R4】
加密交易所 orderbook 实际问题：增量格式各不相同、需要 REST snapshot 对账、checksum 验证。
反驳 [R5]：分开管理行情 book 和交易 book 增加延迟。

### 【架构师 R14】
订单簿应为独立模块 eph-book，事件驱动接口，提供 ArrayBook 和 MapBook 两种实现。
反驳 [R4]：交易所适配应是子模块，核心数据结构与交易所无关。
联盟 [R3]：同意预分配固定内存。

### 【HFT 领域专家】
需要衍生数据（mid price、spread、VWAP、order flow imbalance）、多 symbol 管理、时间序列、book 异常检测。
反驳 [R5]：可通过"本地订单覆盖层"统一行情 book 和交易 book。
联盟 [R14]：独立模块 eph-book + 事件驱动接口正确。

## 第 5 轮：可靠性与运维

### 【性能狂热者 R3】
需要 graceful degradation 和连接优先级；热路径 error handling 应零分配（ErrorCode 枚举代替 string）。
反驳 [R4]：运行时改 buffer size 需要 resize queue，SPSC 无法 lock-free 实现。

### 【第一性原理者 R5】
错误模型混乱（expected<T,string> / optional<T> / 枚举混用）；需区分可恢复/致命错误；缺少 crash handler。
反驳 [R3]：折中方案——热路径用 ErrorCode，日志附带详细信息。

### 【实用主义者 R4】
需要 Prometheus/StatsD 指标导出、结构化审计日志、健康检查 API。
反驳 [R5]：补充 kill switch 需求——不是上层应用的事而是安全基础设施。
联盟 [HFT 领域专家]：审计日志和 kill switch 是监管硬性要求。

### 【架构师 R14】
提议统一错误类型 eph::Error<Category>；MetricsSink 概念（零耦合）；eph-audit 独立模块。
反驳 [R4]：Prometheus 直接集成太重，概念 + 示例适配器更合适。

### 【HFT 领域专家】
MiFID II/Reg NMS/SEC 17a-4 审计要求；drop copy session；灾难恢复（状态快照 + 事件溯源）。
反驳 [R14]：NullSink 默认危险，应默认 stderr sink。
联盟 [R4]：kill switch 和 crash handler 是安全底线。

## 第 6 轮：收敛——优先级与路线图

### 【性能狂热者 R3】
Tier 1（延迟关键）：io_uring、订单簿、UDP multicast、error path 零分配。
立场修正：接受 SIMD masking 优先级不高。

### 【第一性原理者 R5】
接受两阶段演进：v1.x 补齐传输层缺失，v2.x 向上扩展。
立场修正：纯传输层定位太窄，适度向上扩展必要。

### 【实用主义者 R4】
按用户场景排优先级——加密 HFT 用户需要 JSON/连接管理/orderbook，equity 用户需要 multicast/ITCH orderbook。
立场修正：接受分阶段演进。

### 【架构师 R14】
模块化路线图：v1.1(错误统一/Framer增强) → v1.2(eph-book/io_uring) → v1.3(eph-gateway/JSON/multicast) → v2.0(audit/risk)。
立场修正：接受热路径参数保持模板化。

### 【HFT 领域专家】
最高优先级：订单簿、JSON parsing、连接管理层、io_uring 后端。
立场修正：接受分阶段模块化演进，风控审计推迟到 v2。

## 第 7 轮：最终立场声明

### 【性能狂热者 R3】
- 放弃：SIMD masking 优化
- 坚持：io_uring 后端、ArrayBook 极致性能、error path 零分配
- 被说服：分阶段演进 + 模块化设计

### 【第一性原理者 R5】
- 放弃：纯传输层定位
- 坚持：模块独立性——每个新模块必须可独立使用
- 被说服：JSON parsing 属于传输层解码职责，订单簿是 ITCH 解析的自然延伸
- 新增：库需要明确的"定位声明"

### 【实用主义者 R4】
- 放弃：结构性参数热加载
- 坚持：JSON parsing、rate limiter、多交易所连接管理
- 被说服：MetricsSink 概念比直接集成 Prometheus 更合理
- 新增：需要真实场景示例（如连接 Binance 维护 orderbook）

### 【架构师 R14】
- 放弃：OrderBookConcept 过度抽象
- 坚持：错误类型统一、Framer 概念增强、隐式依赖显式化
- 被说服：热路径模板参数保持编译时确定
- 新增：新模块应遵循 concept-driven 设计风格

### 【HFT 领域专家】
- 放弃：一次性加入所有功能
- 坚持：订单簿最高优先级、crash handler/kill switch 尽早提供
- 被说服：分模块独立发展 + 分阶段演进
- 新增：需要 reference implementation（ITCH → orderbook → BBO 完整示例）

## 最终方案

### 核心决策
ephemeral 应从"低延迟传输库"演进为"HFT 基础设施工具集"，通过可组合的独立模块逐步扩展。

### 方案细节

**Phase 1 — 基础补齐 (v1.1)**
1. 错误处理统一：全库采用 eph::ErrorCode 枚举（热路径）+ spdlog 详细日志（慢路径）
2. Framer 概念增强：decode 从静态方法改为实例方法，支持有状态 framer
3. 隐式依赖显式化：提取 eph-core（tcp_concept、transport_types、error types）
4. 更多预定义 type alias 降低模板参数认知负担

**Phase 2 — 核心扩展 (v1.2)**
5. eph-book：订单簿模块——ArrayBook（L2，sorted array，预分配）+ MapBook（L3，open-addressing hash）
6. io_uring 后端：新的 TcpTransport 实现
7. simdjson 集成：作为 JsonFramer（满足 MessageFramer 概念）

**Phase 3 — 场景补齐 (v1.3)**
8. eph-gateway：多连接管理、reconnect state recovery、连接优先级、健康检查
9. UDP multicast 接收器：MulticastReceiver + MoldUDP64 解帧
10. Rate limiter（令牌桶，per-connection）
11. REST HTTP 客户端（复用 TLS 基础设施 + HMAC 签名）
12. 完整 reference implementation 示例

**Phase 4 — 生产加固 (v2.0)**
13. eph-audit：基于 mmap ring buffer 的结构化审计日志
14. Crash handler + kill switch
15. MetricsSink 概念 + Prometheus/StatsD 示例适配器
16. Pre-trade risk check 模块

### 已解决的分歧
- 库的定位 → 从纯传输层扩展为 HFT 工具集，保持模块独立可组合
- 订单簿抽象程度 → 直接提供高性能实现（ArrayBook/MapBook），不做过度抽象
- 模板参数 → 热路径参数保持编译时确定，提供更多 type alias
- 监控集成方式 → MetricsSink 概念（零耦合），不直接集成具体监控系统
- JSON parsing 是否属于库职责 → 属于（与 ITCH 二进制解析同层次）

### 未解决的权衡（需用户决策）
- **Framer decode 改实例方法 vs context 模板参数**：若追求极致性能选后者；若追求 API 简洁选前者
- **默认 MetricsSink 是 NullSink 还是 StderrSink**：若面向专业用户选 NullSink；若面向更广受众选 StderrSink
- **先做加密货币场景还是先做 equity 场景**：取决于目标用户群定位
