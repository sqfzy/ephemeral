# Decision: TD ledger closeout — 5 of 6 technical-debt items closed

**Date**: 2026-04-23
**Commit range**: `1491691..3bbd1fb` (6 commits covering 5 TD items;
cross-references `decision-20260423-045825.md` for the parent review
roadmap)
**Mode**: ADR-style (已决；对 TD-4 的延期明确列 WHY)

## TL;DR

Following the `lucky-giggling-kahan` review roadmap closeout
(`decision-20260423-045825.md`), this session closed **5 of the 6
tracked technical-debt items** (TD-1 / TD-2 / TD-3 / TD-5 / TD-6).
TD-4 (NIC_B wire-level reorder via tc netem) remains open — gated on
an environment change, not an engineering decision. A new TD-6 was
discovered and closed same-session (non-strict NONE-vs-BAD mask
precision). All 39 test targets (36 DPDK + 3 kernel / metrics) pass
across the full sequence.

## 背景 (Context)

### 触发

Parent review (`lucky-giggling-kahan`, archived in
`decision-20260423-045825.md`) identified 5 TD markers (TD-1..TD-5)
while landing the Tier 1/2/3 roadmap. After the roadmap closed (9/11
items), the user requested picking up the TDs one by one.

### 约束

- **HFT direct-colo assumption** (tcp.hpp:9-10 / 287) — all drop
  decisions must stay within the "no retransmit / no Nagle / fresh
  reconnect on loss" design envelope.
- **Byte-for-byte backward compat** for every default path — no
  existing `xmake build -g tests` target is allowed to regress.
  (Confirmed: 39/39 green at every commit.)
- **No host-kernel mutation** — TD-4 needs `tc qdisc netem` + root
  + persistent kernel state on the shared EC2 Graviton host; kept
  out of scope for this session as the cost/value doesn't fit the
  pre-ship window.
- **Auto mode** — `--auto` was active for the whole session; user
  approved TD-1..TD-6 upfront.

### 假设

- Splitting a single aggregate counter into sub-counters is a
  non-breaking extension as long as the aggregate reads the sum
  lazily (`publish_metrics` / dashboards unaffected).
- Strict RX cksum mode is orthogonal to the TD-1 split — opt-in
  bool, zero steady-state cost when off.
- The "medium scope" decision on TD-5 (top-level drop sites only,
  not every session-internal free) carries the same cost-benefit as
  the UDP side's Tier 2 #3.

## 候选方案对比（逐 TD 展开）

### TD-1: split vs single counter

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| A: 保留单 counter `kRxBadChecksum` | 简单，Phase 9 已实现 | 运维无法区分 L3 / L4 故障源 | rejected |
| B: 拆两个 + 保留 aggregate | 精细归因；aggregate 兼容既有 dashboards；零额外 atomic | dual-bit mbuf 把聚合从 1 变 2（语义调整） | **selected** |
| C: 拆两个 + 删除 aggregate | 最干净 | 破坏既有 publish_metrics 消费 | rejected |

**否决 C 的理由**：backward compat 是约束。`kRxBadChecksum` 仍由
`publish_metrics` 作为单一 name 发送到下游；强行删除会牵连所有
dashboards。lazy-compute sum 是零成本的中间方案。

### TD-2: 是否再加 `kRxBadChecksumStrictDropped` 之类新 counter

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| A: 独立 counter | strict/non-strict 归因清晰 | 三态 counter 数爆炸；语义重叠 | rejected |
| B: 复用 TD-1 的 IP / L4 sub-counters | 单一 counter 模型；invariant 恒等 | strict 下 UNKNOWN 一包 +2 须文档清晰 | **selected** |

### TD-3: 放 session 层还是 stream 层

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| A: 在 `TcpSession::process_rx` 内部 drop | 与 session 的其他 drop 点同位 | session 要新增参数 / 暴露 counter API；跨 backend 不对称（UDP 在 stream 层） | rejected |
| B: 在 `DpdkTcpStream::process_burst_` 顶部 drop + compact | UDP 对称；session 零改动；`[[unlikely]]` + 默认 opt-in off 零热路径成本 | compact 需要在发送到 sess 之前 | **selected** |

### TD-4: 做还是推迟

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| A: 现在做 `tc qdisc netem` 基础设施 | 闭合 NIC_B wire 级覆盖真空 | 需要 root + 持久 kernel 状态 + 清理机制；单项 effort 大；共享 host 影响其他 tenant | rejected (env) |
| B: 推迟到专门的 tc-netem session | 风险隔离；需求 / 信号驱动 | 覆盖真空持续（但已由 stream-layer e2e 部分覆盖） | **selected** |

### TD-5: 归因范围

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| 窄: 仅 `PacketsDropped` 总闸 | 最小改动 | 运维分辨不出"peer 重发 (dup)"vs"malformed" | rejected |
| **中: +`kTcpDupSegments` 专用 counter** | 主要 drop 维度都可见；复用 UDP 的 cross-backend counter | 不覆盖 session 内部所有 free 点 | **selected** |
| 宽: session 内每处 free 都归因 | 完整 | 改动侵入 session 热路径；需改 process_rx 签名 | rejected |

### TD-6: 非 strict drop 条件是否要精确化

**发现时机**：TD-2 施工中意识到 DPDK 把 `NONE` 编码为 `BAD|GOOD`
双 bit set，导致 `(olf & BAD_bit) != 0` 会错误匹配 NONE。

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| A: 维持 bit 测（现状）+ 留 TD-6 | 本次不扩张 | 继续错误归因；运维 dashboard 有系统偏差 | rejected |
| B: 改 `(olf & MASK) == BAD` 精确比较 | 语义正确；热路径零额外成本（同样一个 branch） | 非 strict 下 NONE 从"drop"变"accept"——行为变化 | **selected** |

**否决 A 的理由**：TD 本身是"在合适时机闭合"，既然在 session 内
发现，顺手闭合成本 < 延期记忆负担。行为变化对 HFT colo 场景影响
为零（UDP 都带 cksum）。

## 共同的产品级权衡

- **热路径成本**：所有 TD 都走 `[[unlikely]]` 分支，default（opt-in
  off）路径字节零变化。strict 模式在 TAKEN 分支里做 mask 比较而非
  bit 测，但分支判断只在 BAD / UNKNOWN / NONE 时才走进去，GOOD
  直走快路径。
- **并发**：所有新 counter 沿用既有 `alignas(64) std::atomic<uint64_t>`
  (stream) / plain `uint64_t` (TcpSession::Stats, single-lcore) 模式；
  无新锁。
- **观测性**：所有新 counter 都有 OTel name 并通过 `publish_metrics`
  统一导出，无新 sink 代码。
- **文档**：每 TD 都有 CHANGELOG 段 + enum doc comment 说明语义 +
  对称 mode 的行为对比。
- **测试**：每 TD 都有至少 2 个新测试 case（正例 + 反例）+ 更新
  旧测试断言（TD-1 的 `DropsOnBothBadFlags*` 改名 + 断言分裂）。
- **安全**：所有改动都是 stream-layer 加固（drop 更多 / 计更多），
  无新攻击面。

## 代价与权衡

**选 B 候选（中等 / split / 非破坏）对所有 5 个 TD 的代价**：

- **计数器数量膨胀**：`StreamMetric` enum 从 TD 前 18 → 现 21（
  +kRxIpChecksumBad, +kRxL4ChecksumBad, +kTcpDupSegments）。
  `publish_metrics` 对每个 metric 一次 push，单调增加 publish
  开销（~50 ns × 3 = 150 ns / publish call）。典型 publish 频率
  1 Hz，可忽略。
- **TcpSession::Stats 字段**：+3 字段（packets_dropped /
  fragment_rejected / dup_segments）每个 8 bytes = 24 bytes / session。
  对 single-lcore 2-4 TCP streams 意味着 < 100 bytes / lcore。忽略。
- **热路径复杂度**：UDP / TCP `process_burst_` 从 1 行 bit test
  扩展到 strict / non-strict 三元 + 两层分开判定。仍全部 stack-
  local + constexpr mask，编译器常量折叠后 steady-state 代码不变。
- **行为变化 (TD-6)**：非 strict 下 NONE 从 "drop" 变 "accept"。
  HFT 无影响；若上游生产中有已统计 NONE 被计到 BAD counter 的
  dashboard 基线，需要重置一次 baseline。

**选跳过 TD-4 的代价**：

- NIC_B wire 级 reorder 覆盖真空持续。当前覆盖：stream-layer 集
  成测试（`DpdkTcpStreamReorderOverflowE2E.RealReorderOverflowDrivesStreamReset`
  —— 通过构造 mbuf 在 session 内部触发 reorder overflow）已
  覆盖 reorder 逻辑本身。缺的是"真实 NIC 乱序交付"的 end-to-end
  触发路径。如果未来生产观察到 reorder 相关的异常行为（
  `kTcpReorderBufferOverflows` 突然升高但 reorder buffer 从未
  真正被触发），需要 TD-4 来排查。

## 后续影响

### 对架构

- `StreamMetric` 枚举从 18 扩到 21，`counters_[kCount]` 数组在所有
  4 个 backends（KernelTcp/Udp, DpdkTcp/Udp）自动扩展。
- `TcpSession::Stats` 增加 3 个字段；`dump()` / `to_json()` /
  `operator-` 都已更新；下游消费者自动看到新字段。
- `PlatformConfig` 增加 `enable_strict_rx_checksum` bool。`dump()`
  / `to_json()` / `warnings()` 都更新；已有的 pre-attach config
  shape 不破坏。

### 对其他模块

- Kernel backends (`KernelTcpStream` / `KernelUdpSocket`) 对所有
  新 counter 均 emit 0，跨 backend invariant 一致。
- `test_stream_metrics.cpp` 通过 `kStreamMetricNames` 对应表 slot
  的 compile-time `static_assert` 保护 enum ↔ name 同步；无手动
  维护。

### 对团队

- 新 opt-in flag `enable_strict_rx_checksum` 对监控 dashboard 意味
  着：
  - 若该 flag 开 + NIC 在某条路径频繁报 UNKNOWN →
    `kRxIpChecksumBad` / `kRxL4ChecksumBad` 会很高，要区分"真正
    的 cksum fail" vs "UNKNOWN" 需要 strict → non-strict 跨环境
    对比。
  - 若该 flag 默认关（当前默认），监控阈值不变。
- TD-6 导致非 strict 下 NONE 从 drop 转为 accept，dashboard 基线
  需要重置一次（不 reset 会看到 `kRxIpChecksumBad` 下降的"改善"，
  本质是行为变化不是性能改善）。

## 何时重新评估

| 条件 | 触发重评估 |
|------|---------|
| 生产需要真实 NIC 乱序 e2e 测试 + tc-netem 基础设施就位 | TD-4 实施 |
| 生产 `kTcpDupSegments` 频繁升高 | 评估 peer 是否在大量 retransmit，触发 `/pax --fix` 根因 |
| `enable_strict_rx_checksum` 开启后流量骤降 | NIC 驱动在某条路径输出 UNKNOWN；调查或改回 best-effort |
| UDP 下游消费者不接受非 strict NONE-accept 的新语义 | 重新讨论是否默认 strict |
| `StreamMetric` enum 进一步扩到 >30 项 | 考虑按 backend 拆 sub-enum（当前为单一 enum + bounds-check） |
