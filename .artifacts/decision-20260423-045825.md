## 背景 (Context)

### 触发

Review session `lucky-giggling-kahan` audited the `eph-net-dpdk` backend
(TCP + UDP data paths, ~2000-line `tcp.hpp` + `tcp_stream.hpp` + `udp_socket.hpp`
+ `platform.hpp`) after two production-hardening sweeps completed on Apr 22-23.
Review concluded the baseline is production-ready but identified 11 items worth
doing, organized as Tier 1 (shipped with latent risk) / Tier 2 (high-value) /
Tier 3 (polish).

### 约束

- **HFT direct-colo assumption** (tcp.hpp:9-10, 287): no retransmit, no SACK, no
  congestion control — loss → reconnect in ~2 ms. Decisions must stay within
  this design envelope.
- **Phase 9 scope decisions** (`.artifacts/phase-9-scope-decision.md`):
  chunked HTTP, SOCKS5, CONNECT-proxy on DPDK side, Gateway/CircuitBreaker
  frameworks are deliberately out of scope.
- **Environment**: AWS EC2 Graviton (aarch64), 16 cores @ 2 GHz, NIC_B (ENA)
  on vfio-pci. ENA does not advertise multicast through
  `rte_eth_dev_set_mc_addr_list` in a way that round-trips on VPC multicast
  filtering — blocks live-NIC multicast integration tests.
- **Toolchain**: gcc14-g++ (C++23) for xmake default; clang ≥17 for libFuzzer
  harnesses (fuzzers live outside the xmake graph by design).

### 假设

- Default opt-in paths must remain byte-for-byte unchanged — existing tests /
  benchmarks / CHANGELOG consumers unaffected.
- Each roadmap item is an independent pax; TDs are deliberate deferrals, not
  shortcuts.
- "Significant" is a statistical word reserved for `/pax --experiment`; this
  round uses only pax `--bench` baselines (non-statistical regression
  thresholds per bench skeleton §5).

## 候选方案对比（关键决策展开）

### 决策 1: UDP RX checksum — Candidate A vs B

| 维度 | A: 最小改动 | B: 根本修复 |
|------|-----------|-----------|
| 复杂度 | 低（3 hot-path 分支 + 1 opt-in bool） | 高（strict 模式 + L3/L4 拆 counter + SW fallback + TCP 对称） |
| 可维护性 | 高 | 中（opt-in matrix 3 态） |
| 性能（热路径） | 0 ns 开销（GOOD 包走直路） | UNKNOWN → SW 校验 +100-200 ns/包 |
| HFT 对齐 | 强（NIC 能力是 infra 决策） | 弱（SW fallback 违反 HFT 预算） |

**选 A**。理由：B 的 SW fallback 违反 HFT per-packet 预算约束（review 里
R11 怀疑论 / R3 性能狂热均否决）；B 的 strict 模式 / L3+L4 拆 counter 是
平滑扩展（留 TD-1 / TD-2），可事后无破坏性升级。

被否决的 B 的部分：

- **SW 校验和 fallback** — 否决，NIC 能力是 infra 层决策不是 per-packet 成本
- **strict UNKNOWN drop 模式** — 否决，HFT NIC 在 tunnel / VLAN 路径上
  合法发出 UNKNOWN；strict 会误杀；留作 TD-2 等运维请求信号

### 决策 2: 跳过 Tier 2 #4 multicast live-NIC 测试

| 候选 | 评估 |
|------|------|
| 实机 multicast e2e on ENA | ENA 不支持 `rte_eth_dev_set_mc_addr_list` 语义一致；VPC subnet 多播过滤；即便写出也会 SKIP-at-runtime |
| Mock multicast（回 loopback） | 失去真实 NIC 信号，review 已说"若物理环境限制，降级到 mock"；mock 层面测试已在 `test_dpdk_udp_multicast.cpp` 覆盖 RFC 1112 MAC 派生 |
| 跳过 | 明确记录 deferred；CHANGELOG 记为 "Tier 2 #4 deferred due to env limitation" |

**选：跳过**。理由：本环境两种可行路径（实机 / mock）各有根本障碍；
推迟到能切换到具备多播能力的物理 NIC 的环境（或 Linux kernel TUN/TAP +
local bridge 搭积木）再开。Review 原文明确允许此降级。

### 决策 3: 跳过 Tier 3 #11 TLS record-by-record encrypt API surgery

**候选**：

- A: 现在做。动机：把"latch + reconnect"组合换成"record-by-record 原子 encrypt"根本消除 partial-send desync 的可能性。
- B: 不做，等信号。动机：当前的 `tls_corrupt_` latch + reconnect 路径已能在 Apr-22 sweep 后的生产流量下正确处理任何观察到的失败；record-by-record surgery 是大动干戈（改 AEAD sequence state 管理 + wire encoding），且 ROI 在无 production trigger signal 的情况下为负。

**选 B**。理由：review 原文明确 "仅当 latch 被证明不够用时才做"；本会话
+ 2 次 hardening sweep 期间均无 TLS partial-send desync 的产生信号；提前
做是 pre-optimization。留作 conditional TD — 触发条件写入 CHANGELOG
（「latch + reconnect 被证明不足」= 观察到 desync + reconnect 后依然
有 nonce-state 问题的 case）。

### 决策 4: Tier 3 文档 sweep 合并 vs 分拆

**候选**：

- A: 三份文档（#8 / #9 / #10）分 3 个 pax / 3 个 commit
- B: 一个 `/pax --doc --auto` sweep + 1 commit 覆盖全部

**选 B（合并）**。理由：三份都是架构叙述类文档，彼此需要交叉引用
（README ↔ TCP guide ↔ UDP delta），分开施工会引入中间态（link broken
until 后续 commit）。单 commit 199915e 保证链接闭环一致。

## 代价与权衡

**选 A 候选（最小改动）对所有 Tier 1/2 项的代价**：

- `kRxBadChecksum` 单 counter 无法在生产中直接分辨 L3 vs L4 故障 —
  运维要分辨时需要 grep dmesg / NIC stat 辅助。TD-1 有切分路径但未
  预先付出枚举扩张代价。
- `process_burst_` 在热路径多一个 `[[unlikely]]` 分支 + 无 opt-in
  bool。benchmark 显示编译器 DCE + 分支预测保证 opt-in off 时 0 ns
  (默认 rxmode.offloads=0 → NIC 从不标记 BAD → 分支永不触发)，
  确认代价为 0。
- 新增 3 个 enum 值扩展 `StreamMetric::kCount`，所有 backends 的
  `counters_[kCount]` 数组跟进扩展。其他 backends 相关计数器保持 0
  emit，占空间但无行为变化。

**选跳过 Tier 2 #4 / Tier 3 #11 的代价**：

- multicast live-NIC 盲区：`rte_eth_dev_set_mc_addr_list` 真打 NIC 路径
  至今零 e2e 验证。若 Binance / OKX UDP 推送接入时出问题，需先补齐该
  测试（见 TD-4 附带）。
- TLS surgery 未做：若 TX ring 饱和 + AEAD 部分加密的罕见场景在生产中
  出现，当前 latch 路径会主动终止连接并 reconnect — reconnect 成本为
  毫秒级，不是 hard failure 只是 p99 突刺。可观测通过
  `kTlsSendDesyncs` 监控。

**选合并 doc sweep 的代价**：

- 一个 commit 692 insertions，单次 review 成本更高。但对链接闭环的收益
  大于 review 成本的增加（否则会引入 broken-link 中间态）。

## 后续影响

### 对架构

- 增加 3 个公共 StreamMetric（`kRxBadChecksum` / `kPacketsDropped` /
  `kFragmentRejected`）和 1 个 PlatformConfig opt-in 字段
  （`enable_rx_checksum_offload`）。所有均扩展型（default=false /
  N/A for non-DPDK backends），非破坏。
- `is_ip_fragment(mbuf)` 作为 `packet_parse.hpp` 公共辅助函数
  留给 DpdkTcpStream 将来对称 wire-up（TD-3）复用。
- `docs/dpdk-tcp-implementation.md` / `docs/dpdk-udp-design.md` 成为
  eph-net-dpdk 的设计权威参考；`README.md` 的 Thread Model 章节
  是模块文档的最高层入口。

### 对其他模块

- `eph-net/include/eph/net/stream_metrics.hpp` 新增 3 个 enum 导致
  kernel backends (`KernelTcpStream` / `KernelUdpSocket`) 的
  `counters_[kCount]` 数组扩展。编译期即 detect 任何遗漏；所有
  backends 测试（kernel + metrics + transport e2e）已验证通过。

### 对团队

- 新的 DPDK 文档入口（`docs/dpdk-*.md`）是未来 onboarding 的主推材料，
  与现有 `eph-net-dpdk/docs/ONBOARDING.md` 互补（ONBOARDING 讲 "读什
  么顺序"，新文档讲 "具体机制")。
- `test_tcp_close_reset.cpp` 的 keepalive 测试为下一次 refactor 提供
  exhaust-branch 的回归保障（标注 `>=` vs `>` 的边界，防意外降级）。
- bench baseline `.artifacts/bench-rx-hot-path-20260423.txt` 成为
  future regression gate — 任何改动 parse 路径的 PR 都应再跑并对比。
