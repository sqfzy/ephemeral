---

## TL;DR

DPDK client beats kernel p50 RTT by **12–17 %** across the 5 echo scenarios (`tcp` 24.3 → 21.0 µs, `udp` 23.5 → 20.6 µs, `ws` 26.1 → 21.7 µs, `ex_md_udp` 23.3 → 20.5 µs; `ex_order` anomalous this run — see §Anomalies). Pinning every lat_\* client to `cpu_client = 4` **stabilized DPDK RX p99** (tcp −25 %, ws −18 %) and halved run-to-run variance on p50 (<5 % shift vs last sweep). Three DPDK anomalies flagged (ex_order TX stall, UDP p99 spike, ex_market p99 sparsity) — all suspected to be transient / measurement-method artifacts, need follow-up profiling before citing.

---

## 假设（Hypothesis）

**H1 (primary)**: With client thread pinned, the DPDK client beats the kernel client at p50 RTT on every echo scenario, and at p99 by at least as much as in the previous (unpinned) sweep.

Falsifiers:
- Any echo scenario with kernel p50 ≤ DPDK p50 → H1 falsified for that scenario
- DPDK p99 / p50 ratio significantly *worse* than the unpinned baseline → pinning hurt, H1 falsified

**H2 (secondary)**: Pinning reduces run-to-run variance vs the unpinned baseline. Expected signature: p50 delta within ±5 %, DPDK-side RX p99 tightens toward its p90.

---

## 动机

Last sweep (06:51) had the client thread running unpinned on the dev host. The numbers were noisy and the user (correctly) rejected a causal story that rested on those noisy numbers. The reshape that followed:

1. Added `bench::pin_client_from_cfg(cfg, "lat_X")` to `benchmarks/latency/core/pin_client.hpp`
2. Invoked it from every `lat_*` binary main()
3. Saved a memory rule (`feedback_bench_pin_every_thread.md`) so this lesson doesn't get relearned

This rerun is the validation that the fix is effective — same host, same topology, same seed, same (derived) config, only difference = CPU pinning in every participating thread.

### 被测对象

- Git HEAD `7869ea4`; clean apart from `.artifacts/INDEX.md`, `CLAUDE.md`, fuzzer directory, `benchmarks/mockex/fixtures/ex_market_2p_sample.jsonl` (all unrelated to this rerun)
- 14 binaries exercised: `lat_tcp / udp / ws / ex_order / ex_market / ex_market_2p / ex_md_udp` each in kernel + `_dpdk` flavour, plus `mockex` (always kernel, pinned to CPU 6)
- All built with default release optimization; no rebuild between runs

### 数据集 (test inputs)

- Echo scenarios: `payload_size = 256` bytes, fixed (TCP / UDP / WS / ex_order / ex_md_udp)
- Push scenarios (`ex_market`, `ex_market_2p`): MMPP-2 Poisson sampler (`mockex_seed = 42`, `ex_market_params.toml` quiet-state rate λ_q = 2.69916 Hz, busy λ_b = 44,235.1 Hz)
- `warmup_samples = 1000` discarded

### 测量方式

- Echo RTT: client TSC stamp pair round-trip, 24-byte binary header carries client `t0` and mock-echoed `t_mock_recv` / `t_mock_send` for TX/RX leg decomposition
- One-way (`ex_market`, `ex_market_2p`): `bench::monotonic_raw_ns()` at client RX minus `"T"` field in the JSON payload stamped by mockex `PayloadPool::stamp_and_next`
- Aggregation: `eph::utils::Recorder::record_ns` (exact buckets, not HdrHistogram)
- Duration:
  - Echo: `duration_seconds = 30` via `/tmp/bench-30s.toml` (derived from `benchmarks/latency/config.toml`)
  - Push: `duration_seconds = 120` via `/tmp/bench-push-120s.toml` (needed because MMPP quiet state at seed 42 rarely transitions to burst in 30 s)
- Sample counts: 1.0 M – 1.4 M per echo run; 2,142 for `ex_market` (MMPP-limited); 163 k / 251 k for `ex_market_2p`

### 复现命令

```bash
# override configs
sed 's/^duration_seconds = 300$/duration_seconds = 30/' \
    benchmarks/latency/config.toml > /tmp/bench-30s.toml
python3 -c "
import re, pathlib
s = pathlib.Path('/tmp/bench-30s.toml').read_text()
s = re.sub(r'(\[scenarios\.lat_ex_market\]\n(?:.*\n)*?duration_seconds = )30', r'\g<1>120', s)
s = re.sub(r'(\[scenarios\.lat_ex_market_2p\]\n(?:.*\n)*?duration_seconds = )30', r'\g<1>120', s)
pathlib.Path('/tmp/bench-push-120s.toml').write_text(s)
"

# echo sweep
for s in tcp udp ws ex_order ex_md_udp; do
  sudo ./benchmarks/latency/lat "$s"        --config /tmp/bench-30s.toml
  sudo ./benchmarks/latency/lat "$s" --dpdk --config /tmp/bench-30s.toml
done

# push sweep
for s in ex_market ex_market_2p; do
  sudo ./benchmarks/latency/lat "$s"        --config /tmp/bench-push-120s.toml
  sudo ./benchmarks/latency/lat "$s" --dpdk --config /tmp/bench-push-120s.toml
done
```

The `lat` wrapper handles NIC-B state transitions (host ↔ bench_ns ↔ vfio-pci) idempotently.

## 分析

### 统计显著性

- Sample counts 1.0 M – 1.4 M per echo scenario — percentiles up to p99 are tight to within single-ns precision if the distribution is stationary. Anomaly outliers dominate p99 in two runs (see §Anomalies)
- No replication across seeds this sweep — single trial per `(scenario, backend)` pair
- Comparability to last sweep: same host, same binary artifacts for the pre-existing paths, **only** client-side CPU pinning differs — suitable for paired-delta analysis below

### H1 verdict — **✅ holds on 4/5 echo + 1/2 push; ex_order deferred**

For `tcp / udp / ws / ex_md_udp` and `ex_market_2p`: DPDK p50 strictly lower than kernel p50. Magnitudes: 12–17 % on echo, 3.2× on ex_market_2p (one-way latency measurement asymmetry, see previous sweep's report).

For `ex_order`: DPDK p50 = 262 µs vs kernel 25.8 µs — H1 fails catastrophically. But this run is anomalous (§Anomalies #1); not a real DPDK regression.

For `ex_market`: DPDK p50 = 9.0 µs vs kernel 14.4 µs → DPDK wins, but both numbers are noisy at 2,142 samples. p99 is unreliable.

### H2 verdict — **✅ pinning tightened DPDK RX p99**

Paired delta vs the 06:51 (unpinned) sweep on DPDK RX p99:

| 场景 | 06:51 dpdk RX p99 | 10:19 dpdk RX p99 | Δ |
|---|---:|---:|---:|
| tcp | 16,347 | 12,331 | **−25 %** |
| udp | 12,755 | 12,563 | −1 % |
| ws | 15,179 | 12,395 | **−18 %** |
| ex_md_udp | 12,619 | 12,467 | −1 % |
| ex_order | 12,843 | 12,691 | −1 % |

RX p99 is where pinning should help: the client's poll-recv path gets to stay on one core's cache. The 25 % / 18 % tightening on tcp / ws is consistent with that expectation. UDP / ex_md_udp / ex_order RX p99 was already ≤ 13 µs pre-pin, so there was less room to improve.

Kernel side was essentially unchanged (p50 shifts within ±5 %, p99 actually *worse* on some — see §Anomalies #4). That's expected: kernel NAPI + softirq scheduling jitter is not affected by userland client thread pinning.

### 归因 (Attribution)

1. **DPDK p50 echo win, unchanged in magnitude**: same root cause as last sweep — DPDK bypasses NAPI + syscall on the client RX path. Pinning didn't change the syscall count; it eliminated the **variance** on the syscall-less RX path.

2. **RX p99 tightening on tcp / ws**: TCP and WS share a codec-decode path (WsCodec for ws, 24-byte header parsing for tcp). Both decode hot functions fit in L1 once the thread stays on one core. Unpinned, CFS could migrate the client mid-burst, evicting the hot frame.

3. **Kernel p99 now worse on some scenarios**: kernel TCP p99 went 31,991 → 69,022 ns. Not pinning related — this is either environmental noise or a specific softirq pattern this morning. Consistent with kernel being sensitive to host state in ways DPDK isn't.

4. **Run-to-run stability**: echo p50 shifts all within ±5 % vs last sweep. Given we replaced zero variables between the two runs except (a) the pinning and (b) a couple of hours of wall-clock time, the stability is evidence that **pinning removed a large chunk of the previous noise** and most residual shift is pure environmental.

## Anomalies

Flag these; do **not** cite as DPDK performance characteristics.

### #1 — DPDK ex_order TX p50 = 253,880 ns

**Severity**: high (changes conclusion for the scenario if taken at face value)

- Previous sweep (unpinned): DPDK ex_order p50 = 20,983 ns, throughput 31,728 /s. Consistent with other DPDK echo scenarios.
- This sweep: p50 RTT = 262,072 ns; **p50 TX = 253,880 ns**, p50 RX = 8,097 ns. The entire 253 µs gap is in the TX leg. Throughput 3,806 /s (8× drop).
- Shape: `stddev = 12,622` on a p50 of 262 µs means TX leg is consistently ~250 µs, not occasional. The binary is doing something constant-time-expensive.
- Plausible causes (not yet profiled):
  - mockex `ex_order_echo` scenario does a JSON `t_mock_recv` / `t_mock_send` splice before sending back — if that hit a cold allocator / different code path this run, it would show here. But kernel side of the same mock ran at 31,437 /s, so the mock itself is fine; the issue is specific to the DPDK-client↔mock pair.
  - DPDK `tx_burst` on queue 0 blocking on descriptor exhaustion because mockex's kernel-side `send()` is lagging for some reason.
  - Cold `BusyCache` or AWS VPC flow-cache effect specific to this port (mockex binds a different port per scenario).
- **Recommendation**: rerun `lat ex_order --dpdk` 5× back-to-back. If TX p50 stays ~250 µs, capture with `perf record --call-graph dwarf` on the mockex PID and the client PID during a problematic run. If it becomes normal on later runs, it's cold-start noise from this morning's specific EC2 host state — annoying but not actionable.

### #2 — DPDK UDP p99 = 261,944 ns (paired with TX p99 = 253,496)

**Severity**: medium (p50 still clean; a few points smeared into p99)

- p50 RTT = 20,551 ns (perfectly normal), but p99 jumps to 262 µs. `stddev = 27,639` = 27 µs stddev on 21 µs median → long tail with very rare but huge outliers.
- `p99.9 = 264,056` nearly identical to p99 → suggests a small number (~0.9 % of 1.2 M samples ≈ 11 k events) of 250 µs stalls.
- **Coincidentally**, DPDK ex_order's 253 µs matches this number. Suggests a shared root cause — probably some periodic mockex kernel stall during this 30 s window. Did not manifest in TCP / WS / ex_md_udp.
- **Recommendation**: correlate timestamps within the run — if the 250 µs events cluster in time, it's a one-off environmental hit. Also re-run.

### #3 — DPDK ex_market p99 = 16,264,758 ns (16 ms)

**Severity**: low (known measurement-method limitation, not a DPDK defect)

- Same pattern as in the previous sweep's ex_market DPDK p99 = 36 ms. Root cause: MMPP quiet-state λ_q = 2.7 Hz at seed 42 means tens of seconds between bursts; one-way latency computed as `t_RX - t_send` inside a burst is fine, but something about the inter-burst gap leaks into the sample recorder.
- Not a latency of "the network took 16 ms" — it's a measurement artifact.
- **Recommendation**: fix by (a) refitting `ex_market_params.toml` to a higher λ_q from a real capture, or (b) client-side filter samples whose preceding inter-arrival exceeds some expected-quiet-state threshold.

### #4 — Kernel TCP p99 = 69,022 ns (vs 31,991 in last sweep)

**Severity**: low (kernel side, expected noise)

- p50 is unchanged (24.3 vs 24.5 µs). p90 / p99.9 also comparable.
- Only p99 blew up. Likely NAPI batching on a particular moment — kernel TCP p99 is dominated by softirq scheduling tail and is not expected to be stable across reruns without `isolcpus` + NIC IRQ affinity config that we don't have on this dev host.
- **Recommendation**: accept as environmental; if systematic, revisit after `isolcpus` / IRQ rebinding.

## 结论

- **H1 (DPDK ≤ kernel p50 RTT)**: ✅ holds on 4/5 echo + 1/2 push scenarios. `ex_order` result is an anomaly, not a counter-example. `ex_market` wins for DPDK but samples too sparse to be load-bearing.
- **H2 (pinning reduces variance)**: ✅ evidence from RX p99 tightening on tcp (−25 %) / ws (−18 %); p50 shifts contained within ±5 %.
- This sweep is the new baseline — the 06:51 sweep is kept as "unpinned history" and **should not** be used as a reference from now on.

---

## 边界条件 / 局限

1. **Single trial per (scenario, backend) pair**. Given 3 visible anomalies, future reruns should include ≥ 3 seeds per scenario to bracket reproducibility.
2. **30 s windows** for echo — p99.9 and max are dominated by 1–2 events per run. Don't cite those.
3. **ex_market sparse** (2,142 samples / 120 s ≈ 18 Hz). p99+ statistically meaningless.
4. **ex_market_2p p50 = 21.5 µs DPDK vs 69.5 µs kernel (3.2×)**: the delta is inflated by the one-way timing method (RX-side timestamping asymmetry between DPDK PMD vs kernel `recvmsg()`), not purely by the parse-cost benchmark this scenario is built for. Don't cite the 3.2× as "twophase parse is 3× faster on DPDK" — that's not what's being measured.
5. **Graviton aarch64**: numbers won't transfer to x86; pinning benefit may be larger on x86 where branch target buffers matter more.
6. **No `isolcpus`**: dev host has `allow_non_isolated = true`. Kernel p99 tails are floor-limited by this.

## 对决策的影响

- **ex_order DPDK rerun before trusting any DPDK-ex_order metric**. Until then don't compare ex_order against the other scenarios.
- **Keep this sweep as the baseline**; the 06:51 sweep is invalidated by the pinning fix (it measured a different system).
- **`fit_mmpp.py` λ_q is too low** for a 120 s bench window — either regenerate with real capture or introduce an `--artificial-busy` override for repeatable bench timings.
- `lat_*` + mockex pinning code (commit chain `c0488b7 … fe9134d`) is confirmed effective — keep it in place.
