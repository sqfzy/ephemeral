## 决策 1 — TLS encrypt record-by-record API 重写：**推迟**

### 候选方案

| 方案 | 说明 | 工作量 |
|------|------|-------|
| **A （当前）fail-fast latch** | `tls_corrupt_` bool 在任何 partial-send 失败时 set；后续 send/recv 返回 `Disconnected`，调用方 reconnect | 已完成（`bd1e7ce`, ~150 行 + 6 tests） |
| **B streaming callback API** | `TlsState::encrypt_stream(plaintext, send_cb)` 内部按 record 切分，每 record 编完立刻 send；失败就停，`seq_` 只推进已成功发出去的数量 | 4-8 h（3 模块 × 2 backends）|
| **C iterator / generator API** | `TlsEncryptIter::next(record_out)` 每次 encrypt 一条 record；调用方决定是否继续 | 同 B 规模 |
| **D 彻底不管** | 撤回 fail-fast latch，partial-send 静默 corrupt 让 peer AEAD 永久失败 | — |

### 决策

**保留 A（已实装），推迟 B/C**。D 不予考虑（与本次 sweep 的核心目的相悖）。

### 理由

- **A 已覆盖"静默损坏"最严重 failure mode**：`tls_corrupt_` latch 保证任何 desync 立即转成可观察的 `Disconnected`，调用方必然感知
- **B/C 的工作量 vs 回报不划算**：
  - 接口改动跨 `eph-net` / `eph-net-dpdk` / `eph-net-kernel` 三个模块（`TlsEncryptor` 在 eph-net，kernel backend 也用）
  - 需要把 `TlsEncryptor::encrypt()` 改成事务化（当前 `seq_` 先 `++` 再 `EVP_AEAD_seal`；要做 rollback 语义）
  - 级联要改 `TlsDpdkWsSink::send`、`KernelTcpStream` 的对等实现、所有 TLS 测试
- **实际影响面小**：
  - `TcpSession::send` 返回 0 或 error 只在 TCP TX queue 满 / `Disconnected` 两种 case 触发
  - HFT colo 场景下 TX queue 满基本等价"NIC 或 peer 已经有更大问题"，这时 stream corrupt 也不是主要矛盾
  - 所有现有调用点都走 `ReconnectPolicy`，重连代价 <100 ms
- **先做 A 不阻塞 B**：如果后续真有调用方不能容忍 `Disconnected`，扩展到 B 只是在 A 基础上改接口，没有撤销成本

### 代价与权衡

- **接受每次 partial-send 触发一次 reconnect**（TCP handshake + TLS handshake 约 10-50 ms，取决于服务器距离）
- **诊断负担轻微提升**：运维看 metrics 时要区分 `kSendFailures`（一过性）vs `kTlsSendDesyncs`（触发 latch 的那次）；已通过新增 enum + counter 暴露
- **B 方案的零拷贝效率**尚未验证（aws-lc `EVP_AEAD_CTX_seal_scatter` 一次一条 vs 批量；直觉没差但没测）

### 后续影响

- Public API 增补 `is_tls_send_desynced()` 只读 diagnostic；向后兼容
- `StreamMetric::kTlsSendDesyncs` 新 enum 项，`publish_metrics` 映射已更新
- `eph-net-kernel` 对等路径**尚未**实装同样 latch —— **隐式 TODO**，但同样按 A 的优先级处理

### 何时重新评估

- 有调用方报告"我不能容忍 Disconnected"（具体业务场景，比如某市场数据源断线重连成本过高）
- `kTlsSendDesyncs` 的 prod metrics 观察到异常频率（>0.1%/h），说明 partial-send 比预期常见
- TLS 1.4 / QUIC 迁移等大重构，顺带重写该 API 合算

## 决策 2 — Proxy invalid 覆盖：**不做**

### 候选方案

| 方案 | 说明 | 工作量 |
|------|------|-------|
| **A （当前）DPDK 硬拒 + 测** | `cfg.proxy.has_value()` → `InvalidConfig`；已有 `CreateFailsInvalidConfigNotBlockerSentinel` 类似测试覆盖 | 已完成 |
| **B 在 DPDK 侧补 proxy 协议错误测试** | 模拟 `407 Proxy-Auth-Required` / `403 Forbidden` / 挂起 / 超时响应 | — |
| **C 在 kernel backend 补 proxy 协议错误测试** | kernel 是真实支持 proxy 的 backend，补协议错误覆盖 | 4-6 h（含 mock proxy server） |

### 决策

**A 保持现状；B 不做；C 不在本次 scope，留给 kernel backend 独立工作**。

### 理由

- **DPDK 根本不支持 proxy**（`tcp_stream.hpp:464-473` 是 `Error::InvalidConfig` 硬拒），"proxy 协议错误"在 DPDK 语境下是**空集**
- **B 对 DPDK 来说是测一个永远不会走到的路径**，纯浪费
- **C 是 kernel backend 的职责**：`eph-net-kernel/include/eph/net/kernel/tcp_stream.hpp` 才是真正实装 HTTP CONNECT 的地方；应当由 kernel backend 的独立 review / test pass 覆盖，不在 "eph-net-dpdk review" 这个 scope 里
- 本次 `/pax --loop` 的连带 scope 允许改 eph-net，但**无 DPDK 路径的 kernel-only 工作不算连带**（A3 假设：连带必须源自 dpdk review）

### 代价与权衡

- **kernel backend 的 proxy 协议错误路径欠测** —— 接受这个现状直到有明确 kernel review 任务
- 若 DPDK 未来真要支持 proxy（不在 roadmap），本决策反转成"需要补"

### 后续影响

- 无架构影响
- Kernel backend 的覆盖缺口登记为**独立 TODO**，不在 `eph-net-dpdk/CHANGELOG.md` 的 Deferred 列表里

### 何时重新评估

- DPDK backend 的 proxy 支持进 roadmap（目前明确写"HFT colo 不用 proxy"，.artifacts/phase-9-scope-decision.md 锁定）
- Kernel backend 做独立 review pass，把 proxy 协议错误覆盖作为那个 scope 的一部分

## 决策 3 — WS handshake timeout 测试：**可做（下次顺手）**

### 候选方案

| 方案 | 说明 | 工作量 |
|------|------|-------|
| **A （当前）不测，信赖同步错误返回** | `perform_ws_handshake` 超时返回 error，调用方立即知道；依赖 code review 保证正确 | 现状 |
| **B 用 fake sink 模拟 recv() 一直 WouldBlock** | 在现有 `tests/integration/ws_handshake.hpp` 基础上加 mock sink，强制 `recv` 返回 `WouldBlock` 直到 `ws_timeout` 到；验证 `create()` 返回 `Timeout` / `Disconnected` 且不卡死 | 2-3 h |
| **C 用真实 socket 连到立刻 close 的端口** | 起一个 listen-but-no-response 的 TCP server，验证 WS 握手 timeout 路径 | 4-5 h（e2e 脚手架） |

### 决策

**推荐 B**，等下一次 `/pax --test --auto` 顺手做；单独跑一个迷你 pax 也可以。不阻塞 main merge。

### 理由

- **手头既有基础设施充足**：`eph-net-dpdk/tests/integration/ws_handshake.hpp` 已有 WS mock 相关结构，扩展代价可控
- **covers 真实生产场景**：exchange 升级窗口 / 网络分区时 WS server 可能不回 101 Switching Protocols；timeout 路径如果 regression，没有测试兜住就进 prod
- **B 比 C 轻**：纯 mock 不要 NIC_B 环境
- **不紧急的原因**：
  - `ws_timeout` 默认值存在且已在 `create()` validate 阶段拒绝非法值（`tcp_stream.hpp:430-438`）
  - 手写实现的 `perform_ws_handshake` 有 deadline 检查，regression 可能性低但非零
  - 同步错误返回（vs TLS partial-send 的静默 corrupt），调用方立即知道

### 代价与权衡

- **现状下有 regression 风险但无测试兜**（假如有人改 `perform_ws_handshake` 的 deadline 逻辑）
- **补 3-5 个 gtest case** 增加 build time 可忽略
- Mock sink 的复杂度：需要模拟 `TcpSession::poll_rx` 的 WouldBlock 返回；已有 `PlainDpdkWsSink` / `TlsDpdkWsSink` 参考

### 后续影响

- 新增 1 个 test file 或扩展现有 `test_dpdk_ws_handshake.cpp`（如果存在）
- 若抽象成 reusable mock sink，kernel backend 可共享

### 何时重新评估

- **立即可做**：下次 `/pax --test --auto` 或独立任务
- 若 production 观察到 WS timeout 相关 bug → 立即提级

## 决策 4 — TLS cert 校验覆盖：**推迟**

### 候选方案

| 方案 | 说明 | 工作量 |
|------|------|-------|
| **A （当前）只有 BLOCKER 哨兵测试** | `test_dpdk_tls_handshake.cpp:49-75` 只验证 "编译 + `InvalidConfig` 在 TLS 之前触发"；不走实际 aws-lc | 现状 |
| **B mock TLS Server + gtest unit** | 起 TLS echo server（self-signed），cfg 不信任该 CA，验证 `TlsState::handshake` 返回 `TlsHandshakeFailed` | 1 天（需要 TLS server 脚手架 + NIC_B） |
| **C 跑 integration（真实 NIC + tests/integration/dpdk_e2e）** | 把 TLS cert 负路径纳入 `test_dpdk_e2e` 套件；需要 NIC_B + vfio-pci | 同 B 规模 |

### 决策

**A 保持，推迟 B/C**。

### 理由

- **TLS cert 错误 99% 是部署配置错误**（cert path 写错、CA 没装、hostname mismatch），不是运行时 bug
- **同步错误返回**：`create()` 直接返回 `TlsHandshakeFailed`，调用方**部署期间就能发现**，不可能撞到 prod
- **测试基建代价大**：
  - 需要 NIC_B 绑 `vfio-pci`（已有基础设施，但只在手动 e2e 环节启用）
  - 需要真实 TLS echo server (self-signed cert + 可配置信任/不信任)
  - DPDK TLS 握手走 `TcpSession::poll_rx` 拿真实 NIC 包，纯 `--no-pci` gtest 跑不起来
- **本次 sweep 的 Out-of-scope 已锁定"无 NIC_B 环境不跑 e2e"**（A6 假设）
- 相对于其它 deferred items，TLS cert 的 bug 严重程度最低（配置错误 vs 正确性 / 安全 / 静默损坏）

### 代价与权衡

- **TLS cert 校验的 regression 如果真发生**（比如 aws-lc 升级改了 verify callback 语义），本地测试不会发现；但 deployment smoke test + 手动 integration 仍会抓到
- **测试债**堆积到 integration 层；长期看如果 integration 层也不补，就真的盲
- 现行 `BLOCKER sentinel` 模式保护了"测试不会意外走真 TLS" 的契约，但同时也意味着该路径的 regression 不被 CI 检测

### 后续影响

- 无架构影响
- Integration test 脚手架的"TLS echo server"是一个共享基建，若做了也惠及 kernel backend

### 何时重新评估

- NIC_B + vfio-pci + real TLS server e2e 基建就位（目前仅手动 `lat` / `dpdk_e2e` 跑）
- aws-lc 升级到新 major 版本，触发"重要协议路径要重测"
- 出现 prod TLS cert 相关事故（目前无案例）
