## TL;DR

DPDK client wins p50 RTT by **11–16%** across the 5 echo scenarios (`tcp` 24.5→20.8 µs, `udp` 24.7→21.1 µs, `ws` 25.7→22.8 µs, `ex_order` 25.0→21.0 µs, `ex_md_udp` 23.7→20.4 µs). Tail latency benefits are larger: DPDK p99 stays within ~35% of p50, kernel p99 jumps 2–3× (scheduler / soft-IRQ jitter). Two push scenarios (`ex_market`, `ex_market_2p`) needed a longer window (120 s) and `ex_market_2p` additionally exposed a **fixture / client protocol mismatch** — trade-stream payloads fed into a `BookTicker::from()` parser → 100 % `malformed` → 0 samples on both backends. Fixed in-session by regenerating the fixture as synthetic bookTicker. Post-fix both backends produce data; DPDK wins p50 by 2.3× (21.5 µs vs 49.2 µs) on that scenario due to a separate RX-timestamping asymmetry discussed below.

## 假设（Hypothesis）

H1 (primary): **For every one of the 7 lat scenarios, the DPDK client backend achieves lower p50 RTT (or one-way latency, for push scenarios) than the kernel client backend against the same kernel mock, on the same physical path (ens35 → AWS VPC → ens34).**

- Falsification: any scenario where kernel p50 ≤ DPDK p50 disproves H1.
- No magnitude threshold specified — this is a ranking hypothesis. A secondary interest is magnitude: prior project memory (`feedback_aarch64_btb_indirect_branch.md`) flags that "3–5 ns x86 perf intuitions don't hold on Graviton"; this run is also a sanity check of DPDK's headline delta on aarch64 against a commodity AWS ENA NIC.

H2 (secondary, implicit): **All 7 scenarios produce meaningful sample data in a single test pass.** — Falsified for `ex_market_2p` (root-caused below) and partially falsified for `ex_market` / `ex_market_2p` at the 30 s default window (MMPP-2 quiet-state artifact, resolved by 120 s window).

### 测量方式

- One-way (`ex_market`, `ex_market_2p`): `bench::monotonic_raw_ns()` at RX on client minus `"T"` field stamped at send by mockex `PayloadPool::stamp_and_next`. Both sides use `CLOCK_MONOTONIC_RAW` per the CLAUDE-note bench exception to the TSC-everywhere rule.
- Echo RTT (all others): client TSC pair (send→receive), server-side `work_ns = 200` in-kernel spin on mockex subtracted implicitly by the RTT being round-trip.
- Aggregation: `eph::utils::Recorder::record_ns` — produces min / p50 / p90 / p99 / p99.9 / max / avg / stddev (stddev only on a subset). Buckets are exact (no HdrHistogram rounding for the numbers in this report).
- Duration:
  - Echo: `duration_seconds = 30` (overrides bench.conf default of 300 s via `/tmp/bench-30s.conf`)
  - Push: `duration_seconds = 120` (`/tmp/bench-push-120s.conf` — needed because MMPP-2 at `seed = 42` starts in quiet state `λ_q ≈ 2.7 Hz`; at 30 s, burst transitions were not observed on 1st invocation)
- Sample count per run (see §Data) ranges from ≈0.84 M to ≈1.43 M for echo scenarios, giving tight confidence intervals on all reported percentiles.

```bash

    benchmarks/latency/bench.conf > /tmp/bench-30s.conf
# Push scenarios: start from 30s config then bump two sections to 120s

import re, pathlib

# Echo scenarios
for s in tcp udp ws ex_order ex_md_udp; do
  sudo ./benchmarks/latency/lat "$s"         --config /tmp/bench-30s.conf
  sudo ./benchmarks/latency/lat "$s" --dpdk  --config /tmp/bench-30s.conf
done

# Push scenarios (120s each)
for s in ex_market ex_market_2p; do
  sudo ./benchmarks/latency/lat "$s"         --config /tmp/bench-push-120s.conf
  sudo ./benchmarks/latency/lat "$s" --dpdk  --config /tmp/bench-push-120s.conf
done

# Between backends the lat wrapper handles NIC_B state transitions
# (host ↔ bench_ns ↔ vfio-pci) idempotently. After the sweep, return to host:
sudo ip netns exec bench_ns ip link set ens35 netns 1
sudo ip netns del bench_ns
sudo ip link set ens35 up     # DHCP lease comes back on ens35 automatically
```

## 分析

### 统计显著性

- Echo scenarios: sample counts are 0.84 M – 1.43 M per run. At this size, differences of ~3.6 µs in p50 between kernel (24.7) and DPDK (21.1) are vastly above any plausible confidence-interval width on a 30 s single-trial run. **Not formally CI-checked** — this is one run per pair, not a replicated A/B. Project memory `feedback_aarch64_btb_indirect_branch.md` warns against extrapolating x86 micro-benchmark intuitions to Graviton; here the deltas are an order of magnitude larger than that concern, so ranking H1 is safe even without replication.
- Push scenarios: `ex_market` has only 2,142 samples on a 120 s window — too sparse for p99 to be reliable (see §Limitations). `ex_market_2p` (post-fix) has 210 k / 250 k which is fine.
- No replication across seeds (`mockex_seed = 42` fixed). Single-trial results; robust replication deferred to future work.

### 结果解读

**H1 (ranking) — ✅ holds for 5/7 scenarios cleanly.** For the echo five, DPDK p50 < kernel p50 by 11–16 %. Same ordering on p99 and p99.9, with far larger relative gains in the tail (kernel p99 jumps to ~68–78 µs while DPDK p99 stays ≤ 31 µs on most; the two exceptions are `ex_md_udp` kernel p99 = 70 µs vs DPDK 28 µs; and `ex_order` where p99 is dominated by mock-side echo server and is similar across backends).

**H1 on push scenarios**: DPDK also wins p50 on both push scenarios post-fix. Magnitudes (kernel 34 → DPDK 9.1 µs for `ex_market`; kernel 49 → DPDK 21.5 µs for `ex_market_2p`) are **larger** than the echo pattern would predict — because the one-way latency measurement exposes the **RX-timestamp asymmetry** (see Attribution below), not just the DPDK fast-path win. Conclusion: the push numbers validate H1 directionally but shouldn't be compared to the echo deltas without caveat.

**H2 (all scenarios produce data)**: **❌ falsified initially** — `ex_market_2p` returned 0 samples on both backends. Root-caused + fixed mid-session; post-fix H2 holds.

### 归因 (Attribution)

1. **p50 echo win (~15 %)**: consistent with DPDK bypassing syscall + NAPI + socket-buffer scheduling. Not surprising, but the magnitude is lower than x86 baseline numbers in older project artifacts (e.g. `bench-20260328-053255.md` reported 11.6× DPDK RX on synthetic x86 benches); this run measures user-visible RTT including the kernel mock server's ~200 ns work spin, so "kernel at both endpoints" dominates the RTT floor for both backends. The DPDK-saved work is the client-side syscall path only — that bounds the observable delta.

2. **Kernel tail blowup at p90–p99**: rows `udp / ws / ex_md_udp` show kernel p99 ≈ 70–78 µs with p50 ≈ 25 µs. DPDK same scenarios: p99 ≈ 29–31 µs. Attribution: NAPI softirq batching + process scheduling on CPU 4 intermittently stalls the recv() return. DPDK PMD busy-polls from lcore 0, no such tail. This matches the canonical DPDK-vs-kernel tail pattern.

3. **`ex_market` DPDK p99 = 36,355,064 ns (36 ms) — an artifact, not real tail**: at `λ_q = 2.7 Hz` quiet state, the inter-arrival between two frames can exceed 30 seconds (exponential with mean 370 ms, tail reaches seconds). Only 2,142 samples in 120 s means **average arrival rate ≈ 18/s** — the sampler barely left quiet state. The one-way latency calculation is `t_RX - t_send`, both monotonic_raw_ns. Within a burst, this is the real network latency. Between bursts, nothing distorts the measurement directly — but the p99 value of 36 ms is consistent with a specific stall pattern I haven't fully characterised (could be buffered PMD poll cycle + some queuing effect during burst reentry). **Flagged as suspicious, not to be cited as a DPDK weakness.** Kernel side didn't exhibit it — possibly because kernel syscall path drains RX buffer on every recvmsg. Needs a dedicated experiment to rule out measurement vs. real.

4. **`ex_market_2p` kernel p50 = 49 µs ≫ echo p50**: the two-phase path pays deferred-parse cost per poll loop iteration (`eph::json::parse + BookTicker::from` per active slot), which competes with read() for CPU 4's attention. DPDK p50 = 21.5 µs shows the deferred-parse cost is mostly masked by the DPDK busy-poll architecture that keeps PMD RX cache-hot.

### Finding: `ex_market_2p` fixture / client protocol mismatch (resolved in-session)

Full reproduction chain:

```
1. Run: lat_ex_market_2p emits "samples: 0 (no data recorded)", skip_ratio=100%.
2. stderr: "skipped 176116 malformed + 0 clock-skew + 0 slot-overflow samples"
3. total_frames=339574, parsed_frames=0, active_slots=5   ← phase-1 symbol_hash worked
                                                            phase-2 parse failed 100%
4. Inspect benchmarks/mockex/fixtures/ex_market_2p_sample.jsonl head:
     {"e":"trade","E":...,"s":"BTCUSDT","t":...,"p":"75378.45","q":"0.00007",
      "T":0000001776414891880,"m":true,"M":true}
5. Inspect lat_ex_market_2p.cpp:173,228 — calls ej::binance::BookTicker::from(json).
6. Inspect eph-json/include/eph/json/adapters/binance.hpp:156–183:
     BookTicker::from() requires fields {s, b, B, a, A}. Trade stream has
     s but no b/B/a/A → returns nullopt → malformed++.
7. The fixture header comment itself says:
     "real combined multi-symbol capture requires a capture_binance.py upgrade
      to use /stream?streams=... — a follow-up. For now the post-process
      rotation gives realistic payload shape ..."
   — i.e. the mismatch is known, pending a capture-tool upgrade that never landed.
8. lat_ex_market uses the same fixture family but does NOT call BookTicker::from
   (only scans "T" for timing) — which is why that scenario works unchanged.
```

**Fix applied** (this session, NOT committed — left for user to stage):

```
benchmarks/mockex/fixtures/ex_market_2p_sample.jsonl
  regenerated 500 payload lines as synthetic bookTicker derived from the same
  trade capture:
    before : {"e":"trade", "E":…, "s":…, "t":…, "p":…, "q":…, "T":…, "m":…, "M":…}
    after  : {"u":<t>, "s":…, "b":"<p-0.01>", "B":<q>, "a":"<p+0.01>", "A":<q>, "T":…}
  preserved: 5 symbol × 100 line round-robin, T-field width = 19 digits
             (PayloadPool::load_from_jsonl requires ≥ 19), total line count 500
```

**Why fixture and not client?** `lat_ex_market_2p` exists specifically to benchmark "naïve per-frame parse" vs "two-phase deferred parse" cost. Removing the `BookTicker::from` path from the client would defeat the experiment.

**Verification**:

```
xmake run test_mockex_payload_pool                          → 6/6 passed
xmake run test_mockex_push_scenarios --gtest_filter=…2p… → 1/1 passed
post-fix kernel lat_ex_market_2p : samples=209,799, skip_ratio=37.92%, malformed=0
post-fix dpdk   lat_ex_market_2p : samples=250,044, skip_ratio=26.07%, malformed=0
```

`skip_ratio ≠ 0` after fix is by design: in twophase mode, repeated same-symbol frames coalesce into one slot and only produce a single parse event on the next poll-loop iteration; that's the whole point. Separating "skip_ratio" (design) from "malformed" (bug) in the output report is a stats-UX problem worth filing separately.

## 结论

- **H1 (DPDK ≤ kernel p50 RTT on every scenario)**: ✅ **holds** across all 7 scenarios. Magnitude 11–16 % on echo; larger but not directly comparable on push (different timing method). No scenario observed kernel ≤ DPDK.
- **H2 (all 7 scenarios emit data)**: ❌ initially falsified by `ex_market_2p` fixture bug, ✅ re-established after regenerating the fixture.

---

## 边界条件 / 局限

1. **Single trial per (scenario, backend) pair**. No seed variation, no time-of-day variation, no multi-host. A replicated run with varying seeds and separated by ≥ hours is needed to establish CIs around p50 deltas.
2. **30 s / 120 s are short windows** vs the 300 s default in `bench.conf`. Echo scenarios produced >800 k samples so percentiles up to p99 are well-estimated, but p99.9 and max on 30 s runs are dominated by 1–2 outlier events per run — don't cite them.
3. **`mock_work_ns = 200` floor** on every echo RTT is a non-zero mock-side spin. Real kernel processing + mock spin + wire ≈ 10 µs floor independent of client backend. The DPDK advantage over kernel is the difference between the client-side halves.
4. **Single RX queue, no RSS, no FlowDirector**. `bench.conf` has `NB_RX_QUEUES = 1, ENABLE_RSS = false`. A multi-queue run is a separate experiment (referenced in `review-rss-eph-net-dpdk-20260421-052500.md`).
5. **`ex_market` DPDK p99 = 36 ms not explained** — flagged as measurement artifact, not cited as a DPDK weakness. Sparse sampling (2142 / 120 s ≈ 18 Hz) also means all its percentiles are noisy.
6. **`ex_market_2p` post-fix numbers are against a **synthetic** fixture** (bid/ask fabricated from trade price ± 0.01, qty mirrored). The parse cost and overall shape are representative of bookTicker wire format but not of real-exchange bid/ask distributions.
7. **Graviton-specific** per project memory. Indirect-branch penalty small on this CPU; numbers for x86 hosts will differ qualitatively on the tail.

## 对决策的影响

- Ongoing DPDK vs kernel comparisons should treat **DPDK as the low-jitter baseline** and use kernel numbers only as a reference for what the OS-path tail looks like. The p50 delta (≤ 20 %) is less dramatic than the tail delta (2–3×).
- The `ex_market_2p` fixture fix should be **committed as its own patch**:
  ```
  fix(bench): regenerate ex_market_2p fixture as synthetic bookTicker
  ```
  with a note pointing to this experiment report and the `capture_binance.py`
  multi-symbol-stream follow-up as the eventual proper fix.
- The `ex_market` DPDK p99 anomaly should be tracked as a separate issue (`/report issue` candidate) before the next DPDK perf tuning cycle.
- The `skip_ratio` vs `malformed` naming conflation in `lat_ex_market_2p` output is a small stats-UX issue worth a drive-by patch.
