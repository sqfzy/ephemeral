# Decision: lat_ws DPDK p99 稳定性 — mlockall 是当前 host 配置下的最优解

**时间**：2026-05-02 06:35
**Mode**：decision（已决，ADR-style）
**Commits**：`60b1beed` lock_memory helper · `a19b5e0a` bench 接入 mlockall
**触发**：`/pax --auto 稳定 dpdk p99，减少波动。以 lat_ws 为例` 完成后留存
**Host 上下文**：c7g.4xlarge AWS Nitro · aarch64 Graviton · 16 cpu · Amazon Linux 2023 · kernel 6.1 · 默认 irqbalance + CFS · **非 NOHZ_FULL，非 isolcpus**

---

## TL;DR

为降低 lat_ws DPDK 的 RTT 分布尾部波动，对 5 类 host-tuning 介入做了 6 轮实测 bisect。**结论：仅 `mlockall(MCL_CURRENT|MCL_FUTURE)` 单独应用于 lat client + mockex 两端**：TX max 7400k → 3000k ns、TX stddev 15500 → 3700（4×）、跨次 spread 从 10-16× 收紧到 1.5×；p50 / p99 不动。**SCHED_FIFO + relaxed RT throttling + IRQ steering 任意组合都把 TX 尖峰换成 25-50ms 的 RX 尖峰**——根因是内核 softirq wake 路径被 RT 任务饿死。当前 host 配置下 p99 ≈ 28µs / p99.9 ≈ 35µs 是 floor；进一步压低需 NOHZ_FULL + isolcpus（要 reboot）。

## 背景（Context）

### 名词与读者前置

- **lat_ws**：`benchmarks/latency/ws/lat_ws.cpp` — WebSocket-over-TLS RTT 测量二进制；有 `lat_ws`（kernel 客户端）和 `lat_ws_dpdk`（DPDK 客户端）两个 build；服务端永远是 kernel `mockex --scenario ws`。
- **DPDK / mockex 拓扑**：客户端用 vfio-pci 接管 ens35 直接打 NIC；mockex 跑在 host kernel TCP 栈上 ens34。完全过物理 NIC + AWS VPC，无 loopback（详见仓库 MEMORY 中 `feedback_bench_no_loopback`）。
- **mlockall**：POSIX 系统调用，把进程整个地址空间锁进 RAM，禁止 demand paging / swap。
- **SCHED_FIFO**：Linux 实时调度类，FIFO 优先级 ≥ 1 的线程抢占任何 CFS 任务。
- **rt_throttle**：`/proc/sys/kernel/sched_rt_runtime_us` 默认 950000 / 1000000 = RT 任务上限 95% wall-clock，剩 5%（即 50ms / 秒）强制让给非 RT。设 `-1` 完全关闭。
- **softirq wake 路径**：kernel TCP 收到包 → 软中断上下文 enqueue 到 socket buffer → 唤醒 blocking `read()`。整条链跑在 softirq / kworker 线程，CFS 调度。
- **NOHZ_FULL + isolcpus**：kernel cmdline 选项；前者关闭指定 CPU 的周期 timer tick，后者把 CPU 从 CFS 调度器域里摘掉。两者一起用基本消除内核对该 CPU 的所有非自愿打扰。需 reboot。
- **cpu_client / cpu_mock**：bench config（`config.toml [cpu]`）里指定的客户端 / 服务端 pin 的 CPU id；本机 = `4` / `6`。

### 问题陈述

用户报告：lat_ws --dpdk 的 RTT 分布尾部不稳——p99 跨次差 < 1%（早就稳定），但 stddev 在不同 60s 跑之间从 1.7k 漂到 27k（16× 差），max 从 1ms 漂到 11ms（10× 差）。p50 已经稳在 22µs，**不是绝对延迟问题，是分布尾部 + 跨次重复性问题**。

### 约束

- ✗ 不允许重启 host：NOHZ_FULL + isolcpus 需 kernel cmdline 改 + reboot，超出本次 plan 范围
- ✗ 不允许改 DPDK 协议栈热路径：那属于 `/pax --reshape`，不是 `--bench --optimize`
- ✓ 改动需对称：lat client（DPDK 100% busy-poll）和 mockex（kernel TCP, blocking I/O）调度模型完全不同，但两端 jitter 都计入 RTT，要么都改要么都不改
- ✓ 共享 dev host：不能假设独占机器，不能改全局策略不可逆

### 关键假设（验证后确认）

| 假设 | 验证方式 | 结论 |
|---|---|---|
| aarch64 kernel 6.x 的 `clock_gettime(CLOCK_MONOTONIC_RAW)` 走 vDSO（≈30ns），不是变异源 | 对照 baseline RX max 117k = 时基开销不放大 | ✓ |
| 主要变异源在 client + mockex 测量线程，不是网络 / VPC | R6 RX max 106k 接近 baseline 117k → 网络稳定 | ✓ |
| 用户的"稳定 p99 减少波动"= 收敛 stddev / max / 跨次重复性，不是降中位 | 用户在事后 follow-up 中确认改善的是后者 | ✓（事后） |

### baseline 数据（3 × 60s）

| 指标 | run #1 | run #2 | run #3 | 跨次 spread |
|---|---|---|---|---|
| RTT p50 | 22455 | 22391 | 22231 | 1% |
| RTT p99 | 28279 | 28455 | 27863 | 1% |
| RTT max | 11M | 10M | 1M | **10×** |
| TX max | 11M | 10M | 1M | **10×** |
| TX stddev | 27331 | 17471 | 1759 | **16×** |
| RX max | 117k | 117k | 596k | 5× |

诊断：变异源全在 TX side（TX max 与 RTT max 共动），跨次差 ≫ 单次内 spread → 偶发 ms 级 spike 主导分布尾部。典型嫌疑：page fault / scheduler preempt / IRQ。

## 候选方案

5 类介入，6 轮实测：

```
       配置                              TX max         RX max         TX stddev      throughput
       ────────────────────────────────  ─────────      ─────────      ─────────      ──────────
base   nothing                           1-11M (10×)    117-596k       1.7k-27k(16×)  43-44k/s
R1     mlock + FIFO50 + rt=-1            130-150k       24-39M         1.2k-2.0k       43-44k/s
R2-a   R1 + IRQ steer (regex bug)        100-228k       22-26M         1.6k-2.0k       25-44k/s   ← 间歇 bimodal
R2-b   R2-a + 修正 regex 抓全 ENA queues 70-790k        3.3M-25M       1.4k-3.2k       28-44k/s   ← bimodal 偶发
R3     R2-b + irqbalance stop            141-671k       23-27M         1.3k-2.0k       43-44k/s
R4     R3 with mock CFS (drop FIFO)      1.7M-3.8M      41-50M         3.0k-4.7k       43-44k/s
R5     R4 + mock FIFO + rt=999000        712k-790k      10.7M          1.8k-9.9k       41-44k/s
R6     仅 mlockall 两端                  2.4M-4.0M      104-107k       3.0k-4.6k       43-44k/s   ✓ winner
```

下面按"曾考虑过的方案"逐一记录决策与 reject 理由：

### 方案 A — `mlockall` 两端（最终选）

**摘要**：`pin_client_from_cfg` 与 `mockex::pin_to_cpu` 在 pin 完成后追加调用 `eph::utils::lock_memory(MCL_CURRENT|MCL_FUTURE)`，把整个进程地址空间锁入 RAM。

**优势**：
- 直接消除 page-fault 类尖峰（baseline 11ms TX 尖峰的根因）
- 零副作用：无新失败模式，不动调度器，不动 IRQ 路由
- 失败 graceful：缺 CAP_IPC_LOCK 时 WARN + 继续，bench 仍跑（数字稍噪）
- 成本低：单 syscall + 帧锁定，Resident Set 增加几十 MB（无所谓）
- helper 通用：`eph::utils::lock_memory` 进 utils 后任何 HFT 路径都能复用

**劣势**：
- 剩 ~3M 量级 TX 尖峰未消除（kernel timer / softirq 延迟 work batch），需 NOHZ_FULL + isolcpus 才能压低
- 不动 p99 / p99.9 中位（该指标 baseline 早已稳定，不是问题）

**适用条件**：任何 `ulimit -l unlimited` 的 host；DPDK 路径已经 sudo，权限不是问题。

### 方案 B — `mlockall` + 两端 `SCHED_FIFO 50` + `rt_runtime_us = -1`（R1，reject）

**摘要**：除 mlockall 外，把客户端和 mockex 都升到 FIFO 50；为防 50ms RT throttle，把 `kernel.sched_rt_runtime_us` 设 `-1`（完全关闭节流）。

**实测结果**：TX max 11M → 130-150k（**75× 改善**），TX stddev 27k → 1.4k；**RX max 117k → 24-39M（300× 恶化）**。

**Reject 理由**：根因是 `rt_runtime_us = -1` + `mockex SCHED_FIFO 50` 的组合**饿死了 kernel softirq / kworker**。mockex 的 blocking `read()` wake 走 softirq 上下文，softirq 在 CFS 调度，被全局 RT 任务无限期推迟 → wake latency 从 µs 跳到 ms 级。技术上 RT 改造按教科书是对的，但在 dev host 共享场景下**把一类尖峰换成更大的另一类**。

### 方案 C — 方案 B + `irq_steer.sh` 把 ENA / NVMe IRQ 移开 cpu 4 / 6（R2，reject）

**摘要**：Bash 脚本枚举 `/proc/irq/<n>/smp_affinity`，把 device IRQ 重写到 mask 排除 cpu_client / cpu_mock。

**关键过程缺陷**：
- 第一版正则 `(ena|...)` **漏掉所有 ENA per-queue IRQs**，因为 NIC 的 IRQ 名是 `ens34-Tx-Rx-N` —— "ens" 不含 "ena"。改成 `ens[0-9]+-Tx-Rx-N` 后从 2 个 IRQ 扩到 10 个 IRQ。
- 又发现 **`irqbalance` 守护进程每 ~10s rebalance**，**回滚我们的 affinity 改动**。必须 `systemctl stop irqbalance`。
- 即便修完两点，R3 RX max 仍 23-27M，与 R1 同量级。

**Reject 理由**：RX 尖峰根因不是 IRQ preempt 而是 softirq starvation（方案 B 已确认）；steering 不能解决根因。脚本本身正确，但**当前 host 用不上**。

### 方案 D — Client FIFO + Mock CFS + IRQ steer + irqbalance off（R4，reject）

**摘要**：假设让 mockex 退回 CFS 后，内核可正常调度其 wakeup。

**实测结果**：RX max 反而恶化到 41-50M。CFS mockex 在 cpu_mock 被任意 CFS 任务 / kworker 抢占的窗口比 FIFO 更长更频繁。

**Reject 理由**：mockex 也需要 RT 优先级压低 wakeup-after-ready 抖动；纯 CFS 不够。

### 方案 E — 方案 D + 两端 FIFO + `rt_runtime_us = 999000`（99.9% RT，0.1% 留 kernel）（R5，reject）

**摘要**：折中，留 1ms / 秒给 kernel softirq batch 完成。

**实测结果**：RX max 收敛到 ~10.7M（与 1ms × 10 = 10ms 量级吻合），但 **p99 / p99.9 反而变差**（28→34µs / 33→47-135µs，跨次不稳）。

**Reject 理由**：1ms breathing room 不够内核完成 wakeup batch；调更高（990000 / 950000）就退化回 baseline 的 50ms throttle preempt。该 knob 在当前 host 上**没有最优解**——任何取值都坏。

### 方案 F（未实测，记录为后续路径）— NOHZ_FULL + isolcpus on cpu 4/6 + 方案 A/B 任选

**为何未实测**：需要 reboot host 改 kernel cmdline，超出本次 plan 范围。

**预期效果**：消除 cpu 4/6 的 arch_timer tick + RCU softirq + scheduler 周期 work，残留的 ~3M TX 尖峰应该归零。

**触发评估的条件**：见"何时重新评估"。

## 决策

**选 方案 A（仅 `mlockall` 两端，其他全部不改）**，落地两个 commit：

- `60b1beed` — `eph::utils::lock_memory(LockMemoryOptions, tag)` 进 `eph-utils/include/eph/utils/cpu.hpp`，含 actionable 错误诊断（EPERM hint 指向 `CAP_IPC_LOCK`；ENOMEM hint 引用当前 `RLIMIT_MEMLOCK` 让 operator 直接知道改哪个 ulimit）。带 `eph-utils/tests/test_lock_memory.cpp` 三例（success / EPERM-actionable / no-op-flags）。
- `a19b5e0a` — `benchmarks/latency/core/pin_client.hpp` + `benchmarks/mockex/src/main.cpp` 在 pin 后 best-effort 调 `lock_memory`；失败 WARN + 继续。

`benchmarks/latency/lat` wrapper 同步加了一段注释块记录此次 bisect 结论，避免后人重做相同实验。

**未保留**的产物：
- `benchmarks/latency/scripts/irq_steer.sh` 曾作为 commit `3b8323d0` 落地，事后讨论时确认"实测 reject + 当前 host 没用 + '未来 NOHZ_FULL 时也许有用'是反模式"，**reset --hard HEAD~1 删除**，附带把 `lat` wrapper 与 CHANGELOG 中的悬空引用 amend 进 `253c2e90`（重 hash 后即 `a19b5e0a`）。

## 理由

按维度权衡：

| 维度 | A (winner) | B (FIFO+rt=-1) | C (B+IRQ steer) | D (Client FIFO+Mock CFS) | E (FIFO+rt=999000) |
|---|---|---|---|---|---|
| TX max 改善 | 2.5× | 75× | 75× | 3× | 14× |
| RX max 影响 | 2.5× ↓ | 300× ↑ | 200× ↑ | 400× ↑ | 91× ↑ |
| 净 RTT max | **2.5× ↓** | 4× ↑ | 3× ↑ | 5× ↑ | 1.5× ↑ |
| 跨次重复性 | 6× ↑ | 改善但 RX 不稳 | 改善但 RX 不稳 | 大幅恶化 | 改善但 p99.9 跨次差 |
| p99 / p99.9 | 持平 | 持平 | 持平 | 持平 | **变差** |
| 副作用 | 无 | 全局 sysctl + 调度器 | 上 + IRQ 全局 + irqbalance off | 上 | 上 |
| 失败 graceful | ✓ | 部分 | 部分 | 部分 | 部分 |
| 文件改动 | 1 helper + 2 调用点 | + sysctl wrapper | + bash 脚本 + irqbalance ctl | 同 C | 同 C |
| 复杂度 | 低 | 中 | 高 | 高 | 高 |

**A 入选的核心论点**：
1. **唯一一个净 RTT max 不退化的方案**——其他四个都在某条尾部加深问题
2. 用户的真实诉求（跨次稳定性）A 已达成（4× stddev 收紧、6× max spread 收紧）
3. 复杂度最低 → 维护成本最低 → 出问题概率最低
4. 可叠加：未来 host 升 NOHZ_FULL 后，A 不需改，只需在 A 之上加 B/C 即可（可演进路径不堵）

**B-E 集体 reject 的根本原因**：DPDK 客户端 100% busy-poll 的工作模型与 kernel mockex blocking-I/O 的工作模型对调度器期望相反——前者想要"我永不让出"，后者想要"内核及时唤醒我"。任何全局 RT 调度策略只能讨好一边。在共享 dev host 上**没有同时满足两边的 sysctl 取值**，bisect 已穷举验证。

## 代价与权衡

诚实清单：

1. **TX max 仍有 ~3M 量级残留**：未达 hard target（理想是 ≤ 100µs）。原因是 kernel arch_timer / RCU softirq 周期 work，需 NOHZ_FULL 才能消除。
2. **p50 / p99 / p99.9 没动**：baseline 已经稳定，不是本次目标，但用户初次看可能误以为"无效果"。已在事后 follow-up 中向用户解释清楚（见会话尾部对话）。
3. **mlockall 增加 RSS**：进程整个地址空间常驻，包括从未访问的 mmap 区。本场景 RSS 增加 < 100MB，可忽略；高内存压力 host 上需复核。
4. **要求 sudo / `ulimit -l unlimited`**：DPDK 已经强制 sudo，所以新增约束实际上是 0；但若有人未来想在非 sudo 下跑 lat_ws 用别的方式，会看到 WARN（已 graceful）。
5. **bisect 知识只在 commit message + 此 ADR 里**：未来 NOHZ_FULL host 上的工程师如果不读这两处，可能重做一次 R1-R5 的失败 bisect。**这份 ADR 的核心存在价值就是预防该浪费**。

## 后续影响

### 对架构

- `eph::utils::lock_memory` 是新公共 API，header-only，无 ABI 影响。
- pin_client 现在三步：`pin_thread → lock_memory → (return)`。任何调用 `pin_client_from_cfg` 的 lat_*/mockex 自动受益。

### 对其他模块

- 其他 `lat_*` 二进制（lat_tcp, lat_udp, lat_ex_*）共享 `pin_client_from_cfg` → 自动获得相同的 page-fault 免疫。已在 lat_tcp --dpdk 短跑验证 mean 不退化。
- `eph-net-dpdk` / `eph-codec` / 其他生产模块**未受影响**——本次只动 utils helper + bench 接入。

### 对团队 / 文档

- `eph-utils/CHANGELOG.md` 与 `benchmarks/latency/CHANGELOG.md` 各加 Unreleased 条目，含数字 + bisect 引用。
- 未来若有人想再优化 lat_ws 尾部，先读此 ADR + 两个 CHANGELOG，避免重复 R1-R5。

### 对 CI / 运维

- 无 CI 改动。bench 仍 sudo + 手跑。
- 运维需注意：`ulimit -l unlimited` 是新软约束。Amazon Linux 2023 默认就是 unlimited，验证过。

## 何时重新评估

下列**任一条件**触发即重看本决策：

1. **Host 升级到 NOHZ_FULL + isolcpus**（kernel cmdline 改 + reboot）：方案 B/C 的 RT 副作用消失，应叠加方案 B（两端 FIFO 50）实测再决定。
2. **mockex 从 kernel TCP 迁到 DPDK**（双 DPDK 拓扑）：消除 softirq starvation 根因，方案 B 应可启用。
3. **用户要求把 p99 压到 < 25µs 或 p99.9 < 30µs**：当前方案不够，必须走 NOHZ_FULL。
4. **lat_ws DPDK 出现新的尾部退化模式**（本决策保护的尾部之外的）：可能引入了新的 spike 类，需重新 profile + bisect。
5. **`eph-net-dpdk` 协议栈热路径有改动**（如换 reasm 实现 / 改 polling 策略）：可能改变本决策的相对收益，需复测 baseline。
6. **超过 12 个月未复测**：硬性提醒——kernel / NIC firmware / EAL 行为可能变化，至少跑一次 baseline 确认结论仍 hold。
