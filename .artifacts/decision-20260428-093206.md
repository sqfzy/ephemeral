## 决策汇总（按主题分组）

### A. 优先级与范围决策（5 项 — 走 review meta-plan + Phase 2.5 拍板）

#### D1 ─ Tier 1 边界：deflate / async DNS / Reconnect orchestrator 三项均成立

**候选**：
- (a) 三项都 T1（推荐）
- (b) Orchestrator 下陷 T2（仅 deflate + async DNS T1）
- (c) 仅 deflate T1

**裁定**：(a) 三项都 T1 — 用户 Phase 2.5 拍板。

**理由**：
- **deflate** 是硬阻塞（Binance/Bybit 主动启用压缩后库无法解码） — R11 怀疑论者初想要 measurement，被 R3 反驳"RFC 7692 是 Binance API 文档明确推荐项；服务器单方面启用的可能性存在，库不支持解压等于无法解析" — R11 让步。
- **async DNS** 是多 venue reconnect 串行化的根（多 venue 同时断链，每家 30ms RTT 串行 = N×30ms 卡顿）。
- **Orchestrator 骨架**是后续 T2 编排的护航点（TLS resume / sub replay / COD 都挂在它的 callback 上）。

**否决理由**：
- (b) — Orchestrator 不引入则每家 venue 重写 200-400 行胶水代码，违反库的 ROI（R7 主张）。
- (c) — DNS 阻塞的代价被低估；R11 后期承认 multi-venue 真实场景 ≥ 12 连接（4 venue × 3 stream）。

#### D2 ─ ReconnectOrchestrator 归属层：eph-net（不新建 eph-venue）

**候选**：
- (a) eph-net（推荐）
- (b) 新模块 eph-venue
- (c) 应用层负责（不进库）

**裁定**：(a) — 用户 Phase 2.5 拍板。

- 放在 eph-net 与 backend 无关，kernel/DPDK 共享。
- (c) 被 R7 反驳："reconnect 编排不是业务策略，是网络生命周期管理；DNS/TLS/WS 握手序列在所有 venue 结构相同"。

**重新评估触发条件**：N ≥ 3 venue 适配器沉淀后 — **现已 N=4（Binance + OKX + Bybit + Coinbase, T2.10 ship 后）**，门槛已过；可重新讨论 `eph-venue` 抽出（未启动）。

#### D4 ─ Tier 内序与并行度：Tier 1 串 → Tier 2 8 并行 → Tier 3 6 并行

**候选**：
- (a) 全 sequential（保险）
- (b) 同 Tier 内非冲突项最大并行（推荐）

#### D5 ─ Reboot 恢复策略：原 worktree resume vs 全部弃用重跑

**触发**：reboot 切断 7 个 T2 agent。worktree 存活但代码未 commit。

**候选**：
- (a) Resume in-place（spawn 新 agent 指向已存在 worktree，只跑 build/test/commit）
- (b) 弃掉 partial work，全部 fresh agent 重跑

**裁定**：(a) Resume in-place — 用户选 "A"。

**实测结果**：5/5 resume 成功；其中 T2.5 first-attempt build clean（agent 代码 100% 有效，纯被切在 commit 前）；T2.8 发现 heap-use-after-free（实际是测试 fixture 销毁顺序 bug，非生产代码问题；resume agent 成功 root-cause + fix）。

**理由**：
- worktree 持久化保证 agent 写入的代码不丢失。
- 重跑同样的 prompt 理论上应该重现工作；但每次 LLM 输出非确定，重跑可能产出不同 design。
- Resume 预算 30 min；实际所有 5 个 < 25 min 总耗时。

### B. ReconnectOrchestrator 设计决策（5 项 — Phase 2.5 拍板 + 实施细化）

#### D6 ─ Ownership 模型：拥有型 + tick-based

**候选**：
- (a) 拥有型 + tick-based（推荐）
- (b) Observer（用户拥 Stream，orch 仅给建议）
- (c) Pollable Wrapper（orch 自己实现 Pollable，隐藏 Stream）

**裁定**：(a) — 用户 Phase 2.5 拍板。

**理由**：
- (b) 不解决 R7 原提出的"每家 venue 重复造轮子"问题（每家仍写自己的 detach → factory → attach 序列）。
- (c) DPDK 下需 wrapping `poll_step_` / `on_pkt_` / `tuple_for_poller_`，4 层间接调用，代价过高。
- (a) 把 detach + factory + attach 三步统一封装；用户主循环只多一行 `tick(now_tsc)`。

**代价**：用户提供 5 个 callback（factory / on_disconnect / on_reconnect / attach / detach）— 但其中 attach/detach 在 DPDK `create_and_attach` 形态下是 no-op，简化路径已 documented。

---

#### D7 ─ Backoff 计时：tick-based（不 sleep）

**候选**：
- (a) Tick-based（推荐）
- (b) Sleep-based
- (c) 两者并存

**裁定**：(a) — 用户 Phase 2.5 拍板。

**理由**：
- DPDK lcore burst-poll 不能 sleep（会拖路）。
- Tick 模型与 poller 1:1 对齐：用户每轮 `poller.poll()` 后调 `orch.tick(TSC::now())`。
- (c) API 面大、语义重叠需文档说明，over-engineering。

---

#### D8 ─ Callback 类型：`std::function`（非模板）

**候选**：
- (a) `std::function`（推荐）
- (b) 模板参数（`ReconnectOrchestrator<S, OnDisc, OnRecon, Factory>`）
- (c) SFINAE 双路径

**裁定**：(a) — 用户 Phase 2.5 拍板。

**理由**：
- Reconnect 非热路径（Binance 24h 一次；OKX 心跳超时偶发）。一次性堆分配（捕获 lambda）~16-32 字节，可忽略。
- 模板参数会让每个实例成为不同类型，调试 / 错误信息体感差。
- libstdc++ 14 不支持 `std::function<R(...) noexcept>` 模板特化 —— 这是施工时实证发现的限制（commit `04299310`），typedef 必须删 noexcept 限定符；callback 实现仍可标 noexcept 单独 lambda。

**代价**：Phase 2.5 拍板时未知此限制。`noexcept` 从公共 typedef 退化为实现-内部约定。已在 header 注释 documented。

---

#### D9 ─ duration_ns 语义：total + last + count（三 metric 并存）

**候选**：
- (a) 累加 total（counter）
- (b) 仅 last（gauge）
- (c) total + last + count（推荐）
- (d) histogram

**裁定**：(c) — 用户 Phase 0.3 WHAT-级澄清拍板。

**理由**：
- (c) 表达力顶；dashboard 可派生 `avg = total / count`，alert 可看 `last`。
- (d) histogram 需引入 HdrHistogram 集成（CLAUDE.md 显式 deferred）。
- (a) 只 total 难看 outlier；(b) 只 last 难看趋势。

**实施 enum**：`ReconnectMetric { kReconnectCount, kReconnectFailures, kReconnectDurationNs, kLastReconnectDurationNs, kSubscribeReplayCount, kCount }` —— 后增加 `kSubscribeReplayCount` (T2.11) 不破坏二进制。

---

#### D10 ─ Metrics 归属：新独立 `ReconnectMetric` enum，**不**侵入 `StreamMetric`

**候选**：
- (a) 扩展 `StreamMetric` enum（在 stream 的 atomics 上加 reconnect 计数）
- (b) 新独立 `ReconnectMetric` + 自有 atomics + 新 `publish_reconnect_metrics` free fn

**裁定**：(b)。

**理由**：
- 每次 reconnect 是**新 Stream 实例**（`stream_.reset() + factory()`），归到 Stream 的 atomics 会被新 stream 清零 → 跨连接统计失效。
- Orchestrator 自有 atomics 跨连接累加；publish 时通过 `MetricTag` 区分 venue。
- 与现有 `publish_metrics<Stream, Sink>` 风格 1:1 对齐。

### C. WS deflate 决策（4 项 — T1.1 实施细化）

#### D11 ─ 库选型：zlib（不引 libdeflate）

**裁定**：zlib。

**理由**：
- zlib 是 universal Linux core dep，aws-lc + zlib 兼容生态成熟。
- libdeflate 在 host 缺，引入新 supply-chain 重量 / 编译时检测 / 文档维护成本。
- Deflate 是 codec 路径，CPU 占比 < 5%（实测）；libdeflate 的速度优势对 crypto WS 流量可忽略。

**代价**：zlib 比 libdeflate 慢 ~30%（对 GZIP），但 raw deflate 差距更小。可接受。

---

#### D12 ─ 非默认 `*_max_window_bits` 参数：fail-closed（不支持非 15）

**候选**：
- (a) 重新初始化 inflater 适配服务端窗口（更兼容）
- (b) 拒绝非 15 值，握手时 fall back 到无压缩（推荐）

**裁定**：(b)。

**理由**：
- Binance / OKX / Bybit 服务端实测都用默认 15。非 15 极少见。
- (a) 风险：解压结果可能与服务端预期不一致 → 数据损坏（silent corruption）。
- (b) 安全可恢复：无压缩仍可工作，不暴露错误的解压输出。

---

#### D13 ─ 出向 deflate（client → server）：不实现

**裁定**：仅入向。

**理由**：crypto venue 不要求 client 压缩；实现等于双倍 codec 复杂度换零收益。

---

#### D14 ─ Decompression bomb cap：复用 `WsCodecConfig::max_message_size`（默认 1 MiB）

**裁定**：硬上限锚定在已有的 `max_message_size`，不引入新配置项。

**理由**：1KB 压缩 → 1GB 解压的攻击 well-known；既有上限已经为 fragmented 帧防护过载，复用同一阈值减少配置面。

### D. async DNS 决策（2 项 — T1.2 实施 + 后续 T3.18 收尾）

#### D15 ─ AsyncDnsResolver 形态：`DpdkPollable` + 模板化 IO shim

**裁定**：`AsyncDnsResolverT<Io = RealNicIo>` 类，`DpdkPollable` concept 全 5 hook 实现；`Io` 模板参数让单测注入 `FakeNicIo` 录制 / 回放。

**理由**：
- 与 Stream / UdpSocket 的 Pollable 模式一致，零运行时开销（编译时模板）。
- `FakeNicIo` 让单测无 EAL 依赖，13 case 全跑（含 4-way 并发解析）。

**保留旧 API**：阻塞 `resolve()` 不重写为 wrapper（保留独立实现 + `expected<…, std::string>` 错误类型），原因：5 个现有 caller（binance_latency / test_dpdk_e2e / mock_dispatcher / echo_mocks）依赖原字符串错误格式 + `steady_clock` 路径。

---

#### D16 ─ 错误类型对齐（T3.18 follow-up）：仅 `resolve()` 改 ErrorInfo，`parse_dns_response` 留 `std::string`

**裁定**：`resolve()` 8 个 return path 迁移到 `expected<uint32_t, ErrorInfo>`；parser 函数（`parse_dns_response` / `try_parse_dns_packet`）保留 `expected<T, std::string>`。

**实证发现**：`binance_latency.cpp` 0 改动 — spdlog 已有 `format_as` ADL hook 自动渲染 `ErrorInfo` 为 `"CODE: detail"`。

### E. 多 NIC 聚合决策（2 项 — T2.12）

#### D17 ─ MultiPortPlatform 形态：聚合器（Option A）vs 单 Platform 多 port_id（Option B）

**候选**：
- (a) `MultiPortPlatform` 聚合器（推荐）
- (b) 扩展 `Platform` 内部持 N 个 port_id（拒绝）

**裁定**：(a)。

**理由**：
- (b) 破坏 `Platform::port_id()` 单值返回的约定 → 无数 caller / 现有测试需要修改 → 大动作 / 高风险。
- (a) 是 thin wrapper，无新生命周期不变量，单 Platform 形态 byte-for-byte 兼容。

#### D18 ─ ICMP 跨端口路由：**不**共享注册表（强制隔离）

**裁定**：每个 per-port `Platform` 自有 ICMP 注册表；`MultiPortPlatform` 不合并。

**理由**：
- 跨端口共享会导致：端口 A 的 ICMP 包路由到端口 B 的 stream → 5-tuple 别名 bug。
- 强制隔离在测试中显式 pin（`IcmpRegistriesNotShared` test）。

**代价**：用户在多 NIC 拓扑下需自己处理 path-MTU 反馈（典型场景 path-MTU 不会跨 NIC，影响极小）。

### F. JWT 签名决策（3 项 — T2.10-FU Coinbase）

#### D19 ─ JWT 模块归属：独立 `jwt_signed_request.hpp`（不扩展 `signed_request.hpp`）

**候选**：
- (a) 独立 `jwt_signed_request.hpp`（推荐）
- (b) 扩展 `signed_request.hpp` 加 ES256 traits

**裁定**：(a)。

**理由**：
- HMAC-SHA256 与 ES256 (ECDSA) 在算法 / API / key 类型 / 签名格式上**完全不同** → 强行共用 traits 会让 traits 接口分裂或重复声明。
- 独立头文件不引入额外依赖（aws-lc 已链）；不 wire 到 traits 接口（避免 cross-pollution）。
- 用户使用方式：`#include` 时按需选 — `signed_request.hpp` 给 Binance/OKX/Bybit；`jwt_signed_request.hpp` 给 Coinbase。

---

#### D20 ─ PEM 加载 API：`PEM_read_bio_PrivateKey`（兼容 PKCS#8 + SEC1）

**候选**：
- (a) `PEM_read_bio_PrivateKey`（unified；推荐）
- (b) `PEM_read_bio_ECPrivateKey`（only SEC1）

**裁定**：(a)。

**理由**：
- Coinbase Cloud 下载的 EC 私钥**默认 PKCS#8 格式**（`BEGIN PRIVATE KEY`）— `PEM_read_bio_ECPrivateKey` 仅认 SEC1（`BEGIN EC PRIVATE KEY`），用 (b) 会 silently fail。
- (a) 自动检测两种格式 + 加 `EVP_PKEY_id == EVP_PKEY_EC` + `EC_GROUP_get_curve_name == NID_X9_62_prime256v1` 的二级校验 → 双重防御。

---

#### D21 ─ DER → IEEE P-1363 签名转换：手写 `ECDSA_SIG_get0` + `BN_bn2binpad`

**裁定**：手写 32+32 字节 r||s 拼接，详细注释字节布局。

**背景**：
- `EVP_DigestSign*` 默认输出 DER ASN.1 编码（`30 46 02 21 00 <r> 02 21 00 <s>`）。
- JWT 标准要求 raw R||S concatenation（IEEE P1363 模式，固定 64 字节）。
- "These two share the same algorithm but different envelope" 是 JWT 实现的经典坑。

**实施**：注释块详细说明字节布局；`BN_bn2binpad(.., 32)` 处理 r 或 s 短于 32 字节（leading zeros）的情况；测试 `SignatureIs64BytesP1363` 显式断言长度。

### G. 实证发现 / 架构性发现（2 项 — 关键文档化）

#### D22 ─ TLS Resumption 在 aws-lc 后端不工作（架构性 SKIP）

**发现**（T2.4-FU 实证）：
- aws-lc 1.71 TLS 1.3 server **不**在 ServerFinished flight 内发 NewSessionTicket。
- NSE 字节只在服务端下一次 `SSL_write`（典型是 WS HTTP 101 响应）才被 flush。
- 控制对照：同样代码链接 OpenSSL 3.2 时 NSE 跟 ServerFinished 同 flight，drain 路径正常工作。

**架构冲突**：
- eph-net kernel TLS 路径在 `tls_state::handshake()` 返回**立即**调 `extract_hot_state()` —— 把 SSL 对象的 AEAD key 抽走 + drop SSL session。
- WS HTTP 101 是 *handshake 之后* 的应用层事件 —— 此时 SSL 已被 drop，`new_session_cb_` 永远没机会被触发。

**裁定**：
- T2.4-FU drain post-handshake records **仍 ship** —— 对 OpenSSL 3.x 后端正确工作 + 作为防御性措施清理 stray records（NSE / KeyUpdate / alerts），near-zero cost。
- 2 个 resumption 测试（CaptureTicketAfterHandshake + RestoreTicketCutsOneRtt）保持 SKIP，从"未实现"升级为"aws-lc-specific architectural limitation"，document 充分。
- `CorruptTicketFallback` 测试**仍 PASS**（验证全链路 d2i / SSL_set_session / `kTlsResumeCount++` 路径），确认 wiring 正确。

**何时重新评估**：
- aws-lc 升级到与 OpenSSL 同步的 NSE flush 行为（监控 aws-lc 上游）。
- 项目从 aws-lc 切到 OpenSSL（重大架构决策，不太可能）。
- 在 `extract_hot_state` 后保留 SSL 对象到 WS upgrade 完成（架构改动 + 内存代价）。

#### D23 ─ DpdkPoller heap corruption 实为测试 fixture 销毁顺序（非生产代码 bug）

**症状**：T2.8 `OverflowAt65thRejected` 测试触发 glibc heap-use-after-free。

**Root cause**（T2.8 resume agent 通过 ASan 定位）：
```
Test fixture 销毁顺序：
  unique_ptr<DpdkPoller> p   (declared first, freed last)
  vector<ScalePollable> arr  (declared second, freed first ← BUG)

→ ~vector frees arr[i] 元素
→ ~DpdkPoller walks entries_[i].detach_fn(obj) → 触发 freed Pollable 的 notify_detached_
```

生产代码完全无此问题：`DpdkTcpStream::~DpdkTcpStream` 在 `attached_to_->remove(this)` 之后才销毁 — order-correct by RAII。

**Fix**：测试的 `ScalePollable` 加 auto-detach 析构（mirror `~DpdkTcpStream` 的 RAII 模式）+ delete copy/move ops。

**教训**：HFT mock 必须 production-faithful；缺少 RAII 行为的 mock 会引发 "测试有 bug 但生产没有" 的诊断歧途。

---

### H. Scope-narrow 决策（2 项 — 显式不做）

#### D24 ─ OKX/Bybit `op:login` helper：不写

**理由**：
- OKX/Bybit 私有频道用 in-band `op:login` 而非 HTTP header HMAC（`SignedRequest<Traits>` 不适用）。
- 一条 `current()->send(login_msg)` 就完，写 helper class 是 over-engineering。
- T2.10 测试覆盖 public path；私有 in-band login 实战时由 venue adapter 自己拼。

**venue cookbook (T3.20) 显式说明**：以一段示例代码 + 反模式提示替代代码 helper。

---

#### D25 ─ T2.11 `subscribe_replay_count`：不要求状态门控

**候选**：
- (a) 仅在 Connected 状态调用 `note_subscribe_replay()` 才 valid（state-gated）
- (b) 任意状态可调（推荐）

**裁定**：(b)。

**理由**：让 caller 可以从 settle-ack handler 等"晚一步"的 callback 里 bump 计数器，而不必与 orchestrator 状态机赛跑。`NoteSubscribeReplayCallableInAnyState` 测试 pin 此契约。

## 代价与权衡

承认未粉饰的代价：

1. **`std::function` typedef 的 noexcept 限定符必须删除**：libstdc++ 14 不支持 `std::function<R(...) noexcept>`；callback 实现仍可标 noexcept lambda，但 typedef 表达力降级。已在 header 注释 documented。

2. **`test_tls_resumption` 永久 SKIP 2 个测试**：直到 aws-lc 行为变化或项目切 OpenSSL 才解锁。当前 wiring 通过 `CorruptTicketFallback` 间接验证。

3. **Crypto venue adapter tests 不 share base class**：4 个 venue adapter test 文件结构 ~80% 重叠。R14 review 决议 "等 N≥3 venue 模板沉淀后再抽" — 现已 N=4，门槛已过；但本次 session 未启动该重构。

4. **DPDK 真机 E2E benchmark 一直 SKIP**：测试环境不足 hugepages / vfio-pci 状态时跳过。本仓 host 实际有 vfio-pci NIC（per CLAUDE.md），但本次 session 未跑真 NIC bench 抓 baseline。

5. **`DpdkPoller` 默认 16-conn 上限保留**：T2.8 把硬上限提到 64，但 default 配置不变（向后兼容）。用户需显式设置 `PollerConfig::max_connections = 64` 才能用满新容量。

6. **eph-net 公共依赖增 eph-utils**：模块依赖图变更（已 documented in D26）。

7. **多个 docs/ 文件未交叉引用**：`venue-adapter-cookbook.md` 与 `tls-crypto-recommendations.md` 与 `observability-metrics.md` 各自存在，但没有统一入口（如 `docs/README.md` 索引）。
