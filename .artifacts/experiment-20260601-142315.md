# Experiment: AWS ENA RSS key 真伪实证（kernel + DPDK 两后端）

> Mode: experiment ｜ 生成：2026-06-01 14:23 (UTC+8)
> Host: AWS EC2 Graviton aarch64，kernel 6.1.163-186.299.amzn2023.aarch64，NIC=ENA(ens5/ens6)
> 被测 HEAD: `30651c0a`（探针 `examples/dpdk_rsskey_probe.cpp` + xmake target 为本次新增，未提交）

## TL;DR

**AWS ENA 两个后端（kernel epoll / DPDK PMD）guest 能读到的 RSS hash key 都是「占位」——硬件真正用于 steering 的 key 被 Nitro 藏死，读不到也设不进。** 因此**离线 Toeplitz 计算 `src_port→queue` 在 ENA 上根本不成立**（两后端皆然），只能经验实测，且**不可跨 attach/重启复用**。

连带实测推翻了 eph 代码库的一个论断：`eph-net-dpdk` 的 `predict_rss_queue` / `rss_using_probed_key` 路径在 ENA 上**静默产出错误队列**（用 eph 自己的函数 + probed key 预测，命中率 3/16 = 纯随机），而 `flow_steering.hpp:1245` 的文档却声称该 probed key "is the NIC's actual hash key … genuinely usable"。能抓住它的 `test_dpdk_rss_key_correctness` 当前 gated off。

## 假设（Hypothesis）

可证伪链，逐级递进：

- **H1**：AWS ENA kernel 侧能设置 / 读取硬件真正使用的 RSS key。
  - 证伪：设 key 后硬件 steering 不变 ⇒ set 是占位；或 Toeplitz(读到的 key) 与实际 steering 无关 ⇒ get 是占位。
- **H2**：AWS ENA DPDK 侧能设置 RSS key。
  - 证伪：`rte_eth_dev_rss_hash_update` 被拒。
- **H3（最关键）**：DPDK probe 到的 key（`rss_hash_conf_get`，`rss_using_probed_key` 路径所依赖）是硬件真正用于 steering 的 key。
  - 证伪：`Toeplitz(probed_key) → RETA` 预测的队列与实际落核不一致（命中率 ≈ 随机）。

## 动机

会话目标是「统一 kernel/DPDK 的 RSS 架构」并考虑删除 DPDK 侧运行时 `predict_rss_queue`。统一是否可行，取决于"两后端能否拿到一把可信的 RSS key 做离线 src_port→queue 计算"。本实验逐级验证该前提——而前提被**彻底证伪**，直接改变了统一架构的形态（见 §对决策的影响）。

业务背景：eph 的不跨核（软中断核 == app 核）依赖"把业务流 src_port 选到落在目标队列"，这需要预测 4-tuple→queue，而预测需要真实 RSS key。

## 方法（Method）

### 环境
| 维度 | 值 |
|---|---|
| Host | AWS EC2 Graviton **aarch64** |
| Kernel | 6.1.163-186.299.amzn2023.aarch64 |
| NIC | **ENA**：ens5(`0000:00:05.0`, IP 172.31.2.62) / ens6(`0000:00:06.0`, SSH+默认路由) |
| DPDK | system libdpdk，`dpdk-testpmd` / `dpdk-devbind.py` 可用 |
| vfio | **需 noiommu 模式**（`/sys/kernel/iommu_groups` 有项但 guest passthrough 不可用，`devbind` 报 "IOMMU support is disabled, use --noiommu-mode"） |

**安全约束（贯穿全程）**：测试 NIC 一律用 **ens5**（有 IP 但无 app）；**绝不碰 ens6**（承载本 SSH 会话 + 默认路由，绑 vfio = 断连）。ens5 每次临时绑 vfio，测完 `trap` 还原（rebind ena + dhclient 拉回 IP + 释放 hugepages）。同实例 ENI 互通被 AWS 屏蔽（bench 用 `bench_ns` 的原因）——DPDK 收流量改用 VPC DNS 当反射器绕开。

### 被测对象 / 工具
- kernel：`ethtool -X/-x`（set/get key）、`SO_INCOMING_NAPI_ID`(=56) 读 socket 实际落的 napi。
- DPDK：`eph_nicd`（`serve_nic`→`configure_rss`）、`dpdk-testpmd`、**新写的 `examples/dpdk_rsskey_probe.cpp`**（裸 DPDK + eph 的 `query_rss_state`/`queue_for_tuple`/`toeplitz_hash_ipv4`）。

### 数据集（探测输入）
- kernel：固定/递增 src_port（48 个验 set 效果、80 个验 get 预测），dst = VPC DNS 172.31.0.2:53，经 ens5 链路路由。
- DPDK：16 个不同 src_port 的 DNS 查询（src=172.31.2.62，dst=172.31.0.2:53）；回包入站 4-tuple 已知（src=DNS:53, dst=本机:src_port）。

### 测量方式
- **kernel set 是否生效**：换 key 前后，同一组 src_port 经 DNS 往返读 `SO_INCOMING_NAPI_ID`，对比落核是否变化。
- **kernel get 是否真**：`Toeplitz(ethtool key) → RETA` 预测队列 vs 实测 napi 的对应关系（是否双射）。
- **DPDK probed key 真伪**：`queue_for_tuple(query_rss_state(), 入站tuple)` 预测队列 vs DPDK `rx_burst` 实际收到回包的队列号。命中率 vs 随机基线(1/4)。

### 复现命令（要点）
```bash
# kernel set 测试（ens5，安全：无 app）
sudo ethtool -X ens5 hkey <40B>   # 设；ethtool -x 读回；改 key 后经 DNS 往返读 SO_INCOMING_NAPI_ID 对比落核

# DPDK 探针（ens5 临时绑 vfio，noiommu）
sudo modprobe vfio enable_unsafe_noiommu_mode=1; sudo modprobe vfio-pci
echo 1 | sudo tee /sys/module/vfio/parameters/enable_unsafe_noiommu_mode
echo 512 | sudo tee /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages
sudo ip link set ens5 down; sudo dpdk-devbind.py --bind=vfio-pci 0000:00:05.0
sudo build/linux/arm64/release/dpdk_rsskey_probe -l 0-1 -n 4 -a 0000:00:05.0 --file-prefix=rsskeyprobe --
# 测完：rebind ena + dhclient ens5 + nr_hugepages=0
```
完整脚本带 `trap` 还原；`eph_nicd --no-config-file --pci=0000:00:05.0 --total-queues=2` 用于看 configure_rss bring-up 日志。

## 数据

### H1 — kernel
- `ethtool -X ens5 hkey <MSFT key>` → **rc=0，读回确认变更，能还原** ⇒ 驱动接受 set。
- 但换 key 后，**48/48 个 src_port 落的 napi 完全不变** ⇒ **set 只改驱动本地缓存，硬件 steering 不认**。
- Toeplitz(ethtool key `55:14:93:54…`，40B) 预测队列 vs 实测 napi（80 端口）：

```
预测队列 → 实测 napi 分布（理想:每个预测队列只对一个 napi）:
  pred_q0 → {4117:5, 4118:5, 4119:5, 4120:5}   ← 完全均匀
  pred_q1 → {4117:5, 4118:5, 4119:5, 4120:5}
  pred_q2 → {4117:5, 4118:5, 4119:5, 4120:5}
  pred_q3 → {4117:5, 4118:5, 4119:5, 4120:5}
```
⇒ **零相关**：ethtool 读到的 key 是占位。注：kernel `netdev_rss_key` 本就 per-boot 随机、全网卡共用，且这把对 steering 无效。

### H2 — DPDK 设 key
`eph_nicd` 在 ens5/vfio 跑 `configure_rss`：
```
ENA_DRIVER: ena_rss_hash_set(): Setting RSS hash fields is not supported
configure_rss: rte_eth_dev_rss_hash_update(port=0, rss_hf=0x30) failed: rc=-95   ← EOPNOTSUPP
→ Platform: probe succeeded (key_len=64, reta_size=128); RSS active via probed key (using_probed_key=true)
```
⇒ DPDK **设不进 key**，落到 probe 路径。

### H3 — DPDK probed key 真伪（核心）
- 两次 vfio attach 的 probed key **完全不同**（每 attach 随机 40B + 补零到 64B）：
  - attach#1 `e61942ff907ecd5d…7d9` + 0×24
  - attach#2 `85a59bcdf4149857…c08` + 0×24
- `dpdk_rsskey_probe` 结果（16 端口，用 **eph 自己的** `queue_for_tuple(probed key + 真实 RETA, 入站tuple)` 预测）：

```
src_port  实际落队列   eph 预测队列
40001-08:  3,2,1,0,3,2,1,0   1,1,1,1,1,1,1,3
合计:      命中 3/16 = 25% = 纯随机基线(4 队列 → 1/4)
真实 steering 确定且规整(连续端口 3,2,1,0 循环)，probed key 完全预测不了
NIC 是否把 hash 值写进 mbuf: 否（mbuf->hash.rss 恒 0，flag 却置位）
```
⇒ **probed key 是软件占位（case ii）**，不是硬件真正用的 key。

## 分析

### 统计显著性
- H3 命中 3/16 ≈ 4 队列的随机期望(4/16)，**无统计意义上的相关**；真实 steering 自身是确定的（连续端口规整循环），排除"随机分流"解释 ⇒ 是 probed key 错，而非 NIC 不做 RSS。
- H1 的 80 端口分布完美均匀(每格恰好 5)，是"预测与现实完全独立"的教科书特征。
- 关键方法论保证：H3 用的是 **eph production `predict_rss_queue` 调用的同一套函数**（`query_rss_state`+`queue_for_tuple`），所以这直接等价于"eph 生产路径在 ENA 上预测对不对"——答案是"等于瞎猜"。

### 结果解读 / 归因
- ENA 在 AWS Nitro 下，**RSS 配置（key/hash 字段）由 hypervisor 托管，不开放给 guest**。
- kernel `ena` 驱动 `set_rxfh` 接受 key 但只存软件副本（`get_rxfh` 回显它），硬件用 Nitro 的隐藏 key。
- DPDK ena PMD init 时本地生成随机 key、想 `rss_hash_update` 装进设备被 `-95` 拒，`rss_hash_conf_get` 回读的是这把没装进去的软件随机 key（故每 attach 不同）。
- 两后端是**不同驱动**（Linux `ena` 模块 vs DPDK `net/ena` PMD），各自暴露各自的占位 key（kernel 固定占位、DPDK 每 attach 随机），但**共同点**是都不等于硬件真实 key。

## 结论

| 假设 | 裁定 |
|---|---|
| H1（kernel 能设/读真 key） | ❌ **证伪**：set 仅缓存（48/48 落核不变）、get 是占位（预测零相关） |
| H2（DPDK 能设 key） | ❌ **证伪**：`rss_hash_update` → -95 EOPNOTSUPP |
| H3（DPDK probed key 是真 key） | ❌ **证伪**：eph 函数 + probed key 预测命中 3/16 = 随机；且每 attach 随机变 |

**总裁定**：AWS ENA 两后端 guest 可读 RSS key 均为占位，真 key 被 Nitro 藏死 ⇒ 离线 Toeplitz `src_port→queue` 在 ENA 上不可靠（两后端皆然），只能经验实测，不可跨 attach/重启复用。

## 边界条件 / 局限
- 结论限 **AWS ENA / Graviton / 本 kernel+DPDK 版本**。mlx5 / i40e / ixgbe 等接受 `rss_hash_update` 的 NIC 上，离线计算应可行（可设 `kRssDefaultKey`），**不要外推到非 ENA**。
- H3 用 VPC DNS 当反射器（绕同实例 ENI 限制）；DNS 回包 4-tuple 已知，与真实业务流的 RX 同质。未在第二实例上以任意业务 4-tuple 复测（基础设施所限）。
- ENA 不暴露 `mbuf->hash.rss` 值（恒 0），故只能用"队列"对比、不能用"hash 值"对比——但队列对比已足够判真伪。
- 未测真 key 是否跨重启稳定（无法重启生产机）；但即便稳定，guest 读不到，对离线计算无帮助。

## 对决策的影响
1. **统一 RSS 架构的形态变了**：不再是"一份 Toeplitz 引擎 + 双 key 适配器"——ENA 两侧都没有可信 key。正解 = **经验式 discovery 为主**（实测落核分组），Toeplitz 计算只在"能证明 key 真"的非 ENA NIC 上当快路径。
2. **eph 真实问题（建议进 `/pax --reshape`）**：
   - `flow_steering.hpp:1245` 文档错误（"ENA … genuinely usable"），需改。
   - `predict_rss_queue` / `rss_using_probed_key` 在 ENA 上静默产错队列（影响 RSS-pinned src_port、DNS src_port 选择）——应在 ENA 上**经验式替换**或显式 hard-fail，而非信任 probed key。
   - `test_dpdk_rss_key_correctness` 当前 gated off（`pending post-S5`）；新写的 `dpdk_rsskey_probe`（VPC DNS 反射器绕开同实例墙）正是它缺的可跑 harness，应接入 un-gate。
3. `rss_srcport_finder.py`：离线 Toeplitz 模式在 ENA 上无效（强制 verify 已保护它不吐错数据，但会一直 verify 失败）——应转**经验模式为 ENA 主路径**。
