# Experiment：DPDK ex_order / UDP 异常 5min 复现验证

- 时间：2026-04-22 11:23 – 11:46 UTC（报告生成时：11:59）
- Commit：`7869ea4` (refactor(bench): S3 — remove legacy config.hpp + bench.conf + INI MMPP params)
- Host：AWS EC2 aarch64 Graviton
- 原始数据：[`bench-data-20260422-115953-anomaly-verify-5min.txt`](bench-data-20260422-115953-anomaly-verify-5min.txt)
- 前置基线：[`experiment-20260422-103422.md`](experiment-20260422-103422.md)（2026-04-22 10:34 全扫，含两处异常标注）

## TL;DR

前次 10:34 lat 全扫里的两个 DPDK tail 异常（**ex_order TX p50=254µs / throughput 3.8k** 与 **UDP p99=262µs**）在 5 分钟长窗口下均**不复现**。4 次重跑（ex_order ×3 + udp ×1）全部正常，p50/p99/TX/RX 跨 run 一致性 < 1%。**确认两处异常为单次 transient，而非 DPDK 路径稳态问题**。

---

## 假设（Hypothesis）

**H0（零假设，异常是稳态）**：在相同 commit / 相同 config / 相同 pin 下重复跑 DPDK ex_order 与 DPDK UDP，会再次观测到前次异常量级（ex_order TX p50 ≥ 100µs 或 throughput ≤ 10k/s；UDP p99 ≥ 100µs）。

**H1（备择，异常是 transient）**：重复跑这两个场景将得到"正常"量级（ex_order TX p50 < 20µs 且 throughput > 40k/s；UDP p99 < 50µs），与前次 06:51 基线一致。

**可证伪判据**：任何一次 5min 重跑若触发 H0 的阈值，则不拒绝 H0；若全部 4 次重跑都命中 H1 阈值，则拒绝 H0、支持 H1。

---

## 动机

前次 2026-04-22 10:34 全扫报告（`.artifacts/experiment-20260422-103422.md`，post-reshape + 客户端/mock 双绑核的 14-run sweep）标注了 3 处 DPDK 侧 anomaly：

| # | 场景 | 现象 | 前次基线状态 |
|---|------|------|--------------|
| 1 | DPDK ex_order | samples=120,808（同 30s 窗口 kernel 侧 1,005,085），**RTT p50=262,072 ns、TX p50=253,880 ns、throughput 3,806/s**（kernel 同场景 31,437/s） | 前前次 06:51 跑正常（p50≈20.9µs） |
| 2 | DPDK UDP | p50=20.5µs 正常，但 **RTT p99=261,944 ns、TX p99=253,496 ns** | 前前次 06:51 跑正常（p99≈27µs） |
| 3 | DPDK ex_market p99=16ms | 已解释为 MMPP quiet-state 稀疏采样 artifact（2142 samples / 120s ≈ 18 Hz） | 非 transient，系统固有 |

10:34 报告里已写明"不要把 262µs 作为 DPDK 性能引用——是单次 run artifact"，但未验证。用户要求"全部设为跑 5 分钟重新测"以判定异常 #1、#2 是否 transient。只验证 #1、#2（#3 是已归因的 artifact）。

**实验结果将影响**：10:34 报告中 DPDK ex_order / UDP 两行数据的可信度；是否需要 profile 生产级稳定性风险。

## 方法

### 环境

| 维度 | 值 |
|---|---|
| 硬件 | AWS EC2 aarch64 Graviton（m6g 系列） |
| NIC-A（mock 侧） | ens34，kernel 驱动 |
| NIC-B（client 侧） | ens35，bound to **vfio-pci**（DPDK 模式） |
| 链路 | client(ens35 DPDK) → AWS VPC fabric → mock(ens34 kernel) |
| OS | Linux 6.1.163-186.299.amzn2023.aarch64 |
| Compiler | GCC 14 via gcc14-wrap |
| Build mode | xmake release（`-O fastest`） |
| TSC | 1.00 GHz，CV 0.00%（`utils::TSC::calibrate()`） |
| CPU pin | client→CPU 4；mockex→CPU 6（log 每 run 均 verified） |

### 被测对象

- Commit：`7869ea4`（与 10:34 基线相同 HEAD；工作区干净）
- Binary：`build/linux/arm64/release/lat_ex_order_dpdk` / `lat_udp_dpdk` / `mockex`
- Config 文件：`/tmp/bench-5min.toml` ——从 `benchmarks/latency/config.toml` 派生，唯一差别：所有 scenarios 的 `duration_seconds = 300`

### 测量方式

- 工具：`benchmarks/latency/lat` wrapper（自动 vfio-pci NIC 状态转换 + 绑核 + 收样）
- 指标：`eph::utils::Recorder::record_ns()` 按 TSC 采样，产出 RTT / TX leg / RX leg 分布 p50/p90/p99/p99.9/max/avg/stddev；client 端纪录 `clock_gettime(CLOCK_MONOTONIC_RAW)` 与 mock 侧共享时基
- 预热：`warmup_samples = 1000`（从记录前丢弃）
- 窗口：每 run 300 秒
- 迭代：**ex_order 场景 3 次**，**udp 场景 1 次**（ex_order 是主异常点，UDP 异常属被动衍生）

### 复现命令

```bash
# 先确认 NIC_B bound to vfio-pci（lat wrapper 自动处理）
# 生成 /tmp/bench-5min.toml：复制 benchmarks/latency/config.toml 后把所有 scenario 的
#   duration_seconds 全部改为 300，其它字段不变。

sudo ./benchmarks/latency/lat ex_order --dpdk --config /tmp/bench-5min.toml     # r1/r2/r3
sudo ./benchmarks/latency/lat udp      --dpdk --config /tmp/bench-5min.toml     # r1
```

## 分析

### 统计显著性

- **ex_order 三次 5min 一致性**：RTT p50 三次极差 160 ns / mean 0.78%；TX p50 极差 40 ns / mean 0.32%——远小于 stddev 5%（业界稳定性门槛），**可认为稳态**
- **前次 10:34 异常与重跑的差距**：TX p50 差 20.5×（253,880 → 12,395 中位），throughput 差 12.2×——**不可能是噪声**，只能是 run 级事件
- **UDP 单 run 不足以给统计结论**，但 p50/p99 与 06:51 干净基线（p50=21,079 / p99=27µs 级）同量级，**支持 H1**

### 结果解读

- H1（异常是 transient）**成立**，拒绝 H0（异常是稳态）
- 4 次重跑（3+1）全部命中 H1 阈值：ex_order TX p50 < 20µs 且 throughput > 40k/s；UDP p99 < 50µs
- 跨 run 一致性良好——**DPDK 路径本身没有稳定性问题**，前次异常是外部环境事件

### 归因（复现失败情况下的最佳候选，无法 profile 确证）

| 可能根因 | 证据强度 |
|----------|---------|
| 前次 14-run sweep 中 ex_order 与 udp 在 DPDK sweep 里相邻位置，可能共享一次瞬时 NIC / fabric stall | 中——相邻位置的确 |
| 前次 30s 窗口太短，单次 stall 拉坏整个分布 | 高——5min 窗口即稀释到 p99.9 都正常 |
| EAL 冷启动或 hugepage NUMA 远内存命中（只在某次进程启动发生） | 中——无直接证据，但符合现象 |
| mockex 在 CPU 6 被短时其他进程抢占 | 低——`pin_thread` verified + CPU 6 在本机 bench 专用 |

无法 profile 确证——run 跑完就 ena_close 了，没留 profile 窗口。若未来再复现，应在 rerun 脚本里加 `perf record -a --call-graph dwarf -g -- sleep 30` 或 DPDK `rte_eal_trace`。

## 结论

- ✅ **H1（异常是 transient）成立**：4/4 次 5min 重跑全部正常，p50/p99/TX/RX 跨 run 极差 < 1% mean
- ✅ **DPDK 路径稳态性能确认**：ex_order RTT p50 ≈ 20.5µs、throughput ≈ 46k/s；UDP RTT p50 ≈ 21.2µs、throughput ≈ 46k/s
- ⚠️ **10:34 基线报告中 ex_order 与 UDP 两行数据应标注"含 transient"**，不作为 DPDK 性能参考
- ⚠️ **根因未落地**：复现失败即无法 profile；若未来再出现相同异常，必须立刻抓 perf / rte_trace

---

## 边界条件 / 局限

- 本实验**仅**验证 30s→5min 窗口下异常是否消失；不回答"相同 30s 窗口下重复跑会否复现"（未做 30s 多次重跑）
- 单次 5min UDP 样本量对 p99.9 结论偏弱（samples=13.7M 但 run count=1）；ex_order 3 次给统计信心，UDP 还可以加 2 次
- 未做 kernel 侧的 5min 对照跑；本次只证明"DPDK 侧稳态 OK"，不改变 DPDK vs kernel 相对结论（前次基线的 kernel 侧数据仍可用）
- 结论**不泛化**到其他 NIC / 其他 EC2 实例类型 / 其他 DPDK 版本——只对本机此 commit 有效
- profile-level 根因归因仍是开放项（见"归因"一节）

---

## 对决策的影响

- 10:34 基线报告（`experiment-20260422-103422.md`）的 DPDK ex_order / UDP 行**不作为稳态引用**；若需引用 DPDK 性能，改引本报告数值（ex_order RTT p50 20.5µs / UDP RTT p50 21.2µs）或 06:51 基线
- 暂不开 issue 追查根因——复现失败的单次 transient 不值得阻塞；但**建立告警**：若未来 bench 出现 DPDK 侧 TX p50 > 50µs 或 throughput < 20k/s，rerun 1 次；仍异常则 /pax --bench 做 profile 调查
- **不推翻 DPDK 采用决策**：DPDK 稳态比 kernel 低 12-17% RTT p50 的结论（见 10:34 基线）仍成立
