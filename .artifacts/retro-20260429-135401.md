## 做对了

### 1. Worktree 在 `/tmp` tmpfs，避开主盘 100%

- **发生了什么**：plan 阶段 `df -h` 才发现主盘 100%（Avail 69 MiB），常规 `git worktree add /home/ec2-user/eph-...` 一定爆。改 `/tmp/eph-dpdk-review`（tmpfs 16G，14G free）。
- **为什么是做对**：是这次能跑起来的唯一前提。tmpfs 重启即逝但 commit 已 push，反而帮"清理 worktree"做了天然背书。
- **怎么继续做**：plan 阶段 `df -h` 全挂载点不只看 `/`；BOUNDS 的"磁盘下限"必须实测，不拍脑袋。

### 2. `--no-pci --no-huge --vdev=net_null0` 与 market_infra `--in-memory` 完美并存

- **发生了什么**：默认假设是"NIC 被占就不能跑 DPDK 测试"。读 `dpdk_test_env.hpp` 后发现 unit-test 模式专为 CI 等无 vfio 环境设计，跟 market_infra 的 `--in-memory` 都不写 `/var/run/dpdk/<prefix>/` 文件，namespace 完全独立。146 个 unit case 在 market_infra 全程并发跑下零冲突。
- **为什么是做对**：把"NIC 被占用"这个看似 hard block 拆成"PCI scan / hugepages / file-prefix"三个独立资源，逐一确认无冲突。
- **怎么继续做**：碰共享资源前先看 EAL argv —— `--no-X` 和 `--vdev` 通常是绕过路径。

### 3. 承认 batch 4 "已挖透"，不强行 commit 边际项

- **发生了什么**：batch 4 第 16/17 轮，subagent 列出候选 finding 全是 "已 documented limitation" / "诊断改进但价值递减" 类。subagent 老实地 ➡️ 报无进展，触发 UNTIL。
- **为什么是做对**：边际 commit = 引入维护负担。retro 的反面教训库里有"为达成 KPI 而强行交付"的故事，subagent 没栽这个坑。
- **怎么继续做**：在 subagent prompt 末尾**显式写**"承认挖透 > 强行 commit" —— 这次写了，subagent 引用了，正反馈。

### 4. Trust-but-verify 每 batch sample-check

- **发生了什么**：每 batch 之间 `git show --stat`+`git log --oneline` 抽查 1-2 个 commit，看 diff size、Co-Authored-By trailer、commit message 含 why。零造假。
- **为什么是做对**：subagent 报告的"5/5 PASS"不是事实，而是 subagent 的转述；trust-but-verify 是 CLAUDE.md 的硬要求。
- **怎么继续做**：每 batch 至少 sample 1 个 critical 项的 git show + 1 个 random commit 的 stat。

### 5. NIC bind 对称协议

- **发生了什么**：`down → vfio-pci → 跑 → ena → up` 全程，跑完 ens35 IP / 路由 / link state 完全复原。market_infra 之后再起也无障碍。
- **为什么是做对**：共享资源使用必须"用完归还"，否则下次抢的人会 fail。
- **怎么继续做**：bind 协议写进 subagent prompt 模板，永远 explicit。

## 做错了

### 1. plan 阶段没意识到 `xmake -P /tmp/...` 仍把 build dir 落主仓库

- **发生了什么**：`xmake show -t test_dpdk_e2e` 显示 `targetfile: /home/ec2-user/ephemeral_dev/build/...`。原因是主仓库 `xmake.conf` 的 `builddir = "build"` 是相对路径，被 `xmake f -P` 时继承到 worktree 但解析时回到原项目。
- **代价**：发现得晚（开始 build 才看到产物在主仓库）；幸好主盘那时已经被 GC（441M Avail）放得下，否则 build 失败。
- **为什么会这样**：plan 阶段把"worktree 内不 build" 当作约束，但实际改完代码 build target 是必要验证。"不 build" 假设过强。
- **下次怎么避免**：worktree 配置时**显式** `xmake f -P <wt> --builddir=<wt>/build`，把 build 产物固定到 worktree 内。或者 plan 阶段就承认"会 build"，把 BOUNDS 算进 build dir 增量。

### 2. 用户两次提醒了我"应该自己想到"的约束

- **发生了什么**：
  - "先编译验证，但不要用 ens35 dpdk 网卡"—— 我之前给的 push 选项里假设 syntax-only 够了
  - "使用 dpdk 前都需要看 ens35 是否有人使用" —— memory 里有 `feedback_dpdk_shared_resource_check.md`，我没把它前置到 BODY step 0
- **代价**：用户介入两次，loop 节奏被打断；如果 user 没在场，subagent 默认 prompt 没这两条 guard。
- **为什么会这样**：plan 阶段把这俩当成"用户会自然 review"的事，没固化成 BODY 硬约束。memory 是被动加载的——它在 context 里但我没主动 surface。
- **下次怎么避免**：
  - plan 起步先 list 所有"已知需要前置检查"的 memory 条目，一并写进 BODY step 0
  - 任何涉及共享资源 / 远端 push / NIC 的 step 必须有显式 check sub-step

### 3. STATE 字段语义不严格

- **发生了什么**：batch 3 末 `elapsed_min: ~30` （subagent 自报），batch 4 prompt 我填 `elapsed_min: 105`（loop 总时长）。两个语义在不同 batch 间漂移。
- **代价**：小 — 没影响决策（UNTIL 看 consec_no_progress 不看 elapsed），但如果以 elapsed 为退出 BOUNDS 之一就坏事。
- **为什么会这样**：prompt 没明确写 elapsed 是 batch 内还是 loop 总。subagent 默认按字面"我跑了多久"。
- **下次怎么避免**：STATE 字段必须有显式定义（batch_elapsed_min / loop_elapsed_min 分开）。

### 4. batch 4 subagent 把第 16 轮合进第 17 轮报告

- **发生了什么**：subagent 输出只见第 17 轮的块，开头说"第 17 轮也是无进展"，但缺第 16 轮的独立块。违反 prompt 里"每轮一个块（禁合并）"的纪律。
- **代价**：审计时无法独立看第 16 轮挖了什么；trust-but-verify 时 sample 范围打折扣。
- **为什么会这样**：subagent 在两轮都 ➡️ 时容易"合并叙述"，prompt 虽然写了禁合并但没写"即使两轮都无进展也要分块"。
- **下次怎么避免**：prompt 加 "每轮一个块，**包括 ➡️ 无进展轮**，无论是否相邻、内容是否相似"。

### 5. plan 的 BOUNDS 磁盘下限拍脑袋

- **发生了什么**：plan 写 `磁盘下限：1 GiB → 50 MiB`（实测 / 只剩 69 MiB 才改）。这种事后调整就是"拍脑袋"被现实打脸的典型。
- **代价**：plan 的"工程感"减分；如果 user 严格按 plan 监督，会觉得我没做基本功。
- **为什么会这样**：套用 loop 骨架默认值，没在 plan 阶段实测。
- **下次怎么避免**：BOUNDS 每一项 plan 阶段都要实测 + 留 20% 缓冲，不能套默认。

## 意外收获

### 1. market_infra 在跑反而是好事

预期是"NIC 被占就跑不了 DPDK 测试，loop 一定要跳过 NIC-bound 验证"。结果发现：
- unit test 用 `--no-pci --no-huge` 完全独立，跑得起
- 这种"安全模式"覆盖了 batch 1 的 5 commits 的 100%
- 倒逼 BODY 走 syntax-only / unit-only 路径，反而 commit 节奏更稳（无 NIC 等待）

→ 物理约束有时把"不可能选择"变成"被迫的最优选择"。

### 2. `0a4b95cb` (DNS UAF) 是真的 🔴

我一开始把 DNS / TLS / 加密路径标为 "高风险但 batch 1 应该已扫到"。subagent batch 2 第 7 轮挖到 `AsyncDnsResolverT` 完全没有 dtor，doc 声称"两种析构序都安全"是漂移。这是典型的"docstring 滞后于代码"，比预期更值得做这次 loop。

### 3. `a2b958f8` (RETA ceiling-div) 的 forward-defensive 价值

这个 fix 在 production NIC（reta_size 都是 64/128/256/512）上 100% latent，但 DPDK API 不限制 reta_size 必须是 power-of-two，IDPF 等异种 PMD 可能违反。subagent 没把它当 minor 跳过，给了正确的"即使无现网影响也值得修"判断。

## 教训（可迁移）

### 教训 1: BODY 的 step 0 必须是"环境检查"

- **原则**：任何会触碰 *跨进程共享资源* (NIC / hugepages / file lock / port) 的 step 之前，强制有一个"资源占用 + 自身权限 + 失败回滚路径"的检查 step。
- **适用场景**：DPDK / Docker / 容器编排 / 共享数据库 / 远端 PR push / 任何牵涉外部状态的自动化
- **对立面（不适用）**：纯本地、纯只读、纯静态分析的 task —— 这种不该装腔作势加 step 0

### 教训 2: 承认"挖透"比"再挖一项"更负责

- **原则**：当主线 finding 用尽且 ESCALATION 落到"诊断改进 / 注释 / nodiscard 收紧"级别时，**老实承认无新发现** > **强行交一个边际 commit**。边际 commit = 维护负担 + 团队协作摩擦。
- **适用场景**：质量打磨型 loop / review skill / 批量 cleanup / lint 修补
- **对立面**：feature 开发 / 紧急 bug 修复 / 截止日期前的最后冲刺 —— 这些场景下"还能再做一点"是正面的

### 教训 3: 用户的"过来人 memory" 必须主动 surface 进 prompt

- **原则**：有 memory feedback / project memory 时，plan 阶段第一步是把所有"潜在适用"的 memory 列出来，作为 plan 章节里的显式 rule，不要等用户介入才唤醒。
- **适用场景**：自动化 loop / subagent 派发 / pax 类长链路 task
- **对立面**：探索性 / 一次性 / 用户全程在场看的会话 —— 这种不需要主动 surface（用户随时可纠偏）

### 教训 4: 物理约束（磁盘 / NIC / 时间）必须 plan 阶段实测

- **原则**：BOUNDS 不能套骨架默认；plan 阶段对每一项跑一次实测命令（`df -h`、`ps`、`free -m`），把数字写进契约。
- **适用场景**：所有有 BOUNDS 概念的 skill（loop / experiment / bench）
- **对立面**：试探性运行不需要严格 BOUNDS（但要在 prompt 里说"无 BOUNDS"）

### 教训 5: subagent 严格按 contract 执行 → 写得越死越好

- **原则**：subagent 不会自己脑补"你应该想到的事"。prompt 里每一条规则字面执行，越严格的约束越被尊重。
- **适用场景**：subagent 派发 / 长链路 prompt 模板 / 自动化测试 fixture
- **对立面**：探索性研究、开放式头脑风暴 —— 这种过度约束反而扼杀价值
