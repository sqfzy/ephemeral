## 做对了（What Went Well）

### 1. 时间类 UNTIL 硬墙真的硬住了

每个 subagent prompt 都用大字粗体强调"非 UNTIL 原文成分不得 signal"，并给了具体的 `[[ $(date -u +%s) -ge $UNTIL_EPOCH ]]` 检查。结果：
- B6 在 substance 饱和时返回 BATCH_DONE 而非 DONE → 继续派 B7
- B7 在最后 5min 进入 idle cooldown ➡️，没有粉饰假提交，最终 09:00:36 准点退出
- 0 次"差不多了 / 队列耗尽 / 觉得够"式的早退尝试

**为什么有效**：`purposes/loop.md` 把这条写成了 Phase 0.5 假设的"最高优先级"，subagent prompt 里又复述了 3 次。重复就是力气。

**怎么持续**：保留这套话术作为 `/pax --loop --auto` 时间类 UNTIL 的 boilerplate；不要简化。

### 2. ESCALATION 4 级在饱和时按设计触发

- L0→L1（B5 R146-149 ➡️）: sub_lens 7 维度都跑过一轮后，subagent 自己 broad-scan
- L1→L2（B6 起切到 bench gate）: review/test 饱和后改写 microbench
- L2→L3（B7 后段 polish 受限 ⊥ —— 这次直接进 L4 idle）
- L3→L4（B7 末尾）: 时间不够开新事，idle 到点

**为什么有效**：每个 subagent 都给了 ESCALATION 表 + "不许提前退出"，subagent 自然走到 idle。

**对照失败模式**：早期版本的 loop（参考 `.artifacts/retro-20260504-020041.md`）说 "subagent diminishing-returns 转 ESCALATION 而非退出" 是同一句话——这次是它的标准化升级版。

## 做错了（What Went Wrong）

### 1. 初始 BOUNDS 设得太保守，三次 auto-bump

- **现象**：max_rounds=90 在 B3 末就触顶；max_commits=40 在 B2 已经触；最终 172 commits / 174 rounds 远超
- **代价**：每次 auto-bump 都要在 main loop 出一段警告解释，浪费用户阅读带宽 + 让"BOUNDS"这个安全闸看起来像橡皮筋
- **根因**：我设 BOUNDS 时按"3 批 × 30 = 90"算 rounds，按"避免 PR 噪声爆炸"算 commits 上限 = 40。但用户给的是**时间** UNTIL，commit/rounds 上限只是噪声防护——应当按 `ceil(time_budget / avg_round_time) * 安全系数` 估算
- **下次怎么避免**：loop purpose 骨架的 BOUNDS 默认改为 "max_rounds = ceil(time / 3min) × 1.5" 而不是固定常数；或者干脆在时间类 UNTIL 时把 max_rounds 设为 inf（warning），仅靠时间 + max_commits 兜底

### 2. B1 含太多 "drop unused include" 噪声

- **现象**：B1 的 30 commits 里约 8 个是 `chore: drop unused <X> include`；B2 又 13 个；占了相当大的 review 带宽
- **代价**：用户看 review 报告时要从这些低价值 commit 里筛 substance；含水量高
- **根因**：B1 prompt 没有"max drop-include"约束，subagent 觉得这些是"看得见的 cleanup"就大量产出。直到 B3 才加 "max 5"，B5 才"max 0"
- **下次怎么避免**：loop purpose 骨架要求 "drop-include 类 commit 全 batch 上限 5"作为默认，而不是依赖 subagent 自觉

### 3. .artifacts/primer-20260505-113039.md 被 B5 误 stage 两次

- **现象**：B5 R121 + R122 之间，`git add` 误把上次会话留下的 untracked primer 加进暂存，subagent 自己发现后用 2 个 chore commit 撤回
- **代价**：commit 历史多 2 个无意义 chore；如果 subagent 没自检会污染 git history
- **根因**：B5 prompt 没明确"该 primer 是 untracked on purpose, leave it alone"。B6/B7 prompt 加了这条后再没复发
- **下次怎么避免**：loop dispatch 前扫描 `git status --short` 列出的 untracked 文件，prompt 里明确"以下 untracked 不要 stage：[列表]"

### 4. B5 后段产生了真 ➡️ 但 prompt 没显式认可

- **现象**：B5 R146/R147/R149 是 honest ➡️（broad-scan 无新发现）；subagent 输出时似乎有"是不是要保面子"的犹豫
- **代价**：浪费 subagent 推理带宽
- **根因**：直到 B7 prompt 才显式说"honest ➡️ valid; 不要 fake ✅"
- **下次怎么避免**：loop purpose 骨架默认就把"honest ➡️ ≥ fake ✅"加进契约 §10 启动后纪律

### 5. Substance 排序前移可能更高效

- **现象**：bench gate（B6/B7 共 17 个）是这轮最系统的产出之一，但放在最后 2 批
- **可能代价**：如果 UNTIL 比 9:00 早，可能压根没机会跑 bench gate
- **根因**：B1 prompt 把 sub_lens 排成 0..6，bench/perf 不在镜头里；只有 ESCALATION L2 切目的才碰
- **下次怎么避免**：把 "bench gate coverage gap" 加进 sub_lens 默认 7 维度（替换"TODO/FIXME 残留"或与之并列）

## 意外收获 / 惊喜

### 28 real bug fix — 远超预期

入场前以为这个仓库经过 5/4 那次 9 小时 retro（160 commits）后已经"打磨过头"了，预估 5-10 个真 bug fix。实际 28 个，其中 8 个是非显然的 latent UB / data race / 硬件路径 bug。**结论**：HFT codebase 的"看起来干净" ≠ "真的没 bug"，每次 batch 镜头切换都会暴露新视角下的 latent issue。

### memcpy(p, nullptr, 0) UB 簇

C++ 标准（[cstring.syn]）规定 `memcpy(dst, src, 0)` 在 dst 或 src 是 nullptr 时是 UB（即使 n=0）。eph-fix/eph-itch 里用的"先 memcpy 再 advance"模式在 0-byte payload 下命中。**这是个跨整个 trading 类 codebase 的系统性 pattern，值得专门 audit**。

### Bench gate 是金矿

eph-net-kernel 此前**零 benchmark**；eph-fix 的 set_int/set_double / parse_timestamp / OMS submit/on_fill 等热路径都没有微观 bench；containers/BoundedQueueBytes 同样零 bench。批次 6+7 一口气补 17 个 bench → 后续做性能优化时有了基线锚点。

### subagent 接力比单 subagent 跑长稳

每批 subagent 只跑 30 轮（~38-74min），context 不会接近耗尽 → 0 次 CONTINUE 信号 → 0 次中途 fallback。如果设 BATCH_UNTIL=60 或不设，subagent 大概率在 30+ 轮后开始遗忘前面 commit 内容、re-pick guard 失效。

## 教训（Key Takeaways）

### 教训 1: 时间类 UNTIL 必须是硬墙；契约里要重复 3 次

- **原则**：当 UNTIL 是 "Beijing 09:00" 这类时间表达，永远只有时间能触发退出，"队列耗尽 / 无新发现 / 三轮无 commit" 全部转 ESCALATION
- **适用场景**：跑一晚 / 周末跑 / 任何"按时间发量"的 loop
- **对立面**：UNTIL 是"Tier 1 清完" / "测试全绿"等状态类时，状态满足才能退；这种情况下 BODY 可以 signal UNTIL
- **怎么落地**：loop purpose 骨架的 §2 UNTIL 解读铁律 + §10 启动后纪律 + subagent prompt 里都要复述（**3 次**）

### 教训 2: BOUNDS 应该按 budget 估算，不能用常数

- **原则**：时间类 UNTIL 时，`BOUNDS.max_rounds = ceil(UNTIL_seconds / typical_round_seconds) × 1.5`
- **适用场景**：所有时间限定的 loop
- **对立面**：状态类 UNTIL（"Tier 1 清完"）时 BOUNDS 主要是失控保护，常数 OK
- **怎么落地**：loop purpose 骨架在 BOUNDS 章节给公式 + 根据时间显式算

### 教训 3: 契约越早加严越省事

- **原则**：prompt 里写 "max polish=5 / max drop-include=0 / no fake ✅" 这类 "上限"约束，**第一批就放进去**而不是观察到稀释才补
- **适用场景**：subagent 接力 loop（每批新 context，前批的隐性默认不会传递）
- **对立面**：单 subagent 短 loop 时可以信任它自调整
- **怎么落地**：loop purpose 骨架 §3 BATCH_UNTIL + §6 FAILURE 加一节 "默认上限"，subagent dispatch 模板里硬编码

### 教训 4: bug 成簇，跟着 pattern 走

- **原则**：发现一个 latent UB / data race / boundary bug 后，立即用 grep 在邻近代码搜同 pattern；很可能找到 1-3 个同病
- **适用场景**：审视成熟 codebase 时
- **对立面**：bug 是新写的代码独有时（pattern 没有先例）
- **怎么落地**：subagent prompt 加 "after a substantive fix, grep adjacent code for the same pattern" 作为默认 step

### 教训 5: ".看起来干净" ≠ "没 bug"，要换镜头

- **原则**：每次 review 都从一个新角度切（边界 / 并发 / RAII / metrics / dead code / test / TODO 7 维度轮询），不要靠"全面读"找 bug
- **适用场景**：成熟 / 已 review 过的 codebase
- **对立面**：新代码 / 紧 deadline 时，没时间 7 维度都过一遍
- **怎么落地**：sub_lens 7 维度作为 loop purpose 骨架的"代码 review"默认 LENS 实现

### 教训 6: untracked 文件要在 dispatch 前显式列出

- **原则**：派 subagent 前 `git status --short` 把 untracked 列表抓出来，prompt 里写 "以下 untracked 不要 stage"
- **适用场景**：long session（之前 session 留下 untracked 产物）
- **对立面**：clean 仓库时不必
- **怎么落地**：dispatch 前的 main loop 步骤加这条扫描
