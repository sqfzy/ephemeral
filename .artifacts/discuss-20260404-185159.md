## 内容摘要

围绕三大网络模块的生产就绪性展开了 7 轮结构化讨论。核心争议集中在：TLS 序列号限制是否为真实阻塞项（R10 指出可能是 uint64 无实际限制）、测试投入的范围和 ROI（R4 推动 mock 先行策略获得共识）、安全加固深度（R10 与 R4 在证书 pinning 上妥协为 soft pin + 回调）。最终共识：Gateway 降级检测是 #1 功能差距，错误码跨模块统一是 #1 架构债务，fuzzing + ASan/UBSan 是测试投入最佳起点，安全加固采取渐进路线。

## 第 1 轮

### R1 风险卫士
- TCP 重传缺失（eph-dpdk）导致丢包时全链路重建
- TLS 2^24 序列号限制在 100K msg/sec 下约 167 秒触及
- Gateway 降级检测（ConnHealth::Degraded）未实现
- KillSwitch 32 连接上限、Reactor 16 连接上限

### R3 性能狂热者
- RateLimiter spin-yield 等待触发上下文切换
- HttpClient 每请求新建连接无 keep-alive
- Transport::create() 阻塞式握手无法并行
- eph-dpdk 无 window scaling（64KB 限制）
- WebSocket masking 未用 SIMD

### R10 安全专家
- 无证书 pinning
- 无 TLS session resumption
- HMAC 密钥管理缺失（明文 string）
- 默认跳过 UTF-8 验证
- eph-dpdk 无 DoS 防护
- 日志注入风险

### R6 维护性倡导者
- header-only 全局编译膨胀
- 硬编码魔数散落各处
- 缺乏端到端集成测试
- 并发压力测试缺失
- 文档与代码同步风险

### R4 实用主义者
- 目标场景是 HFT 加密货币，很多"生产级"标准是过度工程
- 已做得很好：std::expected、constexpr 验证、spdlog、lock-free
- 聚焦三件事：TLS rekeying、Gateway 降级、E2E 测试
- 不应投入：IPv6、HTTP chunked、connection pooling

## 第 2 轮

### R1 反驳 R4
- TLS 断连时机不可预测，可能在下单确认前断连
- 并发下单场景需要 pre-established 连接
- 新风险：ARP 缓存过期（云环境 failover）

### R3 反驳 R6
- header-only 是 HFT 标准做法，拆分会增加间接调用开销
- Stats HWM 每 64 次采样可能错过队列溢出尖峰

### R10 反驳 R4
- 加密货币系统是高价值攻击目标
- ARP spoofing 在未隔离网络中是威胁
- 证书 pinning 只增加 ~2μs 一次性开销

### R6 反驳 R3
- off-hot-path 代码（http_client、proxy、gateway）拆分不影响性能
- 错误恢复路径（CircuitBreaker HalfOpen 并发、时钟回拨）未测试

### R4 部分让步
- 同意 TLS 序列号需主动追踪
- 同意并发下单需 pre-established 连接
- 反驳证书 pinning（CT Log 替代）
- 反驳编译单元拆分（PCH 可解决）

## 第 3 轮（聚焦 TLS rekeying）

### R1 提出三条路
1. TLS 1.3 KeyUpdate（复杂，需重新走 libssl）
2. 主动重连 make-before-break（热路径不变）
3. 确认实际序列号上限（可能是 2^32 或 2^64）

### R3 支持方案 2
- 热路径零变更，切换为原子指针交换 < 100ns
- 建议用 fuzzing 替代手写错误恢复测试

### R10 澄清
- TLS 1.3 RFC 8446 规定序列号为 uint64，可能无 2^24 限制
- 需检查代码实际实现
- 建议 soft pin（不匹配时 WARN + 回调，不阻断）

### R6 联盟 R3 on fuzzing
- 列出具体 fuzz targets
- 提出错误码语义不统一（string vs ConnectionErrorInfo）

### R4 关键让步
- 同意区分行情流和交易流可靠性
- 更新优先级清单

## 最终方案

### P0 — 立即执行（< 1 天）
1. 确认 TLS 序列号实际限制（审查 tls_encryptor/decryptor）
2. 确认所有时间组件使用 steady_clock

### P1 — 生产必要（1-2 周）
3. Gateway 降级检测（基于 last_activity 原子时间戳）
4. 错误码统一（跨模块结构化错误类型）
5. ASan/UBSan 编译选项
6. 3 个核心 fuzzer（decode_frame、parse_http_response、DNS reply）
7. E2E 集成测试（mock TcpTransport）

### P2 — 安全加固（2-4 周）
8. Soft certificate pinning
9. 日志脱敏审查
10. 日志命名空间统一
11. ARP 缓存定时刷新

### P3 — 性能优化（持续）
12. TX 批量发送（eph-dpdk）
13. HWM 实时追踪
14. 周期性阈值回调
15. E2E 延迟 benchmark
