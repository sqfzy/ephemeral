# Benchmark Report: Socket vs DPDK

## 测试环境

| 项目 | 值 |
|------|-----|
| CPU | AWS Graviton (ARM64), 16 cores, 1 thread/core |
| Cache | L1d 1MB, L2 32MB, L3 36MB |
| 内存 | Hugepages 256×2MB (DPDK) |
| NIC (Socket) | ENA ens34 (0000:27:00.0), kernel driver |
| NIC (DPDK) | ENA (0000:28:00.0), vfio-pci, noiommu mode |
| 目标服务器 | fstream.binance.com (Binance Futures WebSocket) |
| TLS | 1.3, AES-GCM (aws-lc) |
| 日期 | 2026-03-28 |
| Commit | c24d365 |

## 1. Ping-Pong 延迟对比

**场景**：连接 Binance WebSocket bare endpoint (`/ws`)，发送 100 次 WebSocket ping，测量 TX 入队延迟和端到端 RTT。

### TX Queue 延迟（ping enqueue → TX flush）

| 指标 | Socket (ns) | DPDK (ns) | 加速比 |
|------|-------------|-----------|--------|
| min | 1,932 | 252 | **7.7×** |
| p50 | 2,308 | 420 | **5.5×** |
| p99 | 11,884 | 780 | **15.2×** |
| p99.9 | 14,900 | 9,580 | 1.6× |
| max | 14,898 | 9,577 | 1.6× |

### RTT（ping flush → pong arrive）

| 指标 | Socket (ms) | DPDK (ms) | 差异 |
|------|-------------|-----------|------|
| min | 76.0 | 2.0 | **38× 更快** |
| p50 | 87.0 | 87.3 | 持平 |
| p99 | 97.2 | 101.5 | 持平 |

### 握手延迟

| 阶段 | Socket (ms) | DPDK (ms) | 加速比 |
|------|-------------|-----------|--------|
| TCP | 4.2 | 1.8 | **2.3×** |
| TLS | 39.4 | 6.9 | **5.7×** |
| WS Upgrade | 3.5 | 2.9 | 1.2× |
| **总计** | **47.1** | **11.6** | **4.1×** |

### 分析

- **TX 延迟**：DPDK 在 p50 上比 socket 快 5.5 倍（420ns vs 2,308ns）。Socket 的 TX 路径经过内核 `sendmsg()` 系统调用 + 内核 TCP 栈缓冲；DPDK 直接操作 NIC TX ring，省去了系统调用和上下文切换开销。
- **RTT min**：DPDK 的最低 RTT 仅 2ms，socket 为 76ms。这个巨大差异反映的是 Binance 服务器端的 pong 响应行为（可能有批量处理/延迟），而非纯网络延迟——两者 p50 RTT 接近（~87ms），说明稳态下 RTT 由服务器端和网络路径主导。
- **握手**：DPDK 握手总耗时仅 11.6ms（socket: 47.1ms），TLS 阶段加速最显著（5.7×），因为 TLS 握手涉及多轮 TCP 往返，每轮都受益于 DPDK 的低 TX 延迟。

## 2. 单 Symbol 行情对比

**场景**：订阅 btcusdt@bookTicker，接收 30 秒行情数据，测量 RX pipeline 延迟（rx_burst → 应用层解码完成）。

### RX Pipeline 延迟

| 指标 | Socket (ns) | DPDK (ns) | 加速比 |
|------|-------------|-----------|--------|
| min | 3,044 | 283 | **10.8×** |
| p50 | 4,980 | 428 | **11.6×** |
| p99 | 20,072 | 1,628 | **12.3×** |
| p99.9 | 26,888 | 3,932 | **6.8×** |
| max | 26,880 | 3,933 | **6.8×** |

### RX Pipeline 分解（DPDK）

| 阶段 | p50 (ns) | p99 (ns) | 占比 (p50) |
|------|----------|----------|-----------|
| TLS decrypt | 400 | 1,400 | 93% |
| WS decode | 100 | 200 | 7% |
| **Total** | **428** | **1,628** | 100% |

### RX Pipeline 分解（Socket）

| 阶段 | p50 (ns) | p99 (ns) | 占比 (p50) |
|------|----------|----------|-----------|
| TLS decrypt | 500 | 2,000 | 10% |
| WS decode | 100 | 300 | 2% |
| 内核→用户空间 | ~4,380 | ~17,772 | **88%** |
| **Total** | **4,980** | **20,072** | 100% |

### 分析

- **DPDK p50 仅 428ns**，socket p50 为 4,980ns——**11.6 倍加速**。这是最核心的行情接收指标。
- Socket 路径中 88% 的延迟来自**内核→用户空间数据拷贝**（`recvmsg()` + 内核 TCP 缓冲区管理 + 中断/调度）。DPDK 完全消除了这部分开销。
- TLS 解密本身差异不大（400ns vs 500ns），因为两者使用相同的 aws-lc AES-GCM 实现。
- p99 差异更大（12.3×），说明 socket 在尾部延迟上受内核调度抖动影响更严重。

## 3. 多 Symbol 行情对比

**场景**：订阅 btcusdt+ethusdt+solusdt@bookTicker 组合流，接收 30 秒，测量 RX pipeline 和 Feed Latency。

### RX Pipeline 延迟

| 指标 | Socket (ns) | DPDK (ns) | 加速比 |
|------|-------------|-----------|--------|
| min | 2,576 | 351 | **7.3×** |
| p50 | 3,756 | 532 | **7.1×** |
| p99 | 12,388 | 6,492 | 1.9× |
| p99.9 | 15,964 | 11,468 | 1.4× |
| max | 16,661 | 12,241 | 1.4× |

### Feed Latency（服务器发送 → 应用接收）

| 指标 | Socket (ms) | DPDK (ms) | 差异 |
|------|-------------|-----------|------|
| min | 1.37 | 1.25 | -9% |
| p50 | 2.51 | 2.47 | -2% |
| p99 | 3.62 | 25.73 | +610% |
| p99.9 | 4.45 | 29.47 | +562% |

### 吞吐量

| 指标 | Socket | DPDK |
|------|--------|------|
| 消息数 | 6,513 | 5,113 |
| WS frames | 10,109 | 10,055 |
| TLS records | 4,569 | 3,139 |
| 消息/秒 | ~217 | ~170 |
| 字节/秒 | 60.9 KB/s | 43.4 KB/s |

### 分析

- **RX Pipeline**：DPDK p50 仍快 7.1×（532ns vs 3,756ns），但优势在尾部缩小（p99 仅 1.9×）。多 symbol 组合流的 TLS record 更大（多条消息合并），decode 阶段有更多工作，拉平了部分优势。
- **Feed Latency 异常**：DPDK 的 p99 Feed Latency (25.7ms) 远高于 socket (3.6ms)。这是因为 DPDK 运行期间发生了**连接中断和重连**（日志显示 3 次重连尝试后停止），断线期间积累的消息在恢复后集中到达，导致尾部 feed latency 飙升。这不反映稳态性能。
- **吞吐量差异**：DPDK 收到的消息数更少（5,113 vs 6,513），因为有约 12 秒的断线时间。两者在连接期间的实际吞吐量接近。

## 综合对比总结

### 延迟对比表（p50 纳秒）

| 场景 | Socket | DPDK | 加速比 |
|------|--------|------|--------|
| TX Queue (pingpong) | 2,308 | 420 | **5.5×** |
| RX Pipeline (单 symbol) | 4,980 | 428 | **11.6×** |
| RX Pipeline (多 symbol) | 3,756 | 532 | **7.1×** |
| TCP 握手 | 4.2ms | 1.8ms | **2.3×** |
| TLS 握手 | 39.4ms | 6.9ms | **5.7×** |

### 延迟对比表（p99 纳秒）

| 场景 | Socket | DPDK | 加速比 |
|------|--------|------|--------|
| TX Queue (pingpong) | 11,884 | 780 | **15.2×** |
| RX Pipeline (单 symbol) | 20,072 | 1,628 | **12.3×** |
| RX Pipeline (多 symbol) | 12,388 | 6,492 | **1.9×** |

---

## 结论

1. **DPDK 在单 symbol 场景下优势最大**——RX pipeline p50 仅 428ns（socket: 4,980ns），**加速 11.6 倍**。这是因为单条消息的处理链路最短，内核开销占比最高，DPDK 的 kernel-bypass 获益最大。

2. **TX 路径改善更显著**——p99 加速 15.2 倍（780ns vs 11,884ns）。Socket 的 TX 路径包含 `sendmsg()` 系统调用和内核缓冲区管理，DPDK 直接操作 NIC DMA ring，消除了所有系统调用开销。

3. **多 symbol 场景下优势缩小但仍显著**——RX p50 加速 7.1 倍。TLS record 更大（合并多条消息），decrypt 和 decode 工作量增加，成为新的瓶颈（而非内核拷贝）。

4. **DPDK 的握手速度显著更快**——总握手延迟 11.6ms vs 47.1ms（4.1× 加速），TLS 阶段获益最大（多轮 TCP 往返都受益于更低的 TX 延迟）。对于需要快速重连的 HFT 场景，这很重要。

5. **DPDK 连接稳定性待改善**——multi-symbol 测试中 DPDK 出现了断线重连，而 socket 版本稳定运行了完整 30 秒。DPDK 的最小 TCP 栈（无拥塞控制/重传）在高吞吐场景下的鲁棒性不如内核 TCP。

6. **延迟分布**：Socket 的尾部延迟（p99/p99.9）受内核调度抖动影响大（可能出现 20-27μs 的突刺）；DPDK 的尾部延迟由 TLS 解密和 NIC DMA 延迟主导，更加可预测（p99.9 在 4μs 以内）。
