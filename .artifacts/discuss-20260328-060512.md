## 内容摘要

讨论围绕 DPDK TCP 栈是否应实现重传展开。R1 以 benchmark 断线为证主张必须加重传，R3 担忧热路径性能退化，R2 认为复杂度不可接受。R5 指出断线根因未经验证——可能是 reorder buffer 过小（仅 8 slots）导致突发乱序被误判为丢包。R2 提出一行代码加大 buffer 的方案，R3 综合为四层渐进方案。最终共识：不做完整 TCP 重传，分三层解决——加大 reorder buffer（64 slots）、SYN 重传（bug fix）、丢包遥测（数据驱动决策）。仅在遥测证明 overflow rate > 0.01% 时才考虑数据路径选择性重传。

---

## 第 1 轮：初步论点

### 【性能狂热者 R3 | 反对完整重传】
论点：
1. 重传要求 TX 保留发送缓冲区——当前 `tcp.hpp:407` 直接 `rte_eth_tx_burst` 后丢弃 mbuf，零拷贝。加缓冲区 TX p50 从 420ns 涨到 800ns+。
2. RTO timer 上热路径，每次 `poll_rx` 多一次超时检查。
3. 重连延迟约 12ms，数据中心 <0.1% 丢包率下期望成本仅 12μs/连接。
4. 加密货币交易所本身设计了应用层心跳和重订阅机制。

### 【风险卫士 R1 | 支持选择性重传】
论点：
1. `bench_market_multi_dpdk` 实测 30 秒内断线重连——已观测到的生产级失败。
2. 重连代价不止 12ms 握手——`transport.hpp:1718` 的 `tx_queue_.clear()` 丢弃待发消息，FIX session 序列号断裂。
3. Reorder buffer 仅 8 slots（`tcp.hpp:755`），9+ 个乱序包即触发"丢包"判定。
4. 不需要完整重传，只需 SACK：保留最近 N 个已发 segment，3 个 duplicate ACK 后重传。

### 【极简主义者 R2 | 反对】
论点：
1. TCP 重传是状态机噩梦（RFC 6298 + RFC 2018 + RFC 5681），代码量翻倍。
2. 更好方案：加大 reorder buffer（8→64），一行代码变更。
3. 如需增强可靠性，在应用层做（FIX ResendRequest、WebSocket 重连+重订阅）。

### 【成本审计者 R9 | 要求数据支撑】
论点：
1. 需先确定：当前断线中多少是 reorder overflow vs 真丢包？
2. 完整 TCP 重传开发成本：2-4 周，阻塞 Phase 2 订单簿和 io_uring。
3. 假设丢包率 0.01%，每小时约 4.3ms downtime——需要量化是否不可接受。

### 【第一性原理者 R5 | 追问根因】
论点：
1. DPDK multi-symbol 断线但 socket 不断——差异只在 TCP 栈。内核 TCP 有重传，默默解决了。
2. 应先加丢包/乱序遥测：gap size 分布、reorder hit rate、overflow frequency。
3. connect() 中 SYN 不重传（`tcp.hpp:298-302`）是一个真实 bug。

## 第 2 轮：交叉反驳

### 【性能狂热者 R3】
反驳 [R1]：reorder buffer 太小导致的"假丢包"应该加大 buffer 解决，不是加重传。
反驳 [R9]：即使需要重传，也应只做握手阶段（TLS 多轮往返），不动数据路径。

### 【风险卫士 R1】
反驳 [R2]：TLS record 跨 TCP segment 分片时，丢一个 segment 整个 record 不可恢复，应用层重传对此无能为力。
反驳 [R5]：benchmark 已给了数据点——30 秒就断了。等遥测数据期间用户已受损。

### 【极简主义者 R2】
反驳 [R1]：TLS record 分片问题可通过减小 record size 到单 MSS 缓解。加大 reorder buffer 只需改一个模板参数。

### 【成本审计者 R9】
反驳 [R3]：握手阶段的 SYN 重传只需几行代码，connect() 中已有超时循环框架。
联盟 [R5]：遥测优先，决策质量取决于数据质量。

### 【第一性原理者 R5】
反驳 [R1]：benchmark 用的是 af_packet 模式，乱序可能远高于 ENA 硬件直通。不能用 af_packet 表现代表生产 DPDK。
论点补充：SYN 不重传是真实 bug——发完 SYN 等 5 秒超时，应每 200ms 重发。

## 第 3 轮：方案收敛

### 【性能狂热者 R3 | 三层方案】
- Layer 1：ReorderSlots 8 → 64（一行代码）
- Layer 2：SYN 重传（几十行代码）
- Layer 3：丢包遥测（跑数据后决定 Layer 4）
- Layer 4（未来）：数据路径选择性重传（仅遥测证明必要时）

### 【风险卫士 R1】
接受分层方案。建议 reorder buffer 128 slots。

### 【极简主义者 R2】
支持 Layer 1-3。128 slots 占 182KB 栈空间可能过大，64 slots (~90KB) 已是合理上限。

### 【成本审计者 R9】
Layer 1-3 总成本 1-2 天，性价比极高。

### 【第一性原理者 R5】
同意。Layer 4 触发条件：overflow_count / total_rx > 0.01% 且 max_gap > 64。

## 第 4 轮：最终立场

- R3：不在热路径加重传；接受 Layer 1-3
- R1：放弃完整重传；接受先遥测再决策
- R2：Layer 1-3 复杂度可控；reorder > 64 应堆分配
- R9：数据驱动决策；1-2 天投入合理
- R5：遥测是前提；SYN 重传是 bug fix

## 最终方案

### 核心决策
不实现完整 TCP 重传。通过三层渐进方案解决，仅在遥测数据证明必要时才考虑数据路径重传。

### 方案细节

**Layer 1 — 加大 Reorder Buffer（< 1 小时）**
- ReorderSlots 8 → 64，消除大部分假丢包

**Layer 2 — SYN 重传（< 4 小时）**
- connect() 中每 200ms 重发 SYN 直到 SYN-ACK 或超时

**Layer 3 — 丢包遥测（< 1 天）**
- 新增 reorder_hits, overflow_count, max_gap_size, gap_histogram

**Layer 4 — 选择性重传（仅当遥测证明必要）**
- 触发条件：overflow / total_rx > 0.01% 且 max_gap > 64

### 已解决的分歧
- 完整重传 vs 不做 → 分层方案
- reorder buffer 大小 → 64 slots（~90KB 可接受）
- 何时做数据路径重传 → 遥测驱动

### 未解决的权衡
- reorder buffer 64 vs 128：若数据中心内网选 64，跨区域选 128
  → **建议**：先 64，遥测不够再加 | **原因**：90KB 栈空间安全
