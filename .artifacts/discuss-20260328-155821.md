## 内容摘要

讨论围绕 SharedRxDispatcher 的多连接 RX 分发开销展开。当前实现用 O(N) 线性 4-tuple 匹配 + rte_ring 中转，每包额外开销约 50-100ns（含双重 parse_packet）。R3 和 DPDK 专家主张三步优化（hash table → RSS 多 queue → rte_flow 硬件分发），R2 认为当前够用。全员收敛于"先做 hash table + 消除双重解析（Step 1），Step 2/3 等 benchmark 数据驱动"。关键洞察：不同 NIC（ENA/ConnectX/E810）能力差异巨大，应根据硬件自动选择最优策略。

## 最终方案

### 核心决策
分三步渐进优化多连接 RX 分发：hash table O(1) 匹配 → RSS 多 queue 并行化 → rte_flow 硬件分发。Step 1 立即实施，Step 2/3 数据驱动。

### Step 1 — Hash Table + 消除双重解析
- entries_ 改用 unordered_map (O(1) 匹配)
- dispatcher 元数据通过 mbuf dynfield 传递给 session（省 25ns/包）

### Step 2 — RSS 多 Queue（NIC 支持时）
- 检测 RSS offload → 多 queue → 每 queue 一个 mini-dispatcher

### Step 3 — rte_flow 硬件分发（NIC 支持时）
- 5-tuple exact match flow rule → per-connection queue → 零 dispatcher

### 已解决的分歧
- hash table 类型 → std::unordered_map
- NIC 抽象方式 → enum + 运行时检测
- API → connect() 自动检测，用户无感知

### 未解决的权衡
- dynfield 元数据 vs 重新解析：建议选 dynfield（25ns/包收益）
