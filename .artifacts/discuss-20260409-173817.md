## 内容摘要

Bug 100% 真实，且已经定位为协议层硬错：`TransportCore::do_connect()` 在 TLS handshake 之后、`do_ws_upgrade()` 之前 snapshot SSL 序列号并冻结进 `TlsRecordCrypto`，但随后 `do_ws_upgrade()` 通过 `SSL_write/SSL_read` 推进了 SSL 的 application traffic seq，导致 hot-path crypto 用过期的 seq 构造 TLS 1.3 nonce，第一次发送/接收即触发 `bad_record_mac` → server 立即关连接。Bug 由 commit `9788c4a8`（2026-04-02 split Transport into 3 classes）引入，约 7 天龄期。CI 没爆是因为所有 transport 测试要么 `use_tls=false` 要么只测 TLS 原语，没有任何测试同时跑 `use_tls=true + WsFramer + 完整 Transport::create + 收发一条真实 record`；example（simple_hft、binance_book）才是真实暴露面但不在 CI 跑表里。修复 = 把 `extract_hot_state + TlsRecordCrypto::create` 从 `do_connect` 抽离为 `arm_aead_crypto()` 并在 4 个 callsite（含 reconnect 路径）的 `do_ws_upgrade` 之后调用 + 加 e2e 回归测试 + extract_hot_state 加 pre-condition doxygen。P0 hotfix。

## 第 1 轮 — 独立提出核心论点

### R10 安全专家 | 立场：bug 真实存在，且符合 TLS 1.3 协议视角下的硬性矛盾

**论点**：直接逐条击穿用户列出的四个质疑点。

- **(a) 握手完成那一刻 SSL 的 read_seq/write_seq 真的还是 0 吗？**
  在 TLS 1.3 中，application traffic secrets 在 server "Finished" 之后才生效。aws-lc/BoringSSL 的 `SSL_get_write_sequence` / `SSL_get_read_sequence` 返回的是当前 epoch 内的下一个待用记录序号。
  - 客户端的第一个 application-data write 是 client Finished 吗？不是。在 TLS 1.3 里 Finished 是 handshake content type (0x16)，不是 application data (0x17)，它在 handshake epoch 内消耗自己的 seq。所以 application epoch 启动时 write_seq=0 没错。
  - read_seq 不一定是 0：服务器在 handshake 完成后立刻会发 NewSessionTicket，这些是 application content type、属于 application epoch、消耗 read_seq。如果 `tls->handshake()` 内部把这些 ticket 给读掉了，SSL 的 read_seq 已经是 1+，这时 snapshot 出来的 read_seq 是非零的。但这不是关键 —— 关键是 snapshot 之后还有 SSL_write(GET) 和 SSL_read(101) 进一步推进 SSL 内部状态，hot-path crypto 完全没办法跟上。

- **(b) handshake_write/handshake_read 调用 SSL_write/SSL_read 是否真的会推进 application seq？**
  毫无疑问。SSL_write 在 application epoch 内每 emit 一条 application_data record，write_seq++；SSL_read 每消化一条 application_data record，read_seq++。这是 BoringSSL/aws-lc 的硬规则。tls_session.hpp:533-564 的 handshake_write/handshake_read 是直接的 SSL_write/SSL_read 包装。

- **(d) hot-path nonce 构造**：tls_constants.hpp:392-406 的 `build_nonce` 和 RFC 8446 §5.3 完全一致（前 4 字节直接 copy IV，后 8 字节 = IV[4..12] XOR be64(seq)）。所以协议侧没有任何兜底——seq 错了就是 nonce 错，nonce 错就是 GCM tag 错，server 一定会发 fatal alert (`bad_record_mac`) 并掐连接。

这是协议层的硬错，没有"偶然能跑"的可能性。

### R3 性能狂热者 | 立场：hot-path 提取机制本身是对的，但调用点错了

**论点**：先把这个机制的设计意图说清楚。

这个 codebase 的 TLS hot-path 设计是故意绕开 SSL_write/SSL_read 的：从 README 的 "TLS 数据面用 aws-lc EVP_AEAD_CTX_seal/open（单次 AEAD 调用），跳过 SSL_write/SSL_read 多层间接，省 ~150ns/record" 就可以看出。

- `extract_hot_state` 把 SSL 的密钥/IV/seq 拷贝到自己控制的 TlsEncryptor/TlsDecryptor。
- 之后整个 hot path 必须独占 application traffic —— 任何对 SSL_write/SSL_read 的调用都会让 SSL 内部 seq 走偏，hot-path 看到的就是过时快照。

这意味着 `extract_hot_state` 的语义就是"之后再也不会经由 SSL 走 application data"，它必须是 application data 阶段的最后一次 SSL 调用。在 WS framer 的连接流程里，application data 阶段的最后一个 SSL 调用是 `handshake_read(101 响应)`，所以 extract_hot_state 必须放在 do_ws_upgrade 之后。DirectTransport 那条路径就是这样写的（line 990），是对的。

Transport / DirectTxTransport 走 transport_core.hpp::do_connect()，这个 do_connect 把 extract_hot_state 直接绑在 TLS handshake 完成后，没有意识到后面还有一层 application-data SSL 调用要发生。

**Bug 性质**：不是密码学错误，不是 nonce 算法错误，是接口顺序错误。修复零成本。

## 第 2 轮 — 互相反驳，深入子议题

### R10 安全专家 | 补充关于 NewSessionTicket 的精确行为

**论点**：第 1 轮里我对 read_seq 的描述还不够精确，补一刀。

在 BoringSSL/aws-lc 里，`SSL_do_handshake` 完成时，server 的 NewSessionTicket 可能已经在 socket 缓冲里但还没被 SSL_read 消化。两种情况下 bug 都成立：

- **情况 A**（NST 已被 handshake() 吃掉）：snapshot read_seq = 1。do_ws_upgrade 又读了 101 → SSL read_seq = 2。hot path 启动时 = 1。差 1 → bad_record_mac。
- **情况 B**（NST 还没读）：snapshot read_seq = 0。do_ws_upgrade 的 handshake_read(101) 内部会先消化 NST 再返回 101 数据 → SSL read_seq = 2。hot path 启动时 = 0。差 2 → bad_record_mac。
- **关于 write 方向**：snapshot write_seq = 0。do_ws_upgrade 的 handshake_write(GET) → SSL write_seq = 1。hot path = 0。差 1 → server 收第一条 hot-path record 的时候 nonce 错。

**服务器端 RX 肯定先爆**：客户端发出的第一条 hot-path application record，nonce 用了 seq=0，但服务器期望 seq=1。server EVP_AEAD_CTX_open 失败，发 `bad_record_mac` alert，关连接。客户端这边连第一条响应都收不到。

**反驳 R3**：你说 hot-path 设计本身没错，同意。但要补一句 —— `extract_hot_state` 这个 API 本身的命名和文档应该写明 "called must guarantee no further SSL_write/SSL_read on this session after this call"，否则将来又会有同样的 refactor 引入同样的 bug。这是接口契约层面的债。

### R11 怀疑论者 | 反质疑"bug 一定立刻爆"

**论点**：这一轮换一个方向 —— 既然第 1 轮所有"bug 不存在"的尝试都被堵死了，尝试质疑"bug 立刻触发，每次必爆"。

- 客户端 TX 第一条 record：hot path seq = 0，server 期望 seq = 1（GET 已用 0）。差 1。**爆**。
- 客户端 RX 第一条 record：hot path seq = 0 或 1，server 实际发出的下一条是 seq = 2 或 seq = 1。

refactored to use the same helper for consistency.

## 收敛输出

### 核心决策

**Bug 真实存在，是 TLS 1.3 序列号 desync 的协议层硬错；P0 hotfix。**

### 方案细节

**Bug 性质**：`TransportCore::do_connect()` 在 `transport_core.hpp:155-169` 调用 `extract_hot_state()` 并立即构造 `TlsRecordCrypto`，但调用方 `Transport::create` 和 `DirectTxTransport::create` 接下来还要调 `do_ws_upgrade()`，后者通过 `tls->handshake_write/handshake_read` 直接走 `SSL_write/SSL_read`，推进 SSL 内部 application traffic 序列号。hot-path crypto 的 seq 计数器因此停留在 snapshot 时刻的旧值，第一次发送/接收立即触发 GCM nonce 不匹配 → `bad_record_mac` → server 关连接。

**Bug 龄**：约 7 天，由 commit `9788c4a8`（2026-04-02 "refactor(transport): split Transport into 3 classes"）引入。

**为什么 CI 没爆**：所有 transport 测试要么 `use_tls=false`，要么只测 TLS 原语，没有任何测试同时跑 `use_tls=true + WsFramer + 完整 Transport::create + 收发一条真实 record`。example（simple_hft、binance_book）才是真实暴露面但不在 CI 跑表里。

**修复**（Hotfix，单 PR）：
1. 把 `transport_core.hpp:155-169` 抽离为 `TransportCore::arm_aead_crypto()`。
2. 在 4 个 callsite（Transport::create / Transport reconnect / DirectTxTransport::create / DirectTxTransport reconnect）的 `do_ws_upgrade` 之后调用。
3. `DirectTransport::do_connect_()` 重构为调用 `arm_aead_crypto()` 以统一接口。
4. 在 `extract_hot_state` doxygen 加显式 pre-condition。
5. 加 2 个 e2e 回归测试（Transport/DirectTxTransport/DirectTransport × TLS+WS round-trip + reconnect 场景）。

**修复变更规模**：~30 行代码改动 + ~300 行测试。回归风险极低。
