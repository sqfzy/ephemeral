## 完整讨论

### 第 1 轮 — 各角色初始立场

**R-Trader** 支持"HFT 必须子集"：
- HFT 真实用到的：WS/TLS + HMAC 签名 + Rate limiter + Kill switch + Circuit breaker + 订单 Gateway
- HFT 不用的：HTTP CONNECT proxy（colo 机房直连，不 +100μs）、HTTP 所有 edge cases、generic HTTP client
- 提议：HTTP parser 最小子集，proxy 不迁，Gateway/CB/RL/KS 全量

**R-Security** 反对砍 security tests：
- 历史事故：Binance 2019 返回畸形响应头、OKX 2021 TE 混合响应、Kraken 2022 CL 前导空格、2023 DEX 恶意 close 帧
- 交易所自己的 bug 会产生畸形输入
- test_http_request_cl_te_injection 9 cases、crlf 15 cases、whitespace 14 cases、te_edge 13 cases、build_upgrade_request_injection 13 cases 必须全量
- parser 正确性是 guarantee，不是 feature

**R2** 激进砍：
- 每行不用的代码是负债
- 逐项"who uses this" 审查
- 砍 HTTP chunked/TE/Expect/multipart/cookie/redirect
- 砍 test_transport_types 211 cases（旧 alias 系统）
- 砍 test_transport 110 cases（旧 Transport）
- 目标 ~600-700 cases

**R6** 反对激进砍：
- "HFT 不用 X" 每次都会被未来打脸（2 年前不用 proxy，现在 Prime Broker 要求）
- 但同意 R-Trader 对"当前不用"的判断是 signal
- 提议：暂不迁 + baseline 归档 + 文档 TODO

**R4** 要求实证：
- 全员在推测，要 grep
- 检查 proxy / HMAC / Gateway/CB/RL/KS 的实际消费者
- 暂缓立场

**立场修正**：

**R4** 分析证据：
- Proxy：真实用户，迁
- HMAC/Gateway/CB/RL/KS：存在但从未被使用

### 第 3 轮 — 子议题：Gateway/CB/RL/KS 真正该怎么处理

**R6** 提 middle ground 分级方案：

| Level | 内容 |
|---|---|
| L0 | 全部不做 |
| L1 | + KillSwitch (20 行 + 10-15 tests) |
| L2 | + RateLimiter TokenBucket (30 行 + 15-20 tests) |
| L3 | + CircuitBreaker (~50 行) |
| L4 | + Gateway 组合类 (~80 行) |

**推荐 Level 2**：
- KillSwitch 是监管要求，library 提供省事
- RateLimiter 是所有交易所都有限流的通用 primitive
- CircuitBreaker 有 opinions 分歧
- Gateway 是强制组合形态，HFT 有自己的 venue wrapper 层

**R-Trader** 强烈支持 Level 2，用 3 年 HFT 经验证实：
- KillSwitch：每个 trading firm 必需，20 行 `std::atomic<bool> + std::function<void()>`
- RateLimiter：30 行 token bucket，通用 primitive
- CircuitBreaker：HFT 团队写 per-venue 状态机，通用版价值低
- Gateway：反 HFT 实践，通用 Gateway 让人绕过它

**R2** 接受 Level 2：
- 50 行代码 + 30 tests vs "HFT 团队重复造"的收益，可接受
- 但坚持 minimal 实现，不做框架
- 放 `eph-utils/` 不单独 eph-risk 模块

**R-Security** 无意见（Level 2 组件不涉及 security）

**R4** 总结最终 scope（770 cases，51% 迁移率）

### 第 4 轮 — 立场修正封定

**R-Trader**: 从"全量必须"收敛到 Level 2 — 被证据 + baseline 无消费者说服
**R-Security**: 从"全量保留"收敛到"security + parser 全量，app-level 不迁" — 被代码岛论据说服  
**R2**: 从"激进砍全部"软化 5% 接受 Level 2 — 被 HFT 重复造论据说服
**R6**: 从"P3 全量但延迟迁 proxy"收敛到 Level 2 — 被证据压倒
**R4**: 无改变，方法论角色

连续 2 轮无新论点 → 终止条件满足。

## 最终决策

### 核心哲学

> **grep 证据驱动**：baseline 自己 example 都不用的 library code 不迁移；HFT 团队会重复造但 baseline 没有设计 consensus 的组件不迁移；真实 consumer 存在的必须迁；security/regression tests 全量；parser 层测试全量（正确性生命线）；旧 API alias 系统对应的测试丢弃。

### 功能回迁清单

| 组件 | 状态 | 归属 | 实现形态 |
|---|---|---|---|
| HTTP parser | ✓ **子集** | `eph-net/include/eph/net/http.hpp` (public) | 只支持 WS upgrade 响应 + 简单 REST GET/POST；不支持 chunked/TE/cookies/redirect |
| WS HTTP 握手 | ✓ | `eph-net/include/eph/net/detail/ws_handshake.hpp` | `TcpStream::create()` 透明处理，StreamConfig.ws_path 驱动 |
| HMAC | ✓ | `eph-net/include/eph/net/hmac.hpp` (public) | 复用 aws-lc 已有依赖 |
| HTTP CONNECT proxy | ✓ | `eph-net/include/eph/net/detail/http_connect.hpp` | StreamConfig.proxy 透明处理（kernel only，DPDK 拒绝） |
| KillSwitch | ✓ **minimal** | `eph-utils/include/eph/utils/kill_switch.hpp` | ~20 行：atomic<bool> + on_trip 回调 |
| RateLimiter (TokenBucket) | ✓ **minimal** | `eph-utils/include/eph/utils/rate_limiter.hpp` | ~30 行：fixed capacity + refill rate |
| Gateway | ✗ **不做** | — | 强制组合不符合 HFT 实践 |
| CircuitBreaker | ✗ **不做** | — | opinions 分歧，HFT 写 per-venue 状态机 |

**新模块数：不变（11）**。KillSwitch + RateLimiter 进 eph-utils 不立独立 eph-risk 模块。

| 分歧点 | 解决方式 | 关键论据 |
|---|---|---|
| Gateway/CB/RL/KS 全量 vs 部分 | Level 2（保留 KillSwitch + RateLimiter minimal） | grep 证据 baseline 无消费者；HFT 团队会重复造但不用框架 |
