## 做对了（What Went Well）

### 1. STATE 透传 + 已扫光清单防重复

每批 prompt 显式列出"前 N 批已动 / 已确认无 bug"清单，subagent 不会反复回去翻 icmp_registry / queue_allocator / mp_topology。**带来的收益**：13 批 subagent 几乎从未重复挑同一个文件做无意义改动；每批的有效 commit 占比维持在 60%-100%。

### 2. Time-class UNTIL 当硬墙严格执行

batch 7 / batch 10 / batch 13 三个 subagent 都自评 "diminishing returns"、"codebase well-engineered" 想提前退。主循环没接受这个信号，继续派下一批，只是把 prompt 转向 ESCALATION 路径（test 覆盖 / bench 填补 / NaN-slip 专扫）。

**收益**：
- batch 11 ESCALATION L2 转 bench 填补，加了 13 个新 bench 文件 / ~60 microbenches
- batch 12 转 cross-module integration tests，找到 vwap NaN-slip + 5 处其它 NaN-slip
- batch 13-15 专扫 NaN pattern，又收割 9 处独立 NaN-slip（包括 risk_check / signals / position 这些 HFT 关键路径）

如果 batch 7 时就退出，会丢掉 70+ commit。

### 3. Subagent 模式 + git 对账闭环

主循环不依赖 subagent 自报 commit hash 的真实性，每次 BATCH_DONE 后 `git log oldHEAD..HEAD` + `git diff --shortstat` 直接对账。**收益**：subagent 偶尔报告含小数据错误（batch 9 内部计数 137 vs 实际 133；batch 10 内部 elapsed 与外部 wall 不一致），主循环不会被带偏。

### 4. NaN-slip pattern 滚雪球扫法

batch 8 偶然在 `fix/risk_check::projected_exposure` 发现 NaN 不被 `<= 0.0` 守卫拦截。第二轮立刻派下一批专扫——找到 5 处。Batch 12-15 持续扫到饱和——共 22 处独立 NaN-slip / saturating-arith fix。**没有第一处就把它当模式来扫，会修一漏二十**。

### 5. 严格 BATCH_UNTIL 有效防 context 爆炸

batch 11 / 13 / 14 / 15 给了显式 wall-clock cap（60min / 40min / 25min / 25min），subagent 都按时返回。无 cap 的 batch 8 / 9 跑了 60 / 26 轮但 context 仍未爆——证明 cap 是 fail-safe 而非常态约束。

## 做错了（What Went Wrong）

### 1. Batch 2 让 doc 主导（13/13 全 doc）

**发生了什么**：batch 2 subagent 13 个 commit 全是 stage marker / 注释 scrub，没有一处实质 bug fix。  
**代价**：浪费 ~15 分钟，substantive 工作延后到 batch 3 才真正开始。  
**为什么会这样**：batch 2 prompt 没明令优先 substantive，subagent 自然趋向"高产 / 易得分"的 doc 修复。  
**下次怎么避免**：所有 batch 1 之后的 prompt 必须明文 `禁纯 doc 修复 unless 该 doc 描述错误码 / 行为契约`（batch 3 起加了，效果立竿见影）。

### 2. 早期没识别 NaN-slip 是 pattern

**发生了什么**：batch 8 第一次发现 risk_check NaN-slip 时只单点修，没立刻扫全库。  
**代价**：直到 batch 12 才系统化扫，期间 subagent 来回浏览同一类代码。  
**根本原因**：pax 的 BODY pseudocode 没有 "if pattern: sweep" 步骤；只有 "pick → fix → next pick"。  
**下次怎么避免**：BODY 加 pattern detection step——若发现"某守卫缺 isfinite / 某 cast 缺校验 / 某 retval 没检查"等 pattern，下一轮自动派 grep-based 全库扫专项 pass。

### 3. Cross-backend symmetry 未真正深入

batch 9 / 10 / 12 prompt 多次列入 "P1: KernelTcpStream vs DpdkTcpStream concrete symmetry"，但每个 subagent 都浅尝辄止——大多 dismiss 为 "by-design asymmetry"。  
**代价**：可能漏掉真实的对称性 bug，特别是 KeepaliveConfig 的 lower 路径行为对应、WsConfig handshake 处理。  
**根本原因**：prompt 描述太抽象，没给具体对照表 / 测试模板。  
**下次怎么避免**：cross-backend symmetry 议题必须在 prompt 里给具体对照矩阵（"对每个公开方法列出 kernel vs dpdk 的 expected behavior，标记差异"），而不是开放式问 "找差异"。

### 4. 最初没估到 NaN-slip 的体量

**发生了什么**：原以为 review 主要找 race / lifetime / TLS bug，结果 NaN-slip 占 22/160 = 13.75% 总 commit。  
**代价**：batch 1-7 prompt 没把这个维度列入必扫，发现得偏晚。  
**下次怎么避免**：HFT 项目 review 模板必须把 "数值守卫 isfinite 覆盖" 列为 P1，与 race / UB / TLS 同级。

### 5. 主循环每次切换批次有信息损耗

**发生了什么**：每次新派 subagent 必须重新读相关文件（无 context 继承），每批前 5-10% 时间花在重新熟悉代码。  
**代价**：估算 10-15% 的 wall clock 浪费在重复 context 加载。  
**根本原因**：subagent 隔离是必要的（context 限制），但缺持久 cache。  
**下次怎么避免**：在 prompt 里附 "Quick Map" —— 一段 30-50 行的代码地图（关键文件路径 + 一句话 what）让 subagent 跳过初步探索。

## 教训（Key Takeaways）

### 教训 1：单点 bug 出现的 pattern 必须立即 sweep 全库

**原则**：当某个 anti-pattern 在 codebase 出现一次时（NaN slip 守卫、retval 不检查、saturating arith 缺失、注释失真等），第一时间假设它是 pattern 而非单例，立即派一个 grep-based 全库 sweep pass。

**适用场景**：
- 任何 long-running auto-loop review
- code reshape 之后的体检
- 安全 audit

**对立面**：
- 业务初期、设计未稳定时不必 sweep（pattern 边界还在变）
- 单文件 PR review 不必 sweep（scope 已限定）

### 教训 2：time-class UNTIL 是硬墙，subagent 的 "diminishing returns" 是 ESCALATION 触发点

**原则**：在 `--loop --auto` 跑长时窗时，subagent 自评 "找不到东西了 / 收益递减 / 成熟度高" 不是退出条件，是切换搜索面 / 子目的 / 镜头的触发点。主循环必须保持时间硬墙纪律，按 ESCALATION 梯队（L1 跨模块 / L2 测试 / L3 bench / L4 冷却）转向，直到时间到。

**适用场景**：
- 用户给定时间预算的 long-running task
- 自主演进 / 持续打磨

**对立面**：
- "队列耗尽 / Tier 1 清完" 类 UNTIL 时，diminishing returns 等同于 UNTIL 触发，应该退（这是 UNTIL 的原文成分）
- 资源昂贵的迭代（每轮要跑 30 分钟集成测试）时，需要更精准的"是否还有价值"判断

### 教训 3：subagent prompt 的 STATE 注入决定下批 ROI

**原则**：每批 prompt 必须显式列出"前 N 批已动 / 已确认无 bug"+"本批必扫区"。光说"基于上批继续"远不够——subagent 是无状态的，会反复回老地方。

**适用场景**：
- 任何多批次 subagent 编排
- 长 cycle 协作（其中各 cycle 间 context 不连续）

**对立面**：
- 单批次任务无需此结构

### 教训 4：BATCH_UNTIL 必须有 wall-clock 硬上限

**原则**：subagent 模式必须给显式 wall-clock cap，**即使** subagent 自己有 "30 轮" / "context 接近耗尽" 等其他终止条件。wall-clock cap 是 fail-safe，不是常态约束。

**适用场景**：所有 subagent 派发场景。

**对立面**：单次预期 < 5 分钟的 quick task 可省。

### 教训 5：reshape 后必须有 doc-rot scrub commit

**原则**：任何大幅 reshape PR（API rename / 模块重组 / 新机制替代旧机制）merge 前必须有一个独立 commit 专门跑 doc-rot 扫描——grep stale API 名 / TODO marker / "S<phase>" placeholder / removed config keys 等。

**适用场景**：所有破坏性 reshape；所有 multi-stage 落地的 reshape。

**对立面**：纯 bug fix / 行为不变的 refactor 通常不需要。

### 教训 6：cross-backend symmetry review 必须给具体对照矩阵

**原则**：要求 subagent 做"对称性 review"时，prompt 必须附**具体对照表**（每个公开方法 / 每个 sub-config 列两端 expected behavior + 标记差异），否则 subagent 会做表面化扫描。

**适用场景**：Kernel vs DPDK / Cloud vs On-Prem / Sync vs Async / 任何并行实现的对称性核查。

**对立面**：单实现 module 不适用。
