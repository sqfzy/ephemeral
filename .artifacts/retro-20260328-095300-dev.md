## Pitfalls & Lessons

### Pitfall 1: Initial gap analysis had ~35% false positive rate

**Background**
The explore agent identified 17 "gaps" in the first scan, but 6 were already handled by existing code (ITCH length validation, FIX SOH detection, Transport null checks, EvictingQueue clear(), etc.).

**Wrong initial judgment**
Trusted the gap list at face value and started planning implementations for already-solved problems.

**Root cause**
The explore agent read code at a high level and didn't trace through all the call paths. For example, it flagged "ITCH parser no message length check" but the `parse()` function at line 181 already does `if (len < expected) return kTruncated`.

**Lesson**
Always verify each gap by reading the actual code before implementing. A 30-second Read call saves a wasted implementation attempt. **Gap identification and gap verification are separate steps.**

**Reusable pattern**
For any audit/review output, verify the top 3 findings before trusting the rest. If verification shows >25% false positives, re-verify all remaining findings.

### Pitfall 2: Namespace mismatch in test code

**Background**
Added new WebSocket tests that used `ws::opcode::kBinary` syntax, but the test file used `using namespace eph::net::ws;` so the correct form was just `opcode::kBinary`.

**Phenomenon**
Compilation error: `'ws' has not been declared`

**Lesson**
Before writing tests in an existing test file, check the `using namespace` declarations at the top. Match the existing convention exactly. This is obvious in retrospect but easy to miss when generating many tests at once.

### Pitfall 3: EvictingQueueStats test used unqualified type name

**Background**
Test files for containers don't use `using namespace eph::containers;` — they use the fully qualified name.

**Phenomenon**
`'EvictingQueueStats' was not declared in this scope`

**Lesson**
Same as Pitfall 2 but for a different file. Reinforces: **always check naming conventions per test file, not per project.**

## Insights

### Insight 1: Consistency passes are high-value, low-risk

**Discovery**
After adding `throughput()` to BoundedQueueStats, I noticed 3 other stats types (EvictingQueueStats, BoundedQueueBytesStats, EvictingQueueBytesStats) and 2 parser stats types (FIX, ITCH) lacked the same convenience methods.

**Core insight**
Once you establish a pattern in one place, systematically applying it across all similar types is almost always the right call. Each individual change is trivial and low-risk, but the cumulative effect is a significantly more consistent API surface. Users learn one pattern and apply it everywhere.

**When to apply**
Whenever you add a new method to a Stats/Config/View type, check if parallel types in other modules should get the same method.

### Insight 2: /evolve converges fast on mature codebases

**Discovery**
All 10 productive commits happened in rounds 1–11 (~90 minutes). Rounds 12–54 (~6.5 hours) found nothing new despite targeting different modules (whole project, eph-containers, eph-fix, TLS audit, /improve).

**Core insight**
The `/evolve` pattern is most valuable for projects in the "functional but not polished" stage. Once config validation, logging, and API consistency are addressed, the remaining gaps are either large features (SBE module, TLS KeyUpdate) or diminishing returns (testing edge cases of edge cases). The exponential backoff in `/repeat` correctly reflects this — it should have been allowed to terminate earlier.

**When to apply**
For mature codebases, `/evolve` is a one-shot tool (1–2 rounds), not a long-running loop. Reserve `/repeat` for tasks with continuous external input (monitoring, CI checks).

### Insight 3: Delegation to /test skill produces better test coverage than manual test writing

**Discovery**
Round 4 delegated to /test for WebSocket/HTTP boundary conditions. The agent produced a comprehensive gap analysis (every public function, every error path) that would have taken much longer to produce manually.

**Core insight**
Using specialized agents for their domain expertise (test gap analysis, architecture review) produces more thorough results than trying to do everything in the evolve loop. The evolve loop is good at identifying *what kind* of improvement is needed; specialized skills are better at *executing* that improvement.

## Key Decisions

### Decision 1: Add convenience methods vs. keep stats minimal

**Decision point**
After adding throughput() to BoundedQueueStats, should all stats types get convenience methods, or should users compute derived metrics themselves?

**Options**
| Option | Pros | Cons |
|--------|------|------|
| A: Add to all types | Consistent API, less boilerplate for users | More code to maintain, wider API surface |
| B: Keep minimal | Simpler, fewer methods to document | Users repeat `popped * 1e9 / ns` everywhere |

**Choice**: Option A — consistency wins for a library targeting production use.

**In retrospect**: Correct decision. The methods are one-liners with no complexity, and the consistency across 6 stats types makes the API feel intentionally designed rather than ad-hoc.

### Decision 2: Store begin_string in BasicMessageView vs. leave it as parser-internal

**Decision point**
FIX parser extracts `begin_string` but discards it. Should it be stored and exposed?

**Options**
| Option | Pros | Cons |
|--------|------|------|
| A: Store in view | Users can check FIX version, useful for multi-version handlers | +1 field (string_view, 16 bytes) per message |
| B: Leave internal | Smaller MessageView, parser already works | Users can't distinguish FIX.4.2 vs FIX.4.4 |

**Choice**: Option A — the 16-byte cost is negligible, and version awareness is genuinely useful.

**In retrospect**: Correct. The field was already being parsed; not storing it was an oversight, not a design choice.
