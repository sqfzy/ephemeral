## 做错了（What Went Wrong）

### 1. **Subagent 自报数与 git 真相不一致，我没每批次交叉核验**
- **发生了什么**：batch 1 报 14、batch 2 报 14、batch 3 报 4 = 32；最终 git 实际 42。差 10 来自 batch-4-partial（9 commits）+ batch 3 subagent 数据末尾"4 commits"漏报了一项（实际是 4 个 commit 但 STATE.commit_log_size 报 33，对得上 git 那段）。即便如此，**主循环自己没每批末跑一次 `git rev-list --count` 与 subagent 的 commit_log_size 对账**
- **代价**：终止汇报里我自信地写了"32 commits"，直到 retro 阶段被 git diff --stat 打脸；如果用户基于错误数字做后续决策（例如 "32 commits 还远没到 80 上限再跑两批吧"），可能放任 BOUNDS 误报
- **根因**：把 subagent 返回消息中的 "STATE.commit_log_size" 当作 ground truth，没意识到 subagent 在 mid-flight 被打断时返回的 STATE 不一定反映其已经做的所有 git 写入
- **下次怎么避免**：每批次结束后**必须**跑 `git rev-list --count <launch-HEAD>..HEAD`，与 subagent 自报对账；任一不一致 → 以 git 为准，且重新核对 commit_log

### 2. **Batch 4 dispatch 与"完成 batch 3 后终止"的边界没问清楚**
- **发生了什么**：batch 3 BATCH_DONE 后我按契约"立即派发下一批"，把 batch 4 prompt 直接发出去；用户随后用工具拒绝 + 文字"完成Batch 3后终止"打断 —— 但此时 batch 4 subagent 已经跑了约 14 分钟、产出 9 个 commits
- **代价**：用户原意是"跑完 3 批就停"，但实际多产出了 9 个 commit。这 9 个 commit 本身质量没问题（test 类、独立可 revert），但它们的存在违反了用户语气里的"3 批停"边界
- **根因**：契约里"BATCH_DONE 不停"是设计正确的（auto-loop 不能等用户），但**用户最初的 `until: 永远` 与隐含的"够了我会喊停"之间存在张力**；我没在 plan 阶段把"用户打断后是否回滚 mid-flight commits" 这条策略钉死
- **下次怎么避免**：
  - loop plan 必须含"中断策略"小节：用户打断时，已 commit 的工作**默认保留**（每条独立可 revert），还是**自动 revert 到上一 BATCH_DONE 的 HEAD**？
  - subagent dispatch 时同时启动一个轻量"打断窗口" —— 主循环 dispatch 后先快速发 1-2 行"开始派发 batch N，10s 内可打断"再开始等 subagent 返回，但这有副作用（拖慢 auto-loop）。两难，更现实的解是把"打断后保留还是回滚"写死在契约里

### 3. Subagent 返回消息格式不稳定（batch 1 缺 round blocks）
- **发生了什么**：batch 1 的第一个 subagent 返回 CONTINUE 时只写了 STATE summary，没把 3 轮的 round headers 拼进返回消息；我事后用 commit message 追溯还原才补上
- **代价**：用户本应看到 `╔══...╝` 头部框 + diff-stat 结果块的完整轨迹，结果第一段被我"代为补全"，信息保真度打折
- **根因**：subagent prompt 第一次写时没强调"返回消息 itself 必须含所有完成轮的 block，不只是 STATE"；后续 batch 2 prompt 才加了这条铁律
- **下次怎么避免**：subagent prompt 模板里把"返回消息结构"做成第一节而非末节；未来通用 loop dispatcher 把这做成 boilerplate

### 4. 磁盘 BOUNDS 设得偏松，整个 loop 期内未真正逼近过
- **发生了什么**：BOUNDS 设 2 GiB 下限，启动时 free 4 GiB；3 个 batch 后 free 仍 3 GiB —— 实际消耗仅 1 GiB 左右
- **代价**：不是真"做错"，但说明我对 xmake 增量构建消耗预估过悲观（`不要 xmake clean` 是对的，但增量本身耗得不快）。如果再多跑 4-5 批可能也不会触线
- **根因**：我把"build/ 缓存 3.2 GiB"误读为"每批会再吃 1 GiB"，实际增量构建大量是文件覆盖而非新增
- **下次怎么避免**：把 `du -sh build/` 在每批末记一次，画曲线，下次同类 loop 用真实增长率设 BOUNDS

### 5. 没主动跑一次完整测试套件 sanity check
- **发生了什么**：每轮子 pax 跑了 affected tests，但全程没在批次边界跑一次 `xmake -m release -y && xmake build -g tests && xmake run -g tests` 完整 gate
- **代价**：理论上每轮独立绿，但 42 个 commit 累加起来是否仍然全绿，没有显式信号
- **根因**：契约里"每个 commit 独立可编译"被我等同于"全套测试全绿"，这是漏洞 —— 单个 commit 改动 A 时跑 A 的测试，但 A 与 B 的相互作用（例如 kJumboMaxMss 的中心化重构 + 后续依赖该常量的 commit）没被全套测试覆盖
- **下次怎么避免**：契约里加一条"每个 BATCH_DONE 必须跑一次 `xmake build -g tests && xmake run -g tests`"作为 batch gate；不是每轮 gate（太贵），而是 batch gate

## 教训（Key Takeaways）

### T1: Subagent 自报必须与 ground truth 交叉验证
- **原则**：长跑 loop 里，subagent 返回的 STATE 是"它认为做了什么"，git/file system 是"它实际做了什么"。两者可能因中断、漏报、状态计算错误而背离
- **适用场景**：所有 subagent 模式的 loop / 长跑任务
- **对立面**：单 subagent 单次任务（不长跑、不分批）时无此风险，可以信 STATE
- **可操作动作**：每个 BATCH_DONE 后跑一行 `git rev-list --count <baseline>..HEAD` 自动对账

### T2: 饱和信号是 ESCALATION 触发点，不是退出信号
- **原则**：连续 N 轮 ➡️ 无改动 / 队列耗尽 / 同一镜头反复无果 —— 全部是"换镜头/换子目的/降优先级"的信号，**不是**"loop 该结束了"的信号；只有 BOUNDS / 用户打断 / UNTIL 原文成分能终止
- **适用场景**：所有 `until: 永远` / 时间类 UNTIL 的 loop
- **对立面**：UNTIL 原文是"队列清空"或"Tier 1 完"时，饱和信号确实就是退出信号
- **可操作动作**：在 plan 阶段就把这条写进 BODY 注释，subagent prompt 也复制一份

### T3: 中断策略要在 plan 阶段钉死
- **原则**：auto-loop 的"用户打断"是必然事件（除非真的跑到 BOUNDS）；中断时 mid-flight commits 的归宿（保留 / 回滚到上 BATCH_DONE / 询问）必须在契约里写死
- **适用场景**：所有 auto-loop
- **对立面**：单批 < 5 轮的微型 loop 中断概率低，可以省略
- **可操作动作**：plan 模板加"## 中断策略"章节，3 选 1 显式声明

### T4: 子目的优先级不是固定金字塔
- **原则**：review/fix/feat/test/doc 这些子目的的"优先级"应该按当前 loop 阶段的边际价值动态调，而不是僵化"先 fix 后 test 后 doc"
- **适用场景**：所有跨多镜头的 loop
- **对立面**：发布前的 ship loop 必须先全绿测试再 doc，顺序固定
- **可操作动作**：契约把 ESCALATION L1/L2 的"换什么"列成可配置而不是写死的 review→test→bench→doc

### T5: 主动资源勘察是 DPDK 类项目的入口仪式
- **原则**：所有触及 DPDK 的 skill 第一个动作必须是 `ps + lsof + HugePages + lspci -k`
- **适用场景**：本仓库所有 dpdk 相关 skill
- **对立面**：纯 kernel 路径的 loop 不需要
- **可操作动作**：考虑把这写进 CLAUDE.md 而不是个体 skill
