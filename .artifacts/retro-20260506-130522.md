# retro：kernel vs DPDK TCP echo 系统指标 bench → cgroup shield 验证 → "shield 没用"的迭代复盘

**时间**：2026-05-06 09:30 UTC – 13:00 UTC（约 3.5 小时）
**主题**：用 perf stat + /proc 快照对比 kernel TCP 与 DPDK TCP 的系统级开销；尝试用 cgroup shield 进一步降噪；最终通过 replication 发现"shield 收益"主要是噪声。

---

## TL;DR

- 这次 bench 完成了 4 阶段迭代：**baseline (3) → 加 shield (6) → consistency 检查 → replicated baseline (6)**，最终 12 trial × 2 mode × 2 setup = 48 个数据点。
- **意外结果**：原报告里"DPDK cache-miss -41%"主要由 baseline run-1 trial-3 的 outlier (571M) 拉高 mean 造成。replication 后 baseline 真实 mean 是 286M，shielded 200M，**真实改善 mean -15% / stddev -75%**，而不是 -41%。
- **核心教训**：**3-trial 报告 + stddev > 30% mean 的数字不能直接发结论**。我当时看到 baseline DPDK stddev 203M（60% of mean）就该停下来重做，而不是直接对外说 "-41%"。这次幸亏用户问 "cache miss 优化是否还成立" 才触发 replication。

## 做对了（What Went Well）

### 1. 用户一句话"再跑一次"挽救了一份错误结论
**发生**：phase 5 结束时报告里写着 "shielded vs baseline DPDK cache-miss -41%"。用户没接受这个结论，一句"再跑一次非 shield 的，看看 cache miss 优化是否还成立"触发了 replication，发现原 baseline 的 mean 被 outlier 拉高。

**为什么这是做对**：
- 用户用一个朴素的怀疑（"是吗？真的吗？"）切入了一个我自己没去查的问题
- 结果挽救了一个本来要进 INDEX.md / commit 的错误结论
- 印证了"小步质疑 + 廉价 replication"在 bench 工作里的价值远高于"快速发布"

**怎么扩大**：
- 任何 < 5 trial 且 stddev > 30% mean 的对比，**默认必须再跑 1 个 batch**，不向用户呈现"-X%"的相对数字
- 报告里如果出现"显著改善"语气的句子，触发自检：是否跨独立 run 验证过

### 2. "中间产物 + 渐进结论"的工作方式
**发生**：每个 phase 都产出了独立的 markdown 报告（REPORT / COMPARE / CONSISTENCY / LATENCY / REPLICATION），不是一份大报告。

**为什么这是做对**：
- 每次发现新问题都能快速产出新一份小报告，不用回头改大报告（虽然最终还是改了）
- 文件名里的 `_compare` / `_consistency` / `_replication` 让脉络可读
- 用户每次 "看看延迟" / "再跑一次" 都能附加到既有 artifact 树，不用从零开始

**怎么扩大**：
- 任何长 bench / experiment 流程：**优先写多份小报告，不写一份长报告**
- 文件命名直接告诉读者"这份在哪一环"

### 3. 自动化脚本的 production-grade 防线
**发生**：bench-sysmetrics-tcp.sh 写的时候花了精力做：
- forbidden-CPU 断言（用户声明 CPU 2/3/6 占用就 hard-code 拒绝那些 pin）
- 临时 config 副本（不污染 benchmarks/latency/config.toml）
- trap-based cleanup（lat / mockex / perf 子进程兜底 kill）
- 后台 /proc/status poller + atomic mv（避免 pid 被 reap 时 0-byte 截断）
- 每 trial 独立 outdir、ANSI clear-screen、tty/non-tty 双路径、systemd-run scope 适配
- DRY_RUN 支持

**为什么这是做对**：
- 在 systemd-run scope 里跑出"writes to /.artifacts" 这种 cwd-resolution 坑时，trap 兜底救场了
- 后台 poller 的 atomic write 保护是真的派上用场（shielded smoke 时第一版崩了）

**怎么扩大**：
- 一次性 bench 脚本也值得做基本的生产级防线（trap / 输入校验 / cleanup）—— 30 分钟投入避免后面调试 1 小时

### 4. 用 cgroup AllowedCPUs 而不是 partition 模式
**发生**：原本想用 cgroup v2 `cpuset.cpus.partition=root` 这种正式机制，最后选了更简单的 `systemctl set-property AllowedCPUs` 路径。

**为什么这是做对**：
- partition 模式与 systemd 管理的 cgroup hierarchy 复杂交互很多，AllowedCPUs 是 systemd 自己一等公民支持的 → 1 行命令搞定
- 失败模式可见：`systemctl show ... -p AllowedCPUs` 直接显示状态
- trap restore 是 1 行 `systemctl set-property --runtime ... AllowedCPUs=0-7`，不需要 rmdir 复杂 cleanup

## 做错了（What Went Wrong）

### 1. baseline 3-trial 看到 stddev 60% mean 没停下重做（致命错误）
**发生**：baseline run-1 DPDK cache-miss 三 trial 是 207M / 234M / **571M**。聚合时 mean = 337M、stddev = 203M（60% of mean），写进 REPORT.md 当成"事实"，然后基于这个 337M 算出 "shield 让 DPDK cache-miss 从 337M 降到 200M = -41%" 的对比结论。

**代价**：
- 原 REPORT.md 报告里 "DPDK cache-miss -41%" 的论断错了（真实值 mean -15%）
- 这一论断已经被 git commit (2394b36e)，要 amend / 改 doc 才能修正
- COMPARE_baseline_vs_shielded.md 里也错（已修正）
- 用户花了 30 分钟 + 6 trial 重做 baseline 才把这事翻过来

**根因**：
- **bench 心法不严**：stddev > 30% mean 是 bench 业内"小红警告" —— 我当时看到 60% 没触发任何告警机制
- **赶着做"对比"**：心里有"baseline 弄完了，赶紧上 shield"的节奏感，跳过了"baseline 本身可信吗"这一步
- **3 trial 太少**：6 trial 已经能让 outlier 被 robust mean 拉回；3 trial 一个 outlier 就翻盘
- **没有 outlier 检测自动化**：脚本里没有对 stddev/mean 超阈值的 trial 给 warning

**下次怎么避免**：
- bench-sysmetrics-tcp.sh 的 `--aggregate` 模式应该加 `coefficient_of_variation` (CV = stddev/mean) 计算，**任何 metric CV > 30% 必须以红字打印警告**，不光是数字摆出来
- 任何对比报告（"X 比 Y 好 Z%"）默认要求两边都 6 trial 起；3 trial 的对比只能写"初看趋势如此，需要更多数据"
- bench skill 骨架（pax/purposes/bench.md）已经有"标准差合理（通常 < 5% mean）"的验收标准，**我没遵守**

### 2. 没区分 "shield 收益" 与 "systemd-run 开销"
**发生**：shield 用 `systemd-run --scope -p AllowedCPUs=...` 实现。包装本身有 ~8% p50 RTT + ~6% throughput 开销。我在 phase 4 写第一份 COMPARE 时把这个开销当成 "shield 没用" 的证据混在一起，没拆清。

**代价**：
- COMPARE_baseline_vs_shielded.md 里关于"DPDK ctxt-sw +37%"那条，归因写的是"测量伪差"，但其实 systemd-run 引入的额外 cgroup 状态机才是真正原因 —— 我当时混了
- 让用户最终的"shield 没用"结论被同时验证（这是好的），但分析路径不清晰

**根因**：
- 没做 systemd-run 本身的 isolated baseline（即"裸跑 systemd-run --scope，不带 shield"）
- 把"包装"和"shield 本身的 cgroup AllowedCPUs"两个变量混着一起对比

**下次怎么避免**：
- 任何"加包装的 shield"对比都至少 3 组：baseline / 包装-only / 包装+shield
- 这能把"包装开销"和"shield 收益"分开看

### 3. cgroup AllowedCPUs 这套 shield 在 setup 阶段就该被怀疑
**发生**：方案设计阶段写了一段"cgroup AllowedCPUs 是 isolcpus 的'用户态半截'，挡不住 NIC softirq / timer tick / per-cpu kworker"。但还是花了一个小时跑了 6 trial 才"证实"这一点。

**代价**：
- 1 小时浪费在跑一个事先就预期效果有限的方案
- 用户最终确实想要的是 isolcpus（"之后我会重启"），cgroup shield 是个绕路

**根因**：
- 当时 framing 是"先做廉价的，看 partial benefit 是多少；如果不够再上 isolcpus"
- 但实际"廉价 shield"在 sustained busy-poll workload（DPDK 已经独占 CPU）这个具体场景里基本没有可改善的余地 —— 我应该看出来 DPDK 不是 shield 的目标用户

**下次怎么避免**：
- 对"廉价中间方案"的预期收益要做更具体的"目标 workload 是什么"分析，不是默认所有 workload 都受益
- DPDK busy-poll 已经独占 CPU → cgroup shield 的"挡邻居"前提不成立 —— 这一步本来就该让"对 DPDK 不做 shield bench"成为默认推荐

### 4. 报告生成 / 修正纪律不够
**发生**：写完 baseline REPORT.md 之后，每次有新发现（shielded、consistency、replication）都是**追加**新文件，而不是回头修正 REPORT.md。结果 REPORT.md 留着旧的 "-41%" 措辞，COMPARE 里也是旧措辞，最后只在 REPLICATION_check.md 里标了"裁定"。

**代价**：
- 现在 .artifacts/bench-sysmetrics-tcp-echo-20260506/ 里有冲突信息：REPORT.md 说 "-41%"，REPLICATION_check.md 说 "-15%"
- 未来读者看到 REPORT.md 可能就停在 -41% 不往下读 → 错误传播
- 已经 git commit 的 commit message 里写的也是 -41% 那一套

**根因**：
- 渐进追加 markdown 是好的（见"做对"#2），但**结论变化时必须回头标注源头**
- 我没建立"前一份报告的结论被新数据推翻 → 至少在前份报告顶部加 'SUPERSEDED BY ...' 横幅"的纪律

**下次怎么避免**：
- 任何 .artifacts/ 报告里的核心结论（"-X%"、"显著优于"）被后续 replication / 新数据修改时，必须：
  1. 在原报告顶部加 banner: `> ⚠️ SUPERSEDED BY <new-file>: <一句话新结论>`
  2. 在 INDEX.md 该行末尾加 `(SUPERSEDED)` 标记
- 这不是"清理历史"，是"指引读者顺序"
- 本次 retro 之后即应回去给原 REPORT.md / COMPARE 加 SUPERSEDED banner

### 5. 接受 user-level 时间戳忽略 = 一致性陷阱
**发生**：原 baseline run-1 (10:00) 和 baseline run-2 (12:21) 之间隔了 2 小时。这 2 小时里 host 上发生了什么我没记录：可能有别的 cron job、systemd timer、其他用户进程。两组 baseline 的 stddev 不一样（203M vs 22M）也许部分由这个差异导致。

**代价**：
- 严格说，run-1 和 run-2 是两个不同的"宏观环境"，把它们合并算 mean 不严谨
- 但这种 environmental drift 在 EC2 这种 hypervised 环境是常态，没法完全避免

**根因**：
- 没有自动化"环境快照"步骤（top -bn1 / uptime / 其他进程列表）

**下次怎么避免**：
- bench-sysmetrics-tcp.sh 里加一个 pre-flight：`top -bn1 -o +%CPU | head -20 > pre-flight.top.txt`，记录"跑这次 trial 时 host 上别的工作负载是什么"

## 意外收获 / 惊喜

### 1. DPDK RX p99 比 kernel 快 5.5×（这个是真信号）
**发生**：baseline 6 trial 后，RX leg p99 kernel 56 µs vs DPDK 10 µs。这是延迟数据里最戏剧的一项。

**为什么是惊喜**：
- DPDK 的"快"通常被宣传是 p50 或吞吐 —— 但这次在 RX p99 上看到 5.5× 是出乎意料的大
- 解释也清晰：kernel 路径"NIC IRQ → softirq → epoll → recv"任一段被抢占都会贡献到 p99 tail；DPDK 用户态轮询 + vfio 直接读 mbuf 没有这条 tail 路径
- 这个数字远比 "DPDK 比 kernel 快 30%" 这种营销话术更有说服力

### 2. Cgroup shield 在 DPDK ctxt-sw 维度反而是 +37%
**发生**：原本以为 shield 会让 ctxt-sw 减少（毕竟挡了邻居），结果 DPDK shield 后 ctxt-sw 反而 +37%。

**为什么是惊喜**：
- 揭穿了我自己的潜意识假设："包装一定是中性的，效果只来自 shield"
- 实际是 systemd-run --scope 包装本身引入了 cgroup hierarchy 多查一层 → 每个 syscall 多 ctxt-sw
- 这是个**反直觉的工程现象**，记下来：**所有"看似无副作用的包装"都需要单独的 baseline 测试**

### 3. ctxt-sw 不全是 voluntary
**发生**：6 trial × 4 group 的 voluntary_ctxt_switches 全部为 0 —— kernel TCP 客户端跑 epoll 非阻塞 + DPDK 客户端 PMD 轮询，**两边都不调 sleep**。

**为什么是惊喜**：
- 我原本以为 kernel TCP 路径会有 voluntary ctxt-sw（recv 阻塞之类）
- 实际 lat_tcp 用 KernelTcpStream 是 non-blocking + edge-triggered epoll，底层一直 busy-poll
- 这意味着：**kernel TCP 在 sustained-load workload 下也是 busy-poll 模式**，跟 DPDK 的差异只在"协议栈复杂度"，不在"是否睡眠"
- 这点改变了我对 kernel/DPDK 差异机理的理解

## 教训（Key Takeaways，可迁移）

### 1. CV (stddev/mean) > 30% 是 bench 数据"不可信"的硬阈值

- **原则**：任何 bench 里某 metric 的变异系数（CV）超过 30%，**默认这个数字不可用作"-X%"对比**，必须先把 stddev 降下来再说
- **适用场景**：所有 perf bench / latency bench / 任何"对比 A vs B"的工作
- **对立面**：极少数 metric 本质就是高度变异的（比如 max / 偶发尖峰），那只看 mean 没意义；这种应该看分位数而不是 mean

### 2. 廉价 replication 比"快速发布"价值高 10×

- **原则**：在写出"-X%"结论之前，问自己"如果我现在重跑一遍，数字会一样吗？" —— 不确定就再跑
- **适用场景**：所有 bench / experiment 报告，任何对外呈现的对比数字
- **对立面**：纯定性观察（"特性能跑通"）不需要 replication；只 quantitative claim 需要

### 3. 包装即变量

- **原则**：任何"在被测对象外面套一层"的措施（systemd-run / docker / strace / perf record / 不同 shell wrapper）都必须验证包装本身的中性，否则不能把"加 shield 的总效应"归因给 shield
- **适用场景**：profiling / sanitizer / cgroup / namespace / VM / container 类型的环境改造
- **对立面**：包装的开销远小于待测信号时（比如开销 < 1% 而要测的差异是 50%），可以容忍

### 4. 报告随结论演进必须回头标注

- **原则**：渐进追加多份 markdown 是好做法，但当后续报告**推翻或修正**前份的核心结论时，**前份必须加 SUPERSEDED banner 指向新报告**
- **适用场景**：所有 .artifacts/ 报告，bench 迭代尤其
- **对立面**：纯补充（不否定前份）不需要 banner，单独追加即可

### 5. 廉价中间方案要先想"它对我的具体 workload 有没有意义"

- **原则**：方法论排序不是"先廉价后贵"；是"先适配 workload 的"。"先 cgroup 再 isolcpus" 这种降级路径只在 cgroup 对该 workload 有效时才合理
- **适用场景**：所有"分阶段做"的工程决策
- **对立面**：探索期不知道哪个有效时，先快速试是合理的，但要有"快速否定"机制（比如 30min smoke）

### 6. 用户的朴素怀疑是 truth filter

- **原则**：当 stakeholder 问"真的吗"/"再跑一次"，他们直觉到 something is off。**不要急着维护既有结论，先 replicate**
- **适用场景**：任何对外呈现的数据或结论
- **对立面**：不要把"再跑一次"等同于不信任 —— 这是健康的工程怀疑论
