┌─ R14 架构师 | 支持收敛，但反对全 Direct ─────────────────────┐

  论点：用户的 epoll 类比是对的，但只对了一半。`reactor.hpp:172` 的 Reactor 是 DPDK 这一侧的 *硬件抽象层*——它必须存在，因为 DPDK 没有 epoll，poll-mode 的 burst 循环本身就是 NIC 的所有权人，不能"由用户决定"。但 epoll 模型在 *kernel socket* 一侧不成立：内核 socket 天然支持阻塞 send/recv，threaded `Transport` 服务的不是性能，而是把同步 I/O 隔离到独立线程，让 app 不被阻塞。

  所以正确的轴不是"Direct vs Threaded"，而是 **后端是 poll-mode 还是 blocking**。当前三个 Transport 变体的对称性是错的：
  - kernel + threaded：`Transport` ✓ 真实需求
  - kernel + direct：`DirectTransport` 极少有人用，但合法（小 client）
  - dpdk + threaded：荒谬。把 DPDK 包成 SPSC 队列等于浪费 kernel-bypass
  - dpdk + direct + Reactor：唯一对的组合

  `direct_transport.hpp:334` 已经写着 "Call from Reactor's on_data callback" — 设计意图本来就是 Reactor 驱动 DirectTransport，但 examples 里没人这么写，所以这层意图被埋没了。

┌─ R2 极简主义者 | 强烈支持用户提案 ───────────────────────────┐

  这正是 epoll 的哲学：内核给你 fd 和事件，线程模型是你的事。

  我不要"DirectTxTransport 是 RX 线程化便利封装"这种解释——便利封装应该在用户代码里，不在库里。

┌─ R3 性能狂热者 | 部分反对 ───────────────────────────────────┐

  论点：R2 的"用户自己起线程就行"对 HFT 是天真的。Threaded `Transport` 存在的真正原因不是便利，是 **CPU 隔离**：TX 线程 pinned 到 core A、RX 线程 pinned 到 core B、app 跑在 core C，这是 HFT 标准布局。把 pinning + sched_setaffinity + RT 优先级丢回用户代码，每个用户都会写错一遍。

  但是！这个论据**只对 kernel `SocketTransport` 成立**。对 DPDK，只有一个 lcore 在 burst poll，多线程化 DPDK Transport 等于把缓存行挪到另一个 core 再挪回来，纯负优化。`benchmarks/latency/lat_*_dpdk` 没人用 threaded Transport 也是因为这样。

  所以我支持架构师的拆分：DPDK 侧 Direct-only + Reactor，kernel 侧保留 threaded。但 DirectTxTransport（kernel + 半线程）我同意删——RX 线程而 TX 直接发本来就是个混血，没解决任何真实瓶颈。

### 核心决策

**用户的诊断对了一半**：DPDK 一侧确实应该走 epoll 风格（`Reactor + DirectTransport`），但 kernel 一侧的 threaded `Transport` 有 CPU pinning + RX 隔离的真实价值，不应删除。当前问题不是"变体太多"，而是"DPDK 推荐路径在 examples 里没人演示"，导致用户被 `simple_hft_dpdk.cpp` 误导走到次优组合。

### 方案细节

1. **删 `DirectTxTransport`**（`eph-transport/include/eph/transport/direct_tx_transport.hpp`，883 LOC）
   - 证据：grep 全 repo 显示零生产用户、零 example、零 dpdk 测试，仅 `tests/integration/test_transport_tls_ws_e2e.cpp` 一处编译测试
   - 破坏面：删除该测试中对应的一节即可
   - 同步更新：`presets.hpp` 中 `DirectTx*` 系列 alias、相关文档段落

2. **`presets.hpp` 从 11 个 alias 砍到 4 个**
   - 保留：`DefaultTransport`、`DirectDefaultTransport`、`RawTransport`、`DirectRawTransport`
   - 删除：`SmallTransport`、`LargeTransport`、`EvictTransport`、所有 `DirectTx*`、Direct 系列的 Small/Raw 重复变体
   - 用户需要不同 payload/depth 时直接传模板参数，库不预定义

3. **新增 `examples/simple_hft_dpdk_reactor.cpp`**
   - 演示 `eph::dpdk::Reactor + DirectTransport<TcpSession<>, WsFramer>` 多连接模式
   - 通过 `feed_rx` + `process_pending`（direct_transport.hpp:336/379）把 Reactor burst 喂给 DirectTransport
   - 这是 `direct_transport.hpp:334` 注释的 *设计意图*，但当前没有任何 example 演示

4. **`examples/simple_hft_dpdk.cpp` 顶部加引导注释**
   - 说明 "this example uses threaded Transport for EvictingQueue + pipeline latency measurement convenience; for lowest single-connection latency see `simple_hft_dpdk_reactor.cpp`"
   - 不删，不改实现

5. **保留三个核心类**：`Transport`、`DirectTransport`、`Reactor`
   - 8 天前的 split（god class → 组件化）不撤销
   - 三个类各对应一个 *被验证的* 用例
