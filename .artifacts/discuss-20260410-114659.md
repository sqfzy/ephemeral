## 完整讨论

> 出于篇幅，主报告已在交互中完整呈现。本节按轮次保留关键论点。

### 第 1 轮 — 各角色提出参考架构

**R-Kernel**：Linux 内核 narrow-waist 7 层（net_device → sk_buff → proto → sock → socket → file/file_op → epoll）。每层只有一个 narrow interface，vtable 是 per-type 静态的，sk_buff 是层间共享语言。映射：PacketBuffer/NicQueue/ByteStream/Protocol/Channel/Poller 6 个 concept。反对 R-Lib 的 Pipeline。

**R-Lib**：Netty + Tokio 杂交。5 层：Endpoint(Tokio AsyncRead+Write) / Codec(Tokio Encoder/Decoder) / Channel<E,C>(Tokio Framed + Netty Channel) / EventLoop(Netty) / 可选 Pipeline(模板组合非 runtime chain)。引用 5 个参考库的 API 形态对照表。反驳 R-Kernel：C++ 模板单态化让层数可以减少。

**R-DPDK**：thread-per-core share-nothing。引用 mTCP / F-Stack / Seastar / VPP / Aeron 五个项目的所有权模型。**所有最快的 HFT 网络栈都是 per-core 独立栈**。当前 eph Reactor + Transport 跨线程模型违反共识。提议 Worker 拥有 NIC queue + connections + timer。

**R14 架构师**：推迟选边，列硬约束 C1-C12。关键约束：C10（HFT 通常 < 100 connections，不需要百万并发）+ C11（client 库不是 server）+ C12（必须支持单线程嵌入）。反驳 R-DPDK Worker 模型违反 C12。反驳 R-Lib god class。

**R2 极简主义者**：测试每层"删了会怎样"。最小有效 = 3 concept (Endpoint/Codec/Poller) + 1 类 Channel。EventLoop/Pipeline/Worker/NicQueue/PacketBuffer 都不要。反驳 R-Kernel 7 层是 C 语言下没泛型的产物。

### 第 2 轮 — PacketView 突破

**R-Kernel** 让步 narrow-waist 层数，但**坚持 PacketView 必须存在**：当前 `poll_rx(callback)` 把 mbuf vs span 差异藏在 callback 签名里 → DPDK 强制 memcpy。提议 Endpoint concept 暴露 `PacketView` associated type。这是 sk_buff 的 C++ 翻版。

**R-DPDK** 强烈支持，给出当前实现的开销链（rx_burst → mbuf → callback → memcpy → reassembly）vs 理想路径（mbuf → PacketView → in-place TLS decrypt → codec）。AES-GCM 流式 + aws-lc 支持 in-place encrypt/decrypt。收益估算：每包 1500 bytes × 32 burst × 1M pps = 48 GB/s 内存带宽节省（cache 命中后保守 80% 折扣，仍 >9 GB/s 节省）。撤回 Worker 强制主张。

**R-Lib** 接受 PacketView，提出 TLS 应该是 Endpoint 装饰器（Tokio TlsStream<TcpStream> 模式）：`Channel<TlsEndpoint<DpdkEndpoint>, WsCodec>`。理由：Codec 嵌套违反单一职责，TLS 不是 codec 而是会话状态层。撤回 Pipeline。

**R14** 给出 1.0 草案：3 concept + Channel + ReconnectPolicy。

**R2** 接受骨架但反驳 TlsEndpoint：eph 不应该开第三方装饰器口子。建议 `Channel<E, C, EnableTls>` 编译期 bool。

### 第 3 轮 — TLS 位置裁决

**R-Lib** 反驳 R2：当前 `direct_transport.hpp:349-411` 已有 runtime `if (use_tls)` 分支，每个 packet branch 一次。装饰器路径无 runtime cost。

**R-DPDK** 站 R-Lib 但提性能 caveat：TLS in-place decrypt 要懂 mbuf layout → TlsEndpoint 包 DpdkEndpoint 会让 eph-channel 模块 link dpdk。解决：让 PacketView 暴露 `writable_data() / length() / trim_front() / trim_back()`（sk_buff 的 `skb_pull/skb_trim` C++ 翻版）。

**R-Kernel 的关键裁决**：引用 `net/tls/tls_sw.c`，**Linux TLS 是 ULP (Upper Layer Protocol)**，通过 `setsockopt(SOL_TLS)` 替换 sock proto ops（`tcp_sendmsg → tls_sw_sendmsg`），不是新 socket 类型。**TLS 是 socket 的协议操作替换，不是外包装**。R2 的编译期 bool 是这个语义的直接翻译。R-Lib 的装饰器形式更可组合但语义错位（没有"naked TLS endpoint"）。**裁决：TLS 内置 Channel，编译期 bool**。

**R14** 给出 1.1 草案。

### 第 4 轮 — Poller / Reactor 接口签名

**R-Kernel** 提议 Poller mirror epoll_ctl：接受 handle 不是对象，不持有，不内置 callback，返回 ready event 列表。

**R-Lib** 反对：HFT 用户从来不写 epoll dispatch loop。应该 `Poller::add(Channel*)` + 内部 dispatch 到 on_message。建议两套 API（高层 attach + 低层 add_raw）。

**R-DPDK** 反驳 type-erased Channel 存储违反 C2 zero vdispatch。提议编译期固定 Channel 类型集合：`DpdkPoller<E, C, Tls>` 模板化，单态化 channel 数组。

**R2** 仲裁：不是两套 API，是两个 concept (Poller + ChannelGroup)，后者是 example 不在 core。

**R14** 给出 1.2 草案：9 名字（3 concept + 6 类）。

### 第 5 轮 — 模块切分

**R14** 列三方案：X（保留 eph-transport 名）/ Y（改名 eph-channel）/ Z（按 OSI 切 eph-tls + eph-codec + eph-channel）。

**R2** 强烈支持 Y，反对 X 和 Z：X 撒谎（模块叫 transport 但里面没 Transport 类），Z 过度切分（eph-tls 不能独立使用是 Channel 私有 detail）。

**R-Lib** 提改进版 **Y'**：把 codec 拆出独立 `eph-codec` 模块。理由：WsCodec/RawCodec/LengthPrefixCodec 与 eph-fix/eph-itch/eph-json/eph-book 命名不一致——它们应该都是 codec 但前三个住在 channel 模块里。

**R-Kernel** 站 R-Lib：内核里 protocol 和 codec 是不同域，独立模块对。

**R-DPDK** 中立：模块切分对性能无影响（编译期单态化全部内联）。

**R14** 接受 Y'，更新 1.3 草案。修正依赖图：eph-codec 不依赖 eph-net/eph-dpdk，只依赖 eph-core；eph-channel 同时依赖 eph-net + eph-codec + eph-dpdk。

### 第 6 轮 — API 人体工学验证

**R-Lib** 写出 3 个 use case 完整代码：单连接 / 多连接 / 嵌入用户已有 main loop。**单 → 多升级仅 4 行**。

**R2** 提议官方 alias 限定 4 个：`KernelWsClient` / `DpdkWsClient` / `KernelWsPoller` / `DpdkWsPoller`。

**R-Kernel** 提细节：`poller.add(ch)` 之后用户不能再调 `ch->poll()`（buffer 状态机决定）。

**R-DPDK** 写出 `DpdkPoller::poll()` hot path 伪代码：burst 32 mbuf → 一次 TSC → 5-tuple lookup channel → in-place process → free mbuf。**关键差异 vs 当前实现**：节省每包 memcpy 1500 bytes。

**R14** 给出 1.4 草案：13 名字 + 4 alias。

### 第 7 轮 — Corner cases

**R14** 列 6 个 corner case：reconnect handle 失效 / lifetime / on_message 抛异常 / 多 codec 路由 / 错误模型 / 多核扩展。

**R-DPDK** 解决 reconnect：DPDK 路径不存在（用 connection id 不是 fd）；kernel 路径需要 Channel 通知 Poller 重新注册。

**R-Kernel** 反驳 Poller 自动 re-add（违反封装）。提议 Channel 主动调用 `notify_reconnect`。Lifetime 用 RAII handle 但 Poller 必须 outlive Channel。

**R2** 确认 #6：Worker 作为 example，不进 core。

**R-Lib** 解决 #5：统一 `enum class Error` + `struct ErrorInfo`。所有 concept 方法返回 `std::expected<T, ErrorInfo>`。

**R-Kernel** 接受 unified Error，建议 ErrorInfo.detail 用 `const char*`（避免 dangling string_view）。

### 第 8 轮 — Lifetime 简化

**R-DPDK** 提 HFT 实践：startup 建 connection，shutdown 拆，从不动态创建/销毁。建议默认假设 Poller outlive Channel，文档明说，不做复杂 RAII。

**R14** 接受简化，更新 1.5 草案。

### 第 9 轮 — 并发模型

**R-DPDK** 提多核三方案 A/B/C：A=多 Poller 多线程（用户分配），B=单 Poller 多 worker（work stealing），C=不管。推荐 A 对应 DPDK RSS。

**R-Lib** 提 Netty `EventLoopGroup` 自动分配。

**R2** 反对 PollerGroup 进 core（违反 C12）。

**R-Kernel** 引用 epoll 的多线程文档（EPOLLEXCLUSIVE）：内核也是用户决策，库不强制。

**R14** 决议：core 只单 Poller，多线程用户决策，example 提供 `dpdk_lcore_example.cpp` 和 `kernel_threadpool_example.cpp`。

### 第 10 轮 — 命名敲定

**R-Lib** 给命名候选表 + 业界对照：
- Endpoint vs ByteStream vs Socket vs Transport → **Endpoint**
- Reactor vs Poller vs EventLoop → 倾向 Poller concept + DpdkReactor 实现
- Channel vs Connection vs Pipeline → **Channel**

**R2** 反对 Poller/Reactor 不一致：要么全 Reactor 要么全 Poller。建议**全 Reactor**（GoF 模式名 + eph 已用 + 用户已熟悉）。

**R-Kernel** 数据点：Schmidt 1995 Reactor 定义包含 dispatch handler 责任，Linux epoll 本身只是 Demultiplexer。当前 eph Reactor 实现是真正的 Reactor 模式（不是 Demultiplexer）。中立。

**R-DPDK** 站 R2：Reactor 在 HFT 圈是常用词（ACE/TAO 在金融业广泛使用）。

**R14** 接受 Reactor 命名，更新 1.6 草案。

### 第 11 轮 — 验证现有用例

**R-Lib** 把 7 个 examples 全部映射到 1.6 架构。**EvictingQueue 是唯一非平凡迁移**：从 Channel 模板参数下放到用户代码（on_message 内写入 EvictingQueue）。功能不丢失，只是更显式。

**R-DPDK** 验证 4 个 latency benchmarks：全部能映射，预期 lat_ex_market RX latency 不退化且最好下降（PacketView 路径节省 memcpy）。**这是 ship-readiness 量化指标**。

**R14** 锁定 1.6，进入立场修正。

### 第 12 轮 — 立场修正

所有 5 角色声明改变与坚持。连续 2 轮无新论点，触发终止条件。

## 最终架构方案 v1.6

### 设计哲学

> **eph = 内核 narrow-waist 分层（Endpoint/Reactor/Codec 三个 narrow concept）+ Netty 高层命名（Channel）+ Tokio 类型组合（Channel<E, C, Tls>）+ HFT 单态化（编译期参数化所有 hot path）。**

### 完整类型清单

```
─── eph-core ─────────────────────────────────────────────────
concept Endpoint         (PacketView + connect/send/poll_rx + state)
concept Codec            (decode/encode/max_overhead)

struct ErrorInfo         (Error code + const char* detail)

─── eph-net ─────────────────────────────────────────────────
```

### Concept 表面（草案）

```cpp
// eph-core/include/eph/core/endpoint.hpp
template <class T>
concept Endpoint = requires(T& t, std::chrono::milliseconds to,
                            const void* data, size_t len) {
    typename T::PacketView;     // 后端定义：mbuf-backed or span-backed
    
    { t.connect(to) }       -> std::same_as<std::expected<void, ErrorInfo>>;
    { t.close() }           -> std::same_as<std::expected<void, ErrorInfo>>;
    { t.reset() }           noexcept;
    { t.send(data, len) }   -> std::same_as<std::expected<size_t, ErrorInfo>>;
    { t.poll_rx() }         -> std::same_as<std::expected<typename T::PacketView, ErrorInfo>>;
    { t.last_rx_tsc() }     -> std::convertible_to<uint64_t>;
    { t.mss() }             -> std::convertible_to<uint16_t>;
    { t.state() }           -> std::same_as<TcpState>;
};

// PacketView 必须满足：
struct PacketView {
    uint8_t* writable_data() noexcept;   // in-place mutation 必须
    size_t   length() const noexcept;
    void     trim_front(size_t n) noexcept;   // skb_pull 等价
    void     trim_back(size_t n) noexcept;    // skb_trim 等价
    uint64_t arrival_tsc() const noexcept;
};

// eph-core/include/eph/core/codec.hpp
template <class T>
concept Codec = requires(T& t, const PacketView& pv,
                         uint8_t* out, size_t out_cap) {
    typename T::Frame;
    { t.decode(pv) }                -> std::same_as<std::expected<typename T::Frame, ErrorInfo>>;
    { t.encode(out, out_cap, ...) } -> std::same_as<std::expected<size_t, ErrorInfo>>;
    { T::max_overhead }             -> std::convertible_to<size_t>;
};

// eph-core/include/eph/core/reactor.hpp
template <class T>
concept Reactor = requires(T& r, ChannelLike* ch, std::chrono::milliseconds to) {
    { r.add(ch) }       -> std::same_as<std::expected<void, ErrorInfo>>;
    { r.remove(ch) }    -> std::same_as<std::expected<void, ErrorInfo>>;
    { r.poll() }        -> std::convertible_to<size_t>;
    { r.poll(to) }      -> std::convertible_to<size_t>;
};

// eph-core/include/eph/core/error.hpp
enum class Error {
    Ok = 0,
    ConnectFailed, Disconnected, Timeout,
    TlsHandshakeFailed, TlsRecordBad,
    WsHandshakeFailed, WsFrameBad,
    CodecNeedMoreData, CodecBad,
    WouldBlock, NoData,
};

struct ErrorInfo {
    Error       code;
    const char* detail;   // string literal 或 static storage
};
```

```cpp
class Channel {
public:
    using EndpointType = E;

    static constexpr bool kHasTls = EnableTls;

private:
    E endpoint_;
    C codec_;
    [[no_unique_address]] std::conditional_t<EnableTls, TlsState, std::monostate> tls_;
    ReconnectPolicy reconnect_;
    // ...
};
```

## 已解决的分歧

| 分歧点 | 解决方式 | 关键论据 |
|---|---|---|
| 内核分层 vs 库直译 | C++23 模板单态化把 7 层 collapse 成 3 concept + 1 类 | R2 + R-Kernel |
| TLS 是装饰器还是内置 | **内置**（Channel 模板 bool） | R-Kernel 的 Linux ULP 类比 |
| Reactor 拥有 callback vs 返回 events | **拥有 callback**（Reactor 模式而非 Demultiplexer） | Schmidt 1995 原始定义 + eph 已用 |
| Worker / lcore 进 core 吗 | **不**，作为 example | C12 单线程嵌入约束 |
| Codec 在 channel 模块还是独立 | **独立 eph-codec** | 与 fix/itch/json/book 已经独立的命名一致性 |
| 模块名 eph-transport 保留还是改 | **改为 eph-channel** | 模块名应等于主类型名 |
| 命名 Endpoint vs Transport vs Socket | **Endpoint** | Transport 已被烫到，Socket 太具体 |
| 命名 Channel vs Connection vs Pipeline | **Channel** | Netty 标志性命名 |
| 命名 Reactor vs Poller vs EventLoop | **Reactor** | GoF 模式名 + eph 已用 + 用户已熟悉 |
| 错误模型 | **统一 Error enum + ErrorInfo struct** | R-Lib + R-Kernel 一致 |
| Lifetime 管理 | **文档约定 Reactor outlive Channel**，不做 RAII | R-DPDK 的 HFT 实践 |
| 多核扩展 | **多 Reactor 多线程**（用户决策），不进 core | 对应 DPDK RSS |
| EvictingQueue 何处 | **下放到用户代码**（on_message 内写入） | 解耦 channel 与队列策略 |
| PacketView 是否进 concept | **必须**进 | DPDK 零拷贝路径的兑现 |

## 未解决的权衡（需用户决策）

| 冲突 | A | B | 建议 |

| 是否提供 PollerGroup 作为 example | 提供 | 不提供 | **提供** `examples/multi_reactor_example.cpp`，演示绑核 + RSS |
