## 内容摘要

讨论深入分析了 epoll 风格多路复用 RX 方案的 10 个实现不确定点。核心争议在于：(1) reconnect 阻塞风险——R5 量化证明 10 连接 worst case 20μs << NIC ring 300μs drain time，R1 被说服接受内联 reconnect；(2) rx_loop 逻辑是提取（共享）还是复制——R2 主张复制（差异大，强行共享反而难维护），R14 接受；(3) TLS 能否延迟到 app 线程——R3 证明不能（TLS 1.3 按序解密约束）。最终方案：新建 Reactor 类替代 SharedRxDispatcher，单 RX 线程 + per-connection RxContext + hash 分发 + 内联 reconnect，Transport API 不变。

---

## 10 个不确定点解决清单

| # | 不确定点 | 结论 |
|---|---------|------|
| Q1 | Cache miss 代价 | 可控：实际热数据 1-16KB，不是 48KB 全量 |
| Q2 | reconnect 在哪个线程 | RX 线程内联（利用 poll 间隙） |
| Q3 | 时间预算机制 | 不需要（20μs << 300μs NIC ring） |
| Q4 | 新建 vs 修改 Transport | 新建 Reactor，Transport 不改 |
| Q5 | push vs pull | 两者都支持（沿用 Transport 双模式） |
| Q6 | Reactor 层级 | TcpSession 之上、Transport 之下 |
| Q7 | TLS 延迟到 app 线程 | 不能（TLS 1.3 按序解密约束） |
| Q8 | per-connection buffer 注入 | Reactor 直接调用 process_rx + RxContext |
| Q9 | 不破坏 Transport API | Reactor 独立实现 RX 逻辑 |
| Q10 | reconnect NIC queue 竞争 | 内联 = 同一线程 = 无竞争 |

## 关键设计决策

| 决策 | 选择 | 否决项 | 理由 |
|------|------|--------|------|
| rx_loop 逻辑 | 复制到 Reactor | 提取共享 | 差异大，共享反而难维护 |
| Reactor 类型 | 具体类 | 模板化 | eph-dpdk 内部实现 |
| reconnect 方式 | 内联（同线程） | 独立线程 | 简单、无 NIC queue 竞争 |
| crypto 拆分 | Reactor 拥有 read-side | 共享 | TlsRecordCrypto 已分离 read/write |
| pipe 模型 | 删除 | 共存 | 维护两套不值得 |
