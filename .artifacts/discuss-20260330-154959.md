## 内容摘要

核心争议围绕"自研 SPSC 队列（BoundedQueue/EvictingQueue）vs DPDK rte_ring"展开。R5（第一性原理者）首先指出 EvictingQueue 的覆盖语义在 rte_ring 中根本不存在，这不是选择题而是需求驱动的必然。R14（架构师）论证了 eph-containers 作为纯 C++23 无依赖库的解耦价值——它同时服务 socket 和 DPDK 两条路径。R3（性能狂热者）从指令级分析了 BoundedQueue 的 shadow index 优化相比 rte_ring CAS 路径的延迟优势。R6（维护性倡导者）最终从"应该用 rte_ring"修正为"自研正确但需 ARM64 CI 验证"。共识：自研队列在语义、性能、架构三个维度均优于 rte_ring；rte_ring 的正确使用场景是 mempool（MPMC），不是 SPSC 线程间通信。

## 第 1 轮：核心论点

### 【R3 性能狂热者 | 自研队列胜出】

论点：eph 的自研队列在 HFT 场景下有三个不可替代的性能优势：

1. **SPSC 专用化**：`BoundedQueue` 只需 2 个 atomic（`writer_.tail_` 和 `reader_.head_`），且通过 shadow index 将大部分操作降为 relaxed load（`bounded_queue.hpp:183-189`）。`rte_ring` 即使在 SPSC 模式下，内部仍保留 MPMC 的 CAS 路径和更多元数据，这些都是不必要的 cache line 污染。

2. **EvictingQueue 的 seqlock 语义**：`evicting_queue.hpp:219-243` 实现的 writer-wait-free + reader-lock-free 语义在 `rte_ring` 中根本不存在。`rte_ring` 没有"覆盖旧数据"的模式。

3. **Reactor 的零 ring 设计**：`reactor.hpp:259` "Direct dispatch — zero ring overhead"。旧方案 `SharedRxDispatcher` 用 `rte_ring` 做中间缓冲，Reactor 直接 inline 调 `process_rx`。

### 【R6 维护性倡导者 | rte_ring 更稳健】

论点：
1. 自研队列总代码量近 2000 行 + 7 个 benchmark。rte_ring 由 DPDK 社区维护，经过形式化验证。
2. seqlock 的 memory ordering 极其脆弱，一个微小错误可能只在 ARM64 上表现。
3. 新人理解 encode_seq/decode_idx 的位编码成本远高于 rte_ring_enqueue API。

### 【R4 实用主义者 | 要数据说话】

论点：
1. 没有 rte_ring vs BoundedQueue 的对比 benchmark，"更优"是推测。
2. 队列延迟（~10-50ns）远小于网络 RTT（~50-500μs），可能不是瓶颈。
3. Reactor 的零 ring 设计是架构选择，不是队列选择。

### 【R5 第一性原理者 | 重新审视需求】

论点：问题本身问错了。正确的问题是"项目需要什么语义的线程间通信？"
- SPSC backpressure → rte_ring 可以做
- Latest-value 覆盖 → rte_ring **做不到**
- 零拷贝 inline dispatch → 与队列无关

核心洞察：项目不是"选择了自研替代 rte_ring"，而是"需要 rte_ring 不支持的语义"。

### 【R14 架构师 | 解耦价值】

论点：
1. eph-containers 是纯 C++23 header-only 库，零外部依赖。用 rte_ring 会让 transport.hpp 必须链接 DPDK。
2. transport.hpp:145-146 的模板参数设计让队列实现可自由切换，rte_ring 的 C API 无法参与 C++ 模板元编程。
3. 自研队列可以在任何机器上测试，不需要 DPDK 环境。

## 最终方案

### 核心决策
eph-dpdk 使用自研队列是正确选择，且在当前架构下优于 rte_ring。

### 方案细节

| 维度 | 自研队列 | rte_ring | 结论 |
|------|----------|----------|------|
| 覆盖语义（EvictingQueue） | 原生支持 | 不支持 | **自研唯一选择** |
| SPSC backpressure（BoundedQueue） | shadow index 优化，2 atomic ops | CAS-based，3+ atomic ops | **自研更优** |
| RX 分发（Reactor） | inline dispatch，零 ring | 需 enqueue/dequeue 中间层 | **自研更优** |
| 依赖隔离 | 纯 C++23，零外部依赖 | 需链接 libdpdk | **自研更优** |
| 模板集成 | 原生 C++ template | C API + void* | **自研更优** |
| 社区验证 | 项目内测试 | DPDK 社区大规模验证 | **rte_ring 更优** |
| ARM64 正确性 | 需要 TSan CI | 社区已验证 | **rte_ring 更优** |

### 已解决的分歧
- 维护性 vs 性能 → 核心逻辑精简，维护性风险可控
- 需不需要对比数据 → 语义需求分析足以判断
- adapter 方案可行性 → 被否定，会破坏 if constexpr 零开销 dispatch

### 未解决的权衡
- ARM64 正确性验证：若部署 ARM64 应投入 TSan on ARM64 CI；若仅 x86 则现有测试足够
  → 建议添加 ARM64 CI
